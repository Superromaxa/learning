# II. Функции, указатели и управление памятью

Материал главы соответствует Go 1.27. В ней рассматриваются обычные функции, передача значений и указателей, время жизни данных и сборщик мусора стандартной реализации Go. Обобщённые функции и методы пользовательских типов будут подробно рассмотрены в следующих главах.

## §2.1. Объявление и вызов функции

Функция объединяет последовательность действий, получает входные значения и при необходимости возвращает результат. Обычная функция объявляется словом `func`:

```go
func add(left int, right int) int {
	return left + right
}
```

Здесь:

- `add` — имя функции;
- `left` и `right` — параметры;
- стоящий после каждого параметра `int` — его тип;
- последний `int` — тип результата;
- `return left + right` завершает функцию и возвращает вычисленное значение.

Функцию вызывают по имени, передавая аргументы в круглых скобках:

```go
package main

import "fmt"

func add(left int, right int) int {
	return left + right
}

func main() {
	result := add(10, 20)
	fmt.Println(result)
}
```

> Вывод: `30`.

Параметр — локальная переменная в объявлении функции. Аргумент — конкретное значение, переданное при вызове. В вызове `add(10, 20)` числа `10` и `20` являются аргументами, а `left` и `right` — параметрами, которые получат их значения.

### Параметры одного типа

Если несколько соседних параметров имеют одинаковый тип, тип можно написать один раз:

```go
func add(left, right int) int {
	return left + right
}
```

Эта запись означает то же самое, что `left int, right int`. Сокращение действует только на одну соседнюю группу имён:

```go
func format(name string, width, precision int, enabled bool) string {
	// ...
	return name
}
```

### Функция без параметров или результата

Пустой список параметров всё равно записывается круглыми скобками:

```go
func printSeparator() {
	println("---")
}
```

Если функция ничего не возвращает, после списка параметров не указывается `void` или другой специальный тип. В Go просто отсутствует список результатов.

Такую функцию можно завершить явным `return` без значений:

```go
func check(enabled bool) {
	if !enabled {
		return
	}

	println("enabled")
}
```

Или позволить выполнению дойти до закрывающей фигурной скобки. `return` здесь нужен для раннего выхода, а не для передачи результата.

### Сигнатура функции

Сигнатура описывает параметры и результаты функции. Например:

```go
var predicate func(string, int) bool
```

Это тип функции, принимающей `string` и `int` и возвращающей `bool`. Имена параметров в тип функции не входят:

```go
var first func(name string, age int) bool
var second func(string, int) bool
```

Обе записи описывают один и тот же тип. Имена нужны реализации и читателю, но совместимость функций определяется типами и порядком параметров и результатов.

### Перед вызовом вычисляются аргументы

Сначала вычисляются значение вызываемой функции и аргументы, затем создаются параметры вызова, и только после этого начинает выполняться тело функции:

```go
func next(value int) int {
	println("next", value)
	return value + 1
}

func use(first, second int) {
	println("use", first, second)
}

func main() {
	use(next(1), next(2))
}
```

> Сначала выполняется `next(1)`, затем `next(2)`, после чего вызывается `use(2, 3)`.

Обычные вызовы функций, методов и операции получения значений из каналов вычисляются в лексическом порядке слева направо. При этом не следует строить код вокруг запутанных побочных эффектов: промежуточные переменные часто делают порядок очевиднее.

### В Go нет перегрузки функций

В одном пакете нельзя объявить несколько функций с одним именем, даже если у них разные параметры:

```go
func printValue(value int) {}

// func printValue(value string) {} // ошибка: printValue уже объявлена
```

Разные операции получают разные имена, либо обобщаются с помощью интерфейсов или параметров типов. Отсутствие перегрузки упрощает поиск конкретной функции по её имени.

### Нет аргументов по умолчанию и именованных аргументов

У параметров нельзя задать значения по умолчанию:

```go
// func connect(host string, port int = 8080) {} // такого синтаксиса нет
```

Нельзя и передавать аргументы по именам:

```go
// connect(port: 8080, host: "localhost") // такого синтаксиса нет
```

Аргументы сопоставляются параметрам по позиции. Необязательные настройки обычно представляют отдельным типом конфигурации или функциональными опциями, но эти приёмы требуют знания структур, методов и замыканий и будут разобраны позже.

### Неиспользуемый параметр

Компилятор запрещает неиспользуемые локальные переменные, но не запрещает неиспользуемые параметры:

```go
func handle(value int) {
	println("handled")
}
```

Такой код компилируется. Это удобно при реализации заранее заданной сигнатуры, однако неиспользуемый параметр может указывать и на незавершённую логику.

Имя параметра можно не указывать, если оно не нужно:

```go
func handle(int) {
	println("handled")
}
```

В объявлении обычной функции такая форма встречается редко; чаще безымянные параметры используются в типах функций и интерфейсах.

В одном списке параметров или результатов имена должны быть либо у всех элементов, либо ни у одного. Пустой идентификатор `_` считается именем и позволяет явно не использовать отдельный параметр результата.

### Порядок объявлений и функция без тела

Функцию можно вызвать в тексте раньше её объявления:

```go
func main() {
	println(answer())
}

func answer() int {
	return 42
}
```

Пакет проверяется как единое целое, поэтому предварительные объявления для обычных Go-функций не нужны.

Объявление без тела не является способом сообщить, что Go-реализация будет написана ниже:

```go
func flush(begin, end uintptr) // реализация находится вне Go, например в assembly
```

Такая форма используется для функций, реализованных вне Go. У обобщённой функции тело пропустить нельзя.

## §2.2. Возвращаемые значения

### Один результат

Тип единственного безымянного результата можно записать без скобок:

```go
func square(value int) int {
	return value * value
}
```

Если у функции указан результат, каждый возможный обычный путь выполнения должен завершаться `return` с подходящим значением:

```go
func sign(value int) int {
	if value < 0 {
		return -1
	}
	if value > 0 {
		return 1
	}
	return 0
}
```

Если убрать последний `return`, компилятор сообщит, что возврат отсутствует. Он не предполагает, какое значение следовало вернуть.

Бесконечный цикл без относящегося к нему `break` считается завершающей инструкцией, поэтому после него `return` не требуется:

```go
func waitForever() int {
	for {
		// функция не доходит до конца
	}
}
```

### Несколько результатов

Функция может возвращать несколько значений:

```go
func divide(dividend, divisor int) (int, int) {
	return dividend / divisor, dividend % divisor
}

func main() {
	quotient, remainder := divide(17, 5)
	println(quotient, remainder)
}
```

> Вывод: `3 2`.

Скобки после списка параметров содержат список типов результатов. Возвращается не один специальный объект-кортеж: вызов является многозначным выражением, результаты которого принимаются несколькими переменными в подходящем контексте.

Нельзя сохранить такой вызов в одну обычную переменную:

```go
// result := divide(17, 5) // ошибка: два значения в однозначном контексте
```

Ненужный результат отбрасывается пустым идентификатором `_`:

```go
quotient, _ := divide(17, 5)
```

Если не нужен ни один результат, обычный вызов функции можно использовать как отдельную инструкцию:

```go
divide(17, 5)
```

Результаты вычисляются, но отбрасываются. Для функции без полезных побочных эффектов такой вызов обычно бессмыслен.

### Значение и ошибка

Распространённая сигнатура Go возвращает полезный результат и ошибку:

```go
func parsePort(text string) (int, error) {
	// ...
	return 8080, nil
}
```

`error` — встроенный интерфейс для описания ошибки, а `nil` здесь означает её отсутствие. Само по себе возвращение `error` ничего автоматически не обрабатывает: вызывающая сторона должна проверить результат.

```go
port, err := parsePort("8080")
if err != nil {
	// обработка ошибки
	return
}

println(port)
```

Ошибки и интерфейсы будут рассмотрены подробнее отдельно. На уровне функций важно, что несколько возвращаемых значений позволяют передавать результат и информацию о неудаче без скрытого глобального состояния.

### Передача нескольких результатов другой функции

Если одна функция возвращает ровно те значения, которые принимает другая, результаты можно передать напрямую:

```go
func split() (int, int) {
	return 10, 20
}

func add(left, right int) int {
	return left + right
}

func main() {
	result := add(split())
	println(result)
}
```

> Вывод: `30`.

Вызов `split()` должен быть единственным аргументом внешнего вызова. Запись `add(1, split())` недопустима: нельзя смешать отдельный аргумент с разворачиванием многозначного результата таким способом.

### Именованные результаты

Результатам можно дать имена:

```go
func divide(dividend, divisor int) (quotient int, remainder int) {
	quotient = dividend / divisor
	remainder = dividend % divisor
	return quotient, remainder
}
```

Именованные результаты являются локальными переменными функции. При входе они получают нулевые значения своих типов.

Если результаты именованы, разрешён пустой `return`:

```go
func divide(dividend, divisor int) (quotient int, remainder int) {
	quotient = dividend / divisor
	remainder = dividend % divisor
	return
}
```

Такой `return` возвращает текущие значения `quotient` и `remainder`. Его часто называют naked return — «голый возврат».

В короткой функции он может быть понятен, но в длинной заставляет искать последние изменения результатов по всему телу. Поэтому имена результатов полезны как документация и для взаимодействия с `defer`, а значения часто всё равно лучше перечислять явно.

### Затенение именованного результата

Именованный результат можно случайно скрыть во вложенном блоке:

```go
func calculate() (result int, err error) {
	if true {
		result, err := operation()
		_ = result
		if err != nil {
			// return // компилятор отклонит пустой return: err затенён
			return 0, err
		}
	}

	return result, err
}
```

Короткое объявление во вложенном блоке создаёт новые `result` и `err`. Они не являются именованными результатами функции. В месте, где затенён результат, компилятор может запретить пустой `return`, чтобы не скрыть вероятную ошибку.

### Результаты устанавливаются до выполнения `defer`

При `return expression` выражения сначала вычисляются и присваиваются результирующим переменным. Затем выполняются отложенные вызовы, и только после этого управление возвращается вызывающей стороне. Поэтому отложенная функция может изменить именованный результат:

```go
func answer() (result int) {
	defer func() {
		result *= 2
	}()

	return 21
}
```

`return 21` сначала присваивает `21` переменной `result`, затем отложенная функция меняет её на `42`. Вызов `answer()` возвращает `42`.

Такой механизм полезен в обёртках и инструментах наблюдения, но скрытое изменение результата может ухудшить читаемость. Его не следует использовать только ради сокращения нескольких строк.

## §2.3. Функции как значения

Функция в Go может быть значением: её можно записать в переменную, передать как аргумент и вернуть из другой функции.

```go
func add(left, right int) int {
	return left + right
}

func main() {
	operation := add
	result := operation(10, 20)
	println(result)
}
```

Переменная `operation` имеет тип `func(int, int) int`.

### Явный тип функции

Тип можно записать отдельно:

```go
var operation func(int, int) int
operation = add
```

Имена параметров необязательны и не меняют тип:

```go
var first func(left int, right int) int
var second func(int, int) int

first = second
second = first
```

Обе переменные имеют идентичный тип функции.

### Нулевое значение функции

Нулевое значение переменной функционального типа — `nil`:

```go
var operation func(int, int) int

if operation == nil {
	println("function is not configured")
}
```

Вызов `nil`-функции вызывает `panic`:

```go
// result := operation(1, 2) // panic во время выполнения
```

Значения функций можно сравнивать только с `nil`. Две ненулевые функции нельзя сравнить между собой через `==`, даже если они созданы из одного объявления.

### Функция обратного вызова

Функцию, переданную другой функции для последующего вызова, называют callback:

```go
func apply(left, right int, operation func(int, int) int) int {
	return operation(left, right)
}

func multiply(left, right int) int {
	return left * right
}

func main() {
	result := apply(6, 7, multiply)
	println(result)
}
```

> Вывод: `42`.

`apply` не знает конкретную реализацию операции. Она знает только требуемую сигнатуру.

Если `operation` может быть `nil`, это нужно проверить явно либо документировать, что `nil` недопустим:

```go
func apply(left, right int, operation func(int, int) int) int {
	if operation == nil {
		return 0
	}
	return operation(left, right)
}
```

Молчаливое возвращение нуля подходит не каждому API. Иногда правильнее вернуть ошибку или позволить программе завершиться с понятным `panic`; выбор зависит от контракта функции.

### Анонимная функция

Функциональный литерал создаёт функцию без объявленного имени:

```go
operation := func(left, right int) int {
	return left - right
}

println(operation(10, 3))
```

> Вывод: `7`.

Анонимную функцию можно вызвать сразу:

```go
result := func(value int) int {
	return value * value
}(6)
```

Сначала создаётся функция, затем `(6)` немедленно вызывает её. `result == 36`.

Обычное именованное объявление функции нельзя вложить в другую функцию:

```go
func outer() {
	// func inner() {} // ошибка синтаксиса

	inner := func() {}
	inner()
}
```

Для локального поведения используют функциональный литерал и при необходимости записывают его в переменную.

### Замыкание

Анонимная функция может использовать переменные внешней функции:

```go
func makeCounter() func() int {
	count := 0

	return func() int {
		count++
		return count
	}
}

func main() {
	counter := makeCounter()
	println(counter())
	println(counter())
}
```

> Вывод: `1`, затем `2`.

Возвращённая функция образует замыкание: она сохраняет доступ к переменной `count` даже после завершения `makeCounter`. Переменная живёт столько, сколько она доступна через замыкание. Компилятор размещает данные так, чтобы этот доступ оставался корректным.

Замыкание захватывает переменную, а не неизменяемую копию её текущего значения:

```go
value := 10

read := func() int {
	return value
}

value = 20
println(read())
```

> Вывод: `20`.

Если нужна отдельная копия, её нужно создать явно:

```go
value := 10
captured := value

read := func() int {
	return captured
}
```

Начиная с семантики языка Go 1.22, переменные, объявленные заголовком цикла `for`, создаются отдельно для каждой итерации. Это устранило распространённую ошибку, при которой все замыкания видели последнее значение счётчика. Однако внешняя переменная, присваиваемая в цикле, по-прежнему остаётся одной общей переменной.

### Рекурсия

Функция может вызывать саму себя:

```go
func factorial(value uint64) uint64 {
	if value <= 1 {
		return 1
	}
	return value * factorial(value-1)
}
```

У рекурсии должен быть базовый случай, прекращающий дальнейшие вызовы. Иначе стек горутины будет расти до исчерпания доступной памяти или другого ограничения среды выполнения.

Go использует растущие стеки горутин, поэтому начальный стек невелик и увеличивается по необходимости. Это не делает неограниченную рекурсию безопасной. Кроме того, Go не гарантирует оптимизацию хвостовой рекурсии, поэтому цикл часто предсказуемее и экономнее.

## §2.4. Вариативные функции

Последний параметр функции может принимать переменное количество аргументов:

```go
func sum(values ...int) int {
	total := 0
	for _, value := range values {
		total += value
	}
	return total
}
```

`...int` означает: при вызове разрешено передать ноль или больше значений типа `int`.

```go
sum()
sum(10)
sum(10, 20, 30)
```

Внутри функции `values` имеет тип `[]int`, то есть является срезом. При вызове без вариативных аргументов функция получает `nil`-срез длины ноль.

Вариативный параметр обязан быть последним:

```go
func logValues(prefix string, values ...int) {}

// func invalid(values ...int, suffix string) {} // ошибка компиляции
```

### Передача готового среза

Срез можно развернуть оператором `...`:

```go
numbers := []int{10, 20, 30}
result := sum(numbers...)
```

Без `...` передавался бы один аргумент типа `[]int`, а функция ожидает отдельные `int` для вариативной части.

Когда используется `numbers...`, срез передаётся как variadic-часть напрямую; новый срез для неё не создаётся. Поэтому функция видит те же элементы и может изменить их:

```go
func reset(values ...int) {
	for index := range values {
		values[index] = 0
	}
}

func main() {
	numbers := []int{1, 2, 3}
	reset(numbers...)
}
```

После вызова элементы `numbers` равны нулю.

Нельзя смешать отдельные variadic-аргументы и развёрнутый срез в одном вызове обычной функции:

```go
numbers := []int{20, 30}

// sum(10, numbers...) // ошибка компиляции
```

При необходимости сначала создают общий срез или делают несколько вызовов. Встроенная функция `append` имеет специальные правила, но они не меняют правила пользовательских вариативных функций.

### Цена вариативного вызова

При вызове `sum(1, 2, 3)` компилятор формирует срез с переданными значениями. Это не обязательно приводит к выделению памяти в куче: решение зависит от escape analysis и оптимизаций компилятора. Нельзя делать вывод «variadic всегда выделяет память» только по синтаксису.

Если функция находится на горячем пути, фактические выделения проверяют бенчмарком с `-benchmem` или профилем, а не предположением.

## §2.5. Отложенные вызовы `defer`

Инструкция `defer` откладывает вызов до завершения окружающей функции:

```go
func example() {
	println("start")
	defer println("finish")
	println("body")
}
```

> Вывод: `start`, `body`, `finish`.

Отложенный вызов выполняется, когда функция:

- выполняет `return`;
- доходит до конца тела;
- покидает обычный ход выполнения из-за `panic`.

`defer` привязан к функции, а не к ближайшему блоку. Выход из `if` или одной итерации цикла сам по себе не запускает отложенные вызовы.

### Аргументы вычисляются сразу

Функция и аргументы отложенного вызова вычисляются в момент выполнения `defer`, хотя сам вызов происходит позже:

```go
func example() {
	value := 10
	defer println(value)
	value = 20
}
```

> Вывод: `10`.

В `defer println(value)` сохраняется текущее значение `value`. Последующее присваивание его не меняет.

Замыкание ведёт себя иначе, потому что обращается к самой внешней переменной при своём позднем выполнении:

```go
func example() {
	value := 10
	defer func() {
		println(value)
	}()
	value = 20
}
```

> Вывод: `20`.

В первом примере значение передано аргументом и скопировано сразу. Во втором отложенная функция захватила переменную.

### Обратный порядок

Несколько отложенных вызовов выполняются в обратном порядке — последним добавлен, первым выполнен:

```go
func example() {
	defer println(1)
	defer println(2)
	defer println(3)
}
```

> Вывод: `3`, `2`, `1`.

Такой порядок удобен для симметричного освобождения вложенных ресурсов.

Если значение отложенной функции равно `nil`, `panic` возникает не в момент выполнения `defer`, а позже, когда runtime попытается вызвать сохранённое значение:

```go
func example() {
	var callback func()
	defer callback()

	println("body")
}
```

Строка `body` успеет вывестись, после чего выход из `example` приведёт к `panic`.

### Освобождение ресурса

Типичное применение `defer` — гарантировать вызов `Close` после успешного открытия ресурса:

```go
file, err := os.Open("data.txt")
if err != nil {
	return err
}
defer file.Close()

// работа с file
```

`defer` нужно устанавливать только после проверки ошибки: при неудачном `os.Open` корректного файла для закрытия нет.

Ошибка отложенного `Close` в этом примере теряется. Для операции записи она может быть важна, поскольку часть данных буферизуется и окончательная ошибка появляется только при закрытии. Тогда результат `Close` обрабатывают явно или через отложенную функцию с именованным результатом.

### `defer` в цикле

Отложенные вызовы не выполняются в конце каждой итерации:

```go
func process(names []string) error {
	for _, name := range names {
		file, err := os.Open(name)
		if err != nil {
			return err
		}
		defer file.Close()

		// обработка файла
	}

	return nil
}
```

Все файлы останутся открыты до выхода из `process`. При большом количестве итераций программа может исчерпать файловые дескрипторы.

Ресурс одной итерации удобно ограничить отдельной функцией:

```go
func processFile(name string) error {
	file, err := os.Open(name)
	if err != nil {
		return err
	}
	defer file.Close()

	// обработка файла
	return nil
}

func process(names []string) error {
	for _, name := range names {
		if err := processFile(name); err != nil {
			return err
		}
	}
	return nil
}
```

Теперь `file.Close()` выполняется после каждой обработки.

Современный компилятор оптимизирует многие `defer`, поэтому отказываться от безопасного освобождения ресурсов из-за старого правила «defer всегда дорогой» не следует. На действительно критическом пути стоимость измеряют.

`defer` не выполняется, если процесс прекращён немедленно, например через `os.Exit`, `log.Fatal`, внешнее принудительное завершение или фатальную ошибку среды выполнения. Он не является заменой протоколу надёжного хранения данных.

## §2.6. Передача аргументов по значению

В Go все параметры передаются по значению. При вызове значение каждого аргумента присваивается новой локальной переменной-параметру.

```go
func change(value int) {
	value = 100
}

func main() {
	number := 10
	change(number)
	println(number)
}
```

> Вывод: `10`.

`change` изменяет только свой параметр `value`. Переменная `number` вызывающей функции не меняется.

Фраза «передача по значению» не означает, что всегда копируется весь объём данных, к которому можно получить доступ через значение. Копируется именно представление значения данного типа. Например, указатель содержит адрес; при передаче указателя копируется адрес, но обе копии позволяют обратиться к одному объекту.

Срезы, отображения, каналы, интерфейсы, строки и функции тоже являются значениями. Некоторые из них внутри содержат ссылки на другие данные. Копирование такого значения может сохранить общий доступ к этим данным. Поэтому выражение «ссылочный тип» иногда используют неформально, но отдельного общего механизма передачи параметров по ссылке в Go нет.

### Копия не всегда означает дорогую операцию

Компилятор обязан сохранить наблюдаемую семантику копирования, но не обязан буквально переносить каждое значение так, как это представляется по исходному коду. Внутренние соглашения вызова, регистры, встраивание функции и другие оптимизации зависят от реализации.

Поэтому решение передавать указатель не следует принимать только из предположения, что «любая копия медленная». Нужно учитывать:

- должен ли вызываемый код изменять исходное значение;
- нужен ли `nil` как отдельное состояние;
- размер и устройство типа;
- согласованность API;
- фактические результаты профилирования.

Указатель сам по себе тоже имеет цену: он создаёт aliasing — несколько путей доступа к одним данным, может увеличить работу GC и иногда мешает оптимизациям.

## §2.7. Указатели

У каждого адресуемого объекта есть адрес в памяти. Указатель хранит адрес переменной определённого типа.

Если объект имеет тип `T`, указатель на него имеет тип `*T`:

```go
number := 10
pointer := &number
```

Здесь:

- `number` имеет тип `int`;
- `&number` получает адрес `number` и имеет тип `*int`;
- `pointer` хранит этот адрес;
- `*pointer` обращается к переменной по сохранённому адресу.

```go
*pointer = 20
println(number)
```

> Вывод: `20`.

Новый `int` при разыменовании не создаётся. `number` и `*pointer` обозначают одну переменную двумя способами.

Символ `*` используется в двух ролях:

```go
var pointer *int // * участвует в типе *int
value := *pointer // * разыменовывает указатель
```

Во втором выражении указатель должен указывать на доступную живую переменную. В приведённом фрагменте `pointer` равен `nil`, поэтому фактическое выполнение `*pointer` вызвало бы `panic`.

### Нулевой указатель

Нулевое значение любого указательного типа — `nil`:

```go
var pointer *int

if pointer == nil {
	println("no value")
}
```

`nil` означает, что указатель не указывает на переменную. Его можно хранить, передавать и сравнивать, но нельзя разыменовывать:

```go
// value := *pointer // panic: разыменование nil
```

В отличие от C++, в Go нет литерала `nullptr`. Предварительно объявленный идентификатор `nil` используется также для некоторых других типов, но само слово `nil` не имеет самостоятельного типа и требует контекста:

```go
var first *int = nil
var second *string = nil

// value := nil // ошибка: невозможно вывести тип
```

### Сравнение указателей

Указатели можно сравнивать через `==` и `!=`:

```go
first := 10
second := 10

p := &first
q := &first
r := &second

println(p == q) // true
println(p == r) // false
```

`p` и `q` указывают на одну переменную. Равенство значений `first` и `second` не делает равными их адреса.

Упорядочивающих операций `<`, `>` и подобных для указателей нет. Обычная программа не должна определять относительный «порядок объектов в памяти».

Для указателей на разные переменные нулевого размера спецификация допускает равенство адресов. Поэтому адрес не следует использовать как универсальный уникальный идентификатор объекта.

Обычные указатели разных базовых типов нельзя произвольно присваивать друг другу:

```go
number := 10
integerPointer := &number

// var stringPointer *string = integerPointer // ошибка компиляции
```

Тип `*int` сообщает не только числовой адрес, но и тип доступного по нему значения.

### Какие значения можно адресовать

Оператор `&` применим к адресуемому значению: переменной, допустимому разыменованию, некоторым полям и элементам. Нельзя получить адрес результата обычного вычисления или константы:

```go
// pointer := &42      // ошибка: константа не является переменной
// pointer := &(10+20) // ошибка: результат выражения неадресуем
```

В Go 1.27 для создания указателя на вычисленное значение можно использовать `new(expression)`:

```go
pointer := new(10 + 20)
println(*pointer) // 30
```

Отдельное исключение разрешает брать адрес составного литерала, например `&SomeStruct{}`, но составные типы будут рассмотрены позже.

### В Go нет арифметики указателей

К обычному указателю нельзя прибавить число или вычесть из него число:

```go
pointer := &number

// pointer++    // ошибка компиляции
// pointer += 1 // ошибка компиляции
```

Для перехода по последовательности данных используют индексацию и срезы. Пакет `unsafe` позволяет выполнять низкоуровневые преобразования адресов, но выводит код за пределы обычных гарантий типобезопасности и требует отдельного разбора.

### Указатель на указатель

Указатель сам является переменной, поэтому можно получить и его адрес:

```go
number := 10
pointer := &number
pointerToPointer := &pointer

**pointerToPointer = 30
println(number)
```

> Вывод: `30`.

`pointerToPointer` имеет тип `**int`. Первое разыменование получает `pointer`, второе — `number`.

Такие типы встречаются реже, чем в C, поскольку функция может возвращать несколько значений и многие API не требуют выходных параметров. Но указатель на указатель полезен, если функция действительно должна заменить сам указатель вызывающей стороны.

### Операции `*&x` и `&*p`

Для адресуемой переменной `x` выражение `*&x` обозначает саму `x`:

```go
number := 10
*&number = 20
```

Для действительного указателя выражение `&*pointer` снова получает тот же адрес:

```go
number := 10
pointer := &number
same := &*pointer
println(same == pointer) // true
```

Но `*pointer` всё равно вычисляется как разыменование. Если `pointer == nil`, выражение `&*pointer` вызывает `panic`, как и обычное `*pointer`:

```go
var pointer *int

// same := &*pointer // panic: сначала разыменовывается nil
```

Сочетание операторов не делает недействительный указатель безопасным.

### `new`

Встроенная функция `new` создаёт и инициализирует переменную, затем возвращает указатель на неё:

```go
pointer := new(int)
println(*pointer)

*pointer = 42
println(*pointer)
```

> Вывод: сначала `0`, затем `42`.

`new(int)` имеет тип `*int`, а созданная переменная получает нулевое значение `int`.

Начиная с Go 1.27, `new` принимает не только тип, но и выражение:

```go
pointer := new(42)
println(*pointer)
```

> Вывод: `42`.

`new(42)` создаёт переменную типа `int`, инициализированную значением `42`, и возвращает `*int`. У нетипизированной константы сначала выбирается её тип по умолчанию. В версиях Go до 1.27 аргументом `new` мог быть только тип.

Записи

```go
pointer := new(int)
```

и

```go
value := 0
pointer := &value
```

дают указатель на отдельную переменную `int` с нулевым значением. Но это не означает, что `new` обязательно размещает её в куче, а локальное объявление — обязательно на стеке. Конкретное размещение выбирает компилятор.

`new(T)` и `make(T, ...)` выполняют разные задачи. `new` создаёт одну переменную любого типа и возвращает `*T`. `make` инициализирует внутреннее устройство среза, отображения или канала и возвращает значение самого типа `T`, а не `*T`.

### `uintptr` не является указателем

`uintptr` — целое число, достаточно большое для хранения битового представления адреса. Оно не сохраняет объект живым для GC:

```go
address := uintptr(unsafe.Pointer(pointer))
```

После преобразования в `uintptr` получается число. Сборщик мусора не обязан считать его ссылкой на объект, а стек горутины или другая реализация памяти может измениться между операциями. Нельзя надолго сохранять такой адрес и позже бездумно превращать его обратно в указатель.

Правильность кода с `unsafe.Pointer` зависит от строго определённых допустимых шаблонов преобразований. Само наличие числового адреса не гарантирует, что объект всё ещё существует.

### Указатель на функцию обычно не нужен

Функциональное значение уже можно передавать и вызывать напрямую:

```go
operation := add
result := operation(10, 20)
```

Создать `*func(int, int) int` технически возможно, но это почти никогда не даёт преимущества. Нулевое состояние уже представлено `nil`-функцией, а копирование функционального значения не копирует машинный код функции.

## §2.8. Указатели в функциях

### Изменение переменной вызывающей стороны

Чтобы функция могла изменить исходную переменную, ей передают указатель:

```go
func increment(value *int) {
	*value++
}

func main() {
	number := 10
	increment(&number)
	println(number)
}
```

> Вывод: `11`.

Запись `*value++` разбирается как `(*value)++`: операция увеличивает число, на которое указывает `value`. Сам указатель не увеличивается — арифметики указателей в Go нет.

### Указатель тоже передаётся по значению

Функция получает копию адреса:

```go
func resetPointer(pointer *int) {
	value := 100
	pointer = &value
}

func main() {
	number := 10
	pointer := &number

	resetPointer(pointer)
	println(*pointer)
}
```

> Вывод: `10`.

`resetPointer` изменила только локальную копию `pointer`. Исходная переменная-указатель в `main` всё ещё хранит адрес `number`.

Если требуется заменить указатель вызывающей стороны, можно вернуть новый указатель:

```go
func replacement() *int {
	value := 100
	return &value
}

func main() {
	pointer := replacement()
	println(*pointer)
}
```

Либо передать `**int`, но возвращаемое значение часто проще читать:

```go
func resetPointer(pointer **int) {
	value := 100
	*pointer = &value
}
```

### Проверка `nil`

Если `nil` допустим по контракту, функция должна обработать его до разыменования:

```go
func increment(value *int) bool {
	if value == nil {
		return false
	}

	*value++
	return true
}
```

Но автоматическая проверка каждого указателя не всегда правильна. Иногда `nil` означает ошибку программиста, и немедленный `panic` точнее показывает нарушение контракта, чем молчаливое бездействие. Допустимость `nil` должна быть частью документации API.

### Обмен значений

С указателями можно реализовать обмен:

```go
func swap(left, right *int) {
	*left, *right = *right, *left
}
```

```go
first := 10
second := 20

swap(&first, &second)
```

После вызова `first == 20`, а `second == 10`.

Однако для локального кода отдельная функция часто не нужна:

```go
first, second = second, first
```

Множественное присваивание выражает намерение напрямую.

### Aliasing

Несколько указателей могут обозначать одну переменную:

```go
number := 10
first := &number
second := &number

*first = 50
println(*second)
```

> Вывод: `50`.

Такое совместное обращение называется aliasing. Изменение через один путь видно через другой. Это полезно, но усложняет рассуждение о состоянии: для понимания значения недостаточно смотреть только на текущую строку.

В конкурентной программе доступ через разные указатели к одной памяти требует синхронизации. Сборщик мусора следит за временем жизни объекта, но не предотвращает гонки данных.

### Возврат указателя на локальную переменную

В Go можно безопасно вернуть адрес локальной переменной:

```go
func createNumber() *int {
	value := 42
	return &value
}

func main() {
	pointer := createNumber()
	println(*pointer)
}
```

> Вывод: `42`.

После выхода из `createNumber` переменная не уничтожается, пока на неё можно ссылаться. Компилятор размещает её так, чтобы указатель оставался действительным — в стандартной реализации такой объект обычно уходит в кучу.

Это принципиально отличается от возврата адреса автоматической локальной переменной в C или C++, где после завершения функции мог бы остаться висячий указатель.

Важно говорить именно о времени жизни, а не запоминать правило «возвращаемая переменная всегда в куче». Конкретный результат escape analysis является деталью компилятора и может измениться после оптимизации или между версиями Go.

### Когда передавать указатель

Указатель обычно оправдан, если:

- функция должна изменить исходную переменную;
- копирование большого значения действительно существенно;
- несколько объектов должны разделять изменяемое состояние;
- `nil` имеет отдельный осмысленный смысл;
- API или внутреннее устройство типа требует стабильной идентичности объекта.

Значение обычно предпочтительнее, если оно небольшое, логически независимо и функция не должна менять состояние вызывающей стороны. Передача значения уменьшает количество aliasing и часто упрощает конкурентное использование.

Не следует выбирать указатель только потому, что он «быстрее». Маленькое значение может передаваться эффективнее указателя, а лишние указатели увеличивают количество работы при сканировании памяти GC.

## §2.9. Время жизни, стек и куча

### Область видимости и время жизни — разные понятия

Область видимости отвечает на вопрос, в какой части исходного кода доступно имя. Время жизни отвечает на вопрос, как долго должно существовать само значение.

```go
func createNumber() *int {
	value := 42
	return &value
}
```

Имя `value` недоступно за пределами функции. Но переменная, которую оно обозначало, продолжает жить, потому что вызывающая сторона получила указатель.

И обратная ситуация возможна: имя ещё находится в области видимости, но компилятор доказал, что значение больше не будет использоваться. Для целей GC объект может перестать считаться живым раньше закрывающей фигурной скобки. Если код взаимодействует с низкоуровневым внешним ресурсом, это различие иногда требует `runtime.KeepAlive`.

### Стек горутины

Каждая горутина имеет собственный стек вызовов. При входе в функцию среда выполнения и скомпилированный код организуют место для параметров, результатов и части локальных данных. После возврата это место можно быстро использовать повторно.

Стеки горутин начинаются небольшими и растут по необходимости. При росте стек может быть перемещён, а обычные Go-указатели на находящиеся в нём значения корректируются средой выполнения. Поэтому адрес переменной следует воспринимать как значение указательного типа, а не как обещание неизменного числового адреса для низкоуровневых трюков.

Стековое размещение обычно дешёвое:

- освобождение связано с возвратом из функции;
- отдельная работа tracing GC для такого объекта обычно не нужна;
- данные часто хорошо локализованы.

Но исходный код не управляет стеком напрямую, и спецификация языка не обещает конкретное место хранения переменной.

### Куча

Куча используется для объектов, время жизни которых компилятор не может связать с одним стековым кадром, а также для некоторых других размещений, выбранных реализацией.

Объект в куче существует, пока остаётся достижимым. Когда GC определяет, что до него больше нельзя добраться, память может быть повторно использована.

Куча не является «плохой памятью». Без неё было бы неудобно возвращать указатели, строить динамические структуры данных и передавать значения между горутинами. Проблемой становится лишняя скорость выделений или слишком большой объём живых объектов, если измерения показывают заметную стоимость GC.

### Escape analysis

Компилятор выполняет escape analysis — анализ того, может ли ссылка на значение пережить контекст, в котором оно создано.

```go
func localCalculation() int {
	value := 40
	return value + 2
}
```

`value` не требуется после возврата; компилятор обычно может держать её в стеке или вообще только в регистре.

```go
func createNumber() *int {
	value := 42
	return &value
}
```

Адрес `value` возвращается наружу, поэтому память должна пережить вызов. В обычной реализации `value` уходит в кучу.

Но само получение адреса не гарантирует escape:

```go
func incrementLocal() int {
	value := 10
	pointer := &value
	*pointer++
	return value
}
```

Указатель не покидает функцию. Компилятор может оставить `value` в стеке или полностью упростить вычисление.

Escape может быть транзитивным. Если ссылка записывается в объект, который уже должен жить в куче, связанное значение тоже может потребовать более долгого времени жизни.

Решение зависит от всего контекста и алгоритма конкретной версии компилятора. Нельзя составить надёжную таблицу вида «`new` — куча, `var` — стек» или «любой указатель — куча».

### Просмотр решений компилятора

Стандартный компилятор может вывести сведения об escape analysis:

```text
go build -gcflags=-m=3 ./...
```

В выводе встречаются сообщения вроде `moved to heap` и объяснения потока ссылок. Меньший уровень подробности можно получить через `-gcflags=-m`.

Этот вывод предназначен для диагностики и может меняться между версиями. Его следует читать после того, как профиль или бенчмарк показал проблему, а не использовать как цель саму по себе.

Встраивание функции влияет на результат анализа: после inlining компилятор может увидеть больше контекста и избежать выделения, которое казалось необходимым при изолированном рассмотрении функции.

### Выделение памяти не равно объявлению переменной

Слово allocation в профилях обычно означает выделение объекта в куче. Локальная переменная в исходном коде не обязательно создаёт heap allocation, и наоборот, одна строка может скрыто создать несколько объектов.

Например, форматирование, преобразование значений в интерфейс, рост среза, конкатенация строк или создание замыкания иногда приводят к выделениям. Но конкретный результат зависит от типов, размеров, escape analysis и оптимизаций.

Поэтому количество строк с `new` ничего не говорит о фактическом числе heap allocations.

## §2.10. Автоматическое управление памятью

Этот раздел опирается на официальное руководство [A Guide to the Go Garbage Collector](https://tip.golang.org/doc/gc-guide). Руководство описывает стандартный toolchain Go и является живым документом: детали реализации могут меняться.

### Что гарантирует язык

Go берёт на себя управление хранилищем значений. Программист не вызывает аналог `free` для обычных Go-объектов и не должен рассчитывать момент их уничтожения.

Спецификация языка не требует от каждой возможной реализации использовать именно тот tracing GC, который применяет стандартный toolchain. Теоретически реализация может организовать память иначе, сохранив семантику языка.

Поэтому нужно разделять:

- гарантию языка: значение существует, пока оно необходимо корректной программе;
- деталь стандартной реализации: недостижимые heap-объекты обнаруживает tracing garbage collector;
- оптимизационную деталь: конкретная переменная оказалась в стеке, куче или регистре.

### Объекты, указатели и граф

В терминологии GC объект — динамически выделенный участок памяти, содержащий одно или несколько Go-значений.

Указателем для целей трассировки является не только явное значение `*T`. Внутреннее представление строк, срезов, отображений, каналов, интерфейсов и функций тоже может содержать адреса, которые GC должен учитывать.

Объекты и ссылки между ними образуют граф. Сборщик начинает обход с корней — значений, которые программа определённо может использовать. К корням относятся, например:

- указатели в активных стеках горутин;
- указатели в глобальных переменных;
- некоторые данные среды выполнения.

Если до объекта можно дойти от корня, переходя по ссылкам, объект достижим и считается живым. Если такого пути нет, память объекта можно освободить для повторного использования.

### Циклические ссылки не являются утечкой сами по себе

Tracing GC не использует простой счётчик ссылок. Поэтому недостижимый цикл может быть собран:

```go
type Node struct {
	next *Node
}

func createCycle() {
	first := &Node{}
	second := &Node{}

	first.next = second
	second.next = first
}
```

После возврата из `createCycle`, если никакой внешний указатель не сохранён, оба объекта недостижимы от корней. То, что они указывают друг на друга, не сохраняет цикл навсегда.

Исключения возникают у некоторых низкоуровневых механизмов вроде finalizers, правила которых сложнее обычной достижимости.

### Mark and sweep

Стандартный GC Go использует tracing mark-and-sweep:

1. Начиная от корней, GC сканирует ссылки.
2. Найденные объекты помечаются живыми.
3. Из них сканируются ссылки на следующие объекты.
4. После завершения маркировки непомеченная память становится доступной для новых выделений.

Последний этап называется sweeping. Нельзя считать объект мусором до завершения необходимой трассировки: ещё не просмотренная ссылка может привести к нему.

Текущий GC является non-moving: он не уплотняет обычную Go-кучу переносом живых объектов в другое место. Но код всё равно не должен строить переносимость на числовых адресах: спецификация не закрепляет устройство конкретного GC, а стеки горутин могут перемещаться.

### Конкурентная работа и короткие паузы

Большая часть маркировки выполняется конкурентно с кодом приложения. Это уменьшает длительность глобальных пауз, важную для серверов и других latency-sensitive программ.

Полностью без stop-the-world-фаз GC не работает. Короткие глобальные остановки нужны, например, при переходах фаз и сканировании корней. Изменения указателей во время конкурентной маркировки отслеживаются write barrier, чтобы GC не пропустил новую связь между объектами.

Конкурентный GC всё равно потребляет CPU и может влиять на приложение:

- фоновые GC workers выполняют маркировку;
- быстро выделяющие горутины могут помогать GC через mark assists;
- write barrier добавляет работу операциям с указателями;
- остановка и возобновление множества горутин имеет цену.

Маленькие паузы не означают нулевую стоимость. Нужно различать latency отдельной операции и общий throughput программы.

### Память может не вернуться ОС сразу

После sweep память становится свободной прежде всего для следующих выделений самой Go-программы. Это не означает, что показатель RSS процесса немедленно уменьшится на тот же объём.

Среда выполнения повторно использует страницы и в фоне возвращает операционной системе физическую память, которая ей больше не нужна. При этом зарезервированное виртуальное адресное пространство может остаться большим.

Поэтому:

- большой VSS сам по себе не доказывает фактическое потребление RAM;
- RSS ближе к физической памяти процесса, но тоже включает не только живые Go-объекты;
- heap profile и `runtime/metrics` отвечают на другие вопросы, чем системный монитор.

Нужно выбирать метрику в зависимости от того, исследуется ли живой heap, совокупные allocations, память runtime или физическая память процесса.

### GC не освобождает немемориальные ресурсы вовремя

Файл, сетевое соединение, блокировка, транзакция и дескриптор ОС — не обычная память Go. Даже если оболочка такого ресурса стала недостижимой, нельзя ждать неопределённого момента GC.

Ресурсы освобождают детерминированно:

```go
file, err := os.Open("data.txt")
if err != nil {
	return err
}
defer file.Close()
```

GC управляет памятью, но не заменяет `Close`, `Unlock`, `Commit`, `Rollback` и другие операции протокола.

## §2.11. Достижимость, утечки и `KeepAlive`

### GC не делает утечки невозможными

Если объект больше не нужен по логике программы, но остаётся достижимым, GC не имеет права его освободить. Он не знает намерения разработчика.

Типичные причины логической утечки:

- бесконечно растущий глобальный кэш;
- забытые элементы в отображении;
- срез, удерживающий большой backing array ради маленькой части;
- горутина, навсегда заблокированная вместе со своими ссылками;
- callback или замыкание, сохраняющее большой объект;
- таймер, подписка или очередь, которые не были остановлены;
- сохранение ссылки в долгоживущем объекте.

С точки зрения GC такие объекты живы. Увеличение частоты сборки не поможет: после каждого цикла они снова будут найдены от корней.

### Обнуление ссылок

Иногда в долгоживущей структуре полезно убрать ссылку на больше не нужный объект:

```go
items[index] = nil
```

Это имеет смысл, если сам контейнер продолжает жить и иначе удерживал бы объект. Обнулять каждую локальную переменную перед выходом из короткой функции обычно бессмысленно: компилятор и так отслеживает живость, а дополнительный код ухудшает читаемость.

Обрезка среза тоже не обязательно освобождает ссылки в отброшенной части backing array. Если этот массив остаётся достижимым и содержит указатели, явная очистка удаляемых элементов иногда нужна. Подробные правила будут рассмотрены в главе о срезах.

### Объект может стать недостижимым до конца блока

GC интересует последнее возможное использование значения, а не только текстовая область видимости имени. Рассмотрим оболочку над внешним ресурсом:

```go
type File struct {
	fd uintptr
}

func use(file *File) {
	syscall.Write(int(file.fd), data)
}
```

Если после извлечения `fd` Go-объект `file` больше не используется, компилятор может считать его мёртвым до закрывающей скобки. Cleanup или finalizer теоретически способен освободить внешний ресурс слишком рано.

`runtime.KeepAlive` сообщает, что объект должен считаться достижимым до указанной точки:

```go
func use(file *File) {
	syscall.Write(int(file.fd), data)
	runtime.KeepAlive(file)
}
```

`KeepAlive` не продлевает жизнь после своего вызова и не закрепляет числовой адрес навсегда. Его применяют в низкоуровневом коде при взаимодействии с finalizers, cleanups, системными вызовами, `unsafe` или C. В обычном прикладном коде он почти не нужен.

### Принудительный запуск GC

`runtime.GC()` запускает сборку мусора и ждёт завершения текущего GC-цикла. Это полезно в специальных тестах и диагностике, но обычно не должно находиться в рабочем пути приложения.

Принудительный GC:

- потребляет CPU;
- нарушает автоматический pacing;
- не освобождает достижимые объекты;
- не гарантирует немедленного выполнения cleanups и finalizers — они могут быть только поставлены в очередь.

`debug.FreeOSMemory()` пытается выполнить GC и вернуть больше свободной памяти операционной системе. Это ещё более специальный инструмент, а не стандартная операция после каждого запроса.

## §2.12. Стоимость GC и параметр `GOGC`

### Что определяет стоимость

Для практической оценки полезно различать:

- **live heap** — объём объектов, признанных живыми в конце предыдущего цикла;
- **new heap** — память, выделенная после предыдущего цикла;
- **allocation rate** — скорость создания новых heap-объектов;
- **roots** — сканируемые корни, включая указатели в стеках и глобальных данных;
- **структуру графа** — количество указателей, глубину и связность объектов.

Пиковый объём памяти около цикла упрощённо состоит из живой памяти прошлого цикла и новых выделений. Основная CPU-стоимость маркировки примерно растёт с объёмом живых данных и сложностью содержащихся в них ссылок.

Большая скорость выделений приводит к более частым циклам. Большой живой heap делает каждый цикл дороже. Структура с множеством указателей требует больше сканирования, чем такой же объём данных без указателей.

Из этого следует важное различие:

- временные объекты повышают allocation rate и частоту GC;
- долгоживущие объекты увеличивают live heap и работу каждого цикла;
- лишние указатели усложняют граф даже при том же количестве байт.

### Компромисс памяти и CPU

Если запускать GC чаще, программа обычно удерживает меньше лишней памяти, но тратит больше CPU на сборки. Если запускать реже, сборок меньше, но heap успевает вырасти сильнее.

Не существует настройки, которая одновременно всегда минимизирует и память, и CPU. Выбор зависит от ограничений сервиса: доступной RAM, требуемой latency, пропускной способности и характера нагрузки.

### Параметр `GOGC`

`GOGC` задаёт относительную цель роста heap между циклами. Значение по умолчанию — `100`.

Упрощённая формула текущего pacer:

```text
target heap = live heap + (live heap + GC roots) × GOGC / 100
```

Например, после цикла осталось 8 MiB живого heap, а сканируемые корни занимают 2 MiB. При `GOGC=100` цель будет примерно такой:

```text
8 MiB + (8 MiB + 2 MiB) × 100 / 100 = 18 MiB
```

Это означает около 10 MiB новых heap allocations до целевой точки следующего цикла. Цель не является жёстким максимумом: большая единичная аллокация, скорость работы программы и другие детали могут привести к превышению.

Настройка через окружение:

```text
GOGC=200 ./service
```

При прочих равных увеличение `GOGC`:

- реже запускает GC;
- уменьшает долю CPU, занятую сборкой;
- увеличивает допустимый объём памяти между циклами.

Уменьшение `GOGC` делает обратное. Изменить параметр во время выполнения можно через `debug.SetGCPercent`.

```go
previous := debug.SetGCPercent(200)
_ = previous
```

Функция возвращает прошлое значение. Глобальная настройка затрагивает весь процесс, поэтому библиотека обычно не должна самовольно менять её за приложение.

`GOGC=off` или `debug.SetGCPercent(-1)` отключает сборки, основанные на процентной цели. Если установлен memory limit, runtime всё равно может запускать GC ради соблюдения лимита.

Отключение GC безопасно лишь в специальных ограниченных сценариях, например для короткого процесса с заранее известным объёмом памяти. В долгоживущем сервисе heap иначе может расти без ограничения.

### Почему увеличение `GOGC` иногда ускоряет программу

Если приложение имеет запас памяти и действительно тратит заметный CPU на GC, более высокий `GOGC` может уменьшить число циклов. Но выигрыш не гарантирован:

- приложение может упереться в память;
- больший heap влияет на кэши CPU и системные метрики;
- latency зависит не только от частоты GC;
- GC мог вообще не быть существенной частью нагрузки.

Настройку меняют после профилирования и проверяют на нагрузке, похожей на рабочую.

## §2.13. Мягкий лимит памяти `GOMEMLIMIT`

`GOMEMLIMIT` задаёт мягкий предел памяти, которой управляет runtime Go:

```text
GOMEMLIMIT=900MiB ./service
```

Во время выполнения то же значение можно изменить через `debug.SetMemoryLimit`:

```go
previous := debug.SetMemoryLimit(900 << 20)
_ = previous
```

Лимит учитывает Go heap и другие классы памяти runtime. В терминах `runtime.MemStats` его область приблизительно соответствует:

```text
Sys - HeapReleased
```

Это не абсолютный предел RSS всего процесса. В него не входят некоторые внешние источники:

- память, выделенная C-кодом через `cgo`;
- отображение исполняемого файла и библиотек;
- память, которую ОС держит от имени процесса;
- некоторые другие ресурсы вне контроля Go runtime.

Если контейнеру доступен 1 GiB, устанавливать `GOMEMLIMIT=1GiB` обычно слишком тесно. Официальное руководство рекомендует оставлять примерно 5–10% запаса для памяти, которую runtime не учитывает, а реальный запас выбирают по измерениям конкретного приложения.

### Лимит является мягким

Runtime прилагает разумные усилия, чтобы остаться около предела, но не гарантирует его соблюдение при любых условиях. Живые объекты нельзя удалить только ради лимита.

Если live memory приблизилась к слишком низкому пределу, частые GC уже не освобождают достаточно памяти. Возникает thrashing: программа тратит огромную долю времени на повторные сборки и почти не продвигает полезную работу.

Чтобы неправильная настройка не остановила программу полностью, runtime ограничивает долю CPU, которую GC может забирать на длительном окне, и допускает превышение мягкого предела. Поэтому `GOMEMLIMIT` не заменяет системный лимит контейнера и не гарантирует отсутствие OOM.

### Совместная работа с `GOGC`

`GOGC` задаёт нормальный компромисс CPU и памяти относительно live heap. `GOMEMLIMIT` ограничивает рост при пиках или в окружении с известным бюджетом.

Обычно разумная модель такова:

- `GOGC` управляет поведением при обычной нагрузке;
- `GOMEMLIMIT` служит ограничителем при росте памяти;
- системный или контейнерный лимит остаётся последней жёсткой границей.

Даже при `GOGC=off` runtime соблюдает мягкий memory limit. Такая конфигурация минимизирует частоту GC до необходимой для удержания около лимита, но становится опасной, если Go-процесс делит память с непредсказуемыми соседями или сам лимит выбран слишком низко.

Не следует «лечить» постоянное превышение памяти только уменьшением лимита. Если live heap слишком велик, нужно найти удерживаемые объекты, уменьшить нагрузку, изменить структуру данных или увеличить доступный бюджет.

## §2.14. Cleanups, finalizers и weak pointers

Обычный код не должен наблюдать точный момент смерти объекта. Но runtime предоставляет низкоуровневые механизмы для редких задач, связанных с внешней памятью, кэшами и ресурсами:

- `runtime.AddCleanup`;
- `runtime.SetFinalizer`;
- `weak.Pointer`.

У этих механизмов сложные ограничения. Их следует инкапсулировать внутри пакета и покрывать тестами, а не делать частью обычной бизнес-логики.

### Нет гарантии своевременного выполнения

Cleanup или finalizer может выполниться значительно позже потери последней ссылки. Нет гарантии, что он выполнится перед завершением программы или вообще успеет выполниться.

Поэтому основной путь освобождения файла или соединения должен быть явным:

```go
resource, err := openResource()
if err != nil {
	return err
}
defer resource.Close()
```

Cleanup можно использовать как страховку от ошибки разработчика, но не как единственный механизм соблюдения системного лимита дескрипторов.

### `runtime.AddCleanup`

Cleanup связывает объект с функцией, которую runtime может вызвать после того, как объект станет недостижимым. В callback лучше передавать только необходимые данные внешнего ресурса:

```go
type Resource struct {
	handle uintptr
}

resource := &Resource{handle: handle}
runtime.AddCleanup(resource, func(handle uintptr) {
	release(handle)
}, handle)
```

Функция cleanup не должна захватывать сам `resource`, а её аргумент не должен делать `resource` достижимым. Иначе образуется путь, который не позволит объекту умереть, и cleanup не запустится.

Порядок cleanups не определён; они могут выполняться конкурентно. Долгая cleanup-функция не должна блокировать выполнение остальных.

`runtime.GC()` ждёт постановки подходящих cleanups в очередь, но не ждёт завершения их функций.

### `runtime.SetFinalizer`

Finalizer получает сам умирающий объект. Ради вызова объект фактически становится снова доступным, поэтому его память нельзя сразу использовать повторно. Объект можно даже случайно воскресить, сохранив указатель из finalizer.

Это делает finalizers более дорогими и подверженными ошибкам. Цикл объектов с finalizer может не быть собран, поскольку невозможно определить подходящий порядок зависимостей. Цепочка finalizers может потребовать нескольких GC-циклов.

Для нового кода Go 1.24+ официальное руководство рекомендует предпочитать `AddCleanup`, если не требуется редкая семантика упорядочения finalizers.

### Weak pointer

Слабый указатель позволяет сослаться на объект, не сохраняя его живым только из-за этой ссылки. После сборки объекта получение значения вернёт `nil`.

Такой механизм полезен в специализированных кэшах и таблицах канонических объектов, но требует проверки результата при каждом использовании. Объект может исчезнуть в момент, который обычному коду кажется неожиданным.

Слабый указатель не является способом обойти модель владения памятью. Если значение отображения само содержит сильную ссылку на объект, слабый ключ не сделает объект недостижимым.

### Тестирование смерти объекта

Тесты cleanups и finalizers сложны из-за недетерминированного времени:

- их не стоит запускать параллельно без необходимости;
- `runtime.GC()` помогает поставить callback в очередь, но не ждёт выполнения;
- тесту нужен канал или другой явный сигнал о завершении callback;
- код следует запускать с `-race`, поскольку cleanups могут быть конкурентными;
- `time.Sleep` не доказывает, что callback обязан был завершиться.

В обычном тесте лучше проверять детерминированный `Close`, а не надеяться на GC.

## §2.15. Поиск и уменьшение затрат памяти

### Сначала доказать наличие проблемы

Оптимизация начинается не с переписывания всех значений на указатели и не с ручного вызова GC. Сначала нужно выяснить:

- сколько памяти реально используется;
- какие объекты остаются живыми;
- где происходят allocations;
- сколько CPU тратит GC;
- важна ли проблема для latency или throughput.

### Бенчмарки

Команда

```text
go test -bench=. -benchmem
```

показывает время, число выделенных байт и количество heap allocations на операцию для бенчмарков. Сравнивать варианты нужно на стабильной нагрузке и по нескольким запускам.

Ноль allocations не является самостоятельной целью. Иногда одна понятная аллокация дешевле сложного пула, копирования большого буфера или удержания лишней памяти.

### Heap profile

Профиль памяти позволяет смотреть на heap с разных сторон:

- `inuse_objects` — количество живых объектов;
- `inuse_space` — объём живых объектов;
- `alloc_objects` — суммарное число созданных объектов;
- `alloc_space` — суммарный объём allocations за время работы.

Для снижения стоимости GC часто полезен `alloc_space`, потому что он показывает места с высокой скоростью выделений. Для поиска удерживаемой памяти важнее `inuse_space` и `inuse_objects`.

Профиль обычно использует выборку и не обязан содержать каждую отдельную аллокацию. Этого достаточно для поиска крупных горячих мест, но маленькие результаты нужно интерпретировать осторожно.

### CPU profile и trace

CPU profile показывает, сколько процессорного времени уходит на приложение и runtime. Заметные `runtime.gcBgMarkWorker`, `runtime.gcDrain...`, `runtime.mallocgc` и `runtime.gcAssistAlloc` могут указывать на существенную стоимость allocations и маркировки.

Execution trace помогает исследовать короткие интервалы, паузы, работу GC, планировщика и конкретных горутин. Он особенно полезен для latency-проблем, которые теряются в агрегированном CPU profile.

Подробный текстовый GC trace включается переменной окружения:

```text
GODEBUG=gctrace=1 ./service
```

Он печатает строку на каждый цикл в `stderr`. Формат и внутренние показатели зависят от версии runtime, поэтому этот инструмент используют для диагностики, а не как стабильный машинный API.

Для программного мониторинга предпочтительнее `runtime/metrics`: пакет предоставляет документированные метрики heap, GC cycles, pauses, allocations и настроек runtime.

### Escape analysis после профиля

Если профиль показал горячую точку allocations, можно запустить:

```text
go build -gcflags=-m=3 ./path/to/package
```

После этого исследуют, почему конкретное значение уходит в heap. Возможные изменения:

- не сохранять указатель дольше необходимого;
- не захватывать крупное значение замыканием;
- позволить компилятору встроить небольшую функцию;
- передавать буфер вызывающей стороной;
- уменьшить преобразования через интерфейсы;
- повторно использовать подходящую память.

Каждое изменение нужно снова измерить. Перестановка кода ради текущей версии escape analysis может ухудшить читаемость и перестать работать после обновления компилятора.

### Уменьшение графа указателей

GC должен просматривать указатели в живых объектах. Структура без указателей может сканироваться дешевле, чем сложный граф того же размера.

Иногда индексы вместо связей-указателей, плотное хранение значений или группировка указательных полей уменьшают работу GC и улучшают локальность. Но это implementation-specific оптимизации. Они оправданы только после профилирования: более запутанная структура данных может стоить дороже выигранных процентов.

### Повторное использование памяти

Повторное использование буфера способно снизить allocation rate. Но долгоживущий пул одновременно удерживает память и увеличивает live heap.

`sync.Pool` предназначен для временных объектов, которые можно безопасно удалить в любой момент. Runtime имеет право очистить pool во время GC, поэтому его нельзя использовать как обычный кэш или место хранения обязательных данных.

Для каждого пула нужно сравнить:

- стоимость создания объекта;
- частоту повторного использования;
- объём удерживаемой памяти;
- конкуренцию между горутинами;
- усложнение кода.

### Практический порядок работы

1. Зафиксировать рабочую нагрузку и метрику проблемы.
2. Снять CPU, heap profile или trace.
3. Отличить высокий allocation rate от большого live heap.
4. Найти конкретные места, а не оптимизировать весь код.
5. Проверить escape analysis только для найденных мест.
6. Внести минимальное понятное изменение.
7. Повторить измерения и проверить корректность.
8. Только затем подбирать `GOGC` и `GOMEMLIMIT` под среду выполнения.

GC Go спроектирован так, чтобы обычная программа работала без ручного управления каждым объектом. Лучшее управление памятью обычно начинается с простых времён жизни, ограниченных ссылок и измерений, а не с вмешательства в runtime.
