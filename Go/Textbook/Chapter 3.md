# III. Коллекции и обработка ошибок

Материал главы соответствует Go 1.27. Сначала рассматриваются последовательности и ассоциативные коллекции: строки, руны, массивы, срезы и карты. Затем разбирается модель ошибок Go: значения типа `error`, оборачивание, проверка цепочек, объединение ошибок, `panic` и `recover`.

## §3.1. Строка как последовательность байтов

Тип `string` представляет неизменяемую последовательность байтов. Это определение важнее привычной фразы «строка — это текст»: строка может содержать корректный UTF-8, повреждённый UTF-8 или вообще произвольные байты.

```go
text := "Go"
empty := ""
binary := "\xff\x00\x7f"
```

Нулевое значение `string` — пустая строка `""`.

Строка неизменяема: после создания нельзя заменить отдельный байт.

```go
s := "cat"
// s[0] = 'b' // ошибка компиляции
```

Переменной можно присвоить другую строку, но это заменит значение переменной, а не изменит прежнюю строку:

```go
s := "cat"
s = "bat"
```

### `len` считает байты

Встроенная функция `len` возвращает длину строки в байтах, а не число видимых символов и не число Unicode code points:

```go
fmt.Println(len("Go"))    // 2
fmt.Println(len("Привет")) // 12
fmt.Println(len("🙂"))     // 4
```

UTF-8 кодирует разные code points разным количеством байтов. Поэтому для произвольного текста неверно считать, что `len(s)` равно числу букв.

### Индексация возвращает байт

Выражение `s[i]` имеет тип `byte`, то есть псевдоним `uint8`:

```go
s := "Go"
fmt.Printf("%c %d %T\n", s[0], s[0], s[0])
```

> Вывод: `G 71 uint8`.

Индекс должен удовлетворять условию `0 <= i < len(s)`. Нарушение границ во время выполнения вызывает panic.

Для многобайтового символа индекс возвращает лишь один байт UTF-8:

```go
s := "я"
fmt.Println(len(s))         // 2
fmt.Printf("%x\n", s[0])   // d1
fmt.Printf("%x\n", s[1])   // 8f
```

### `byte` и `rune`

Имена `byte` и `rune` — предопределённые псевдонимы:

```go
type byte = uint8
type rune = int32
```

`byte` удобно подчёркивает работу с сырыми байтами, а `rune` — работу с Unicode code points. Псевдоним не создаёт новый отдельный тип.

### Строковые литералы

Интерпретируемый литерал записывается в двойных кавычках. В нём работают escape-последовательности:

```go
path := "C:\\temp\\file.txt"
line := "first\nsecond"
quote := "\"Go\""
```

Raw string literal записывается между обратными кавычками. Escape-последовательности в нём не обрабатываются, а переводы строк сохраняются:

```go
query := `SELECT *
FROM users
WHERE name = 'Ann'`
```

В raw-литерал нельзя непосредственно включить обратную кавычку. Возвраты каретки `\r` внутри raw-литерала удаляются из его значения.

### Сравнение строк

Строки сравнимы. `==` и `!=` проверяют равенство байтов, а `<`, `<=`, `>` и `>=` задают лексикографический порядок по байтам:

```go
fmt.Println("go" == "go") // true
fmt.Println("Go" < "go")  // true
```

Это не языковая сортировка с учётом регистра, локали, нормализации Unicode или человеческого алфавита.

### Конкатенация

Оператор `+` создаёт строку из содержимого двух строк:

```go
full := "Hello, " + "Go"
```

Многократное наращивание строки в цикле может создавать много промежуточных значений. Для сборки большого текста обычно применяют `strings.Builder`:

```go
var b strings.Builder
for i := 0; i < 3; i++ {
	b.WriteString("go")
}
result := b.String()
```

Копировать ненулевой `strings.Builder` нельзя: его методы рассчитывают на то, что объект после начала использования не копируют.

## §3.2. Unicode и руны

Unicode code point — числовое значение, назначенное символу стандартом Unicode. В Go его обычно представляют типом `rune`.

Rune literal записывается в одинарных кавычках:

```go
latin := 'A'
cyrillic := 'Я'
emoji := '🙂'

fmt.Printf("%T %U\n", cyrillic, cyrillic)
```

> Тип литерала после получения значения по умолчанию — `rune`, то есть `int32`.

Литерал руны должен обозначать ровно один code point, escape-последовательность либо один байт через подходящий escape. Строковый литерал может содержать сколько угодно code points.

### Code point не всегда равен видимому символу

Одна видимая пользователю графема может состоять из нескольких рун. Например, буква и комбинируемый знак ударения являются двумя code points; некоторые emoji состоят из нескольких emoji, модификаторов и соединителя.

Следовательно, существуют три разные величины:

- число байтов UTF-8;
- число рун, то есть Unicode code points;
- число воспринимаемых пользователем символов — grapheme clusters.

Стандартные `len` и `utf8.RuneCountInString` отвечают только на первые два вопроса.

### Перебор строки через `range`

`range` декодирует UTF-8 и выдаёт индекс начала руны в байтах и саму руну:

```go
s := "Aя🙂"

for index, r := range s {
	fmt.Printf("index=%d rune=%c code=%U\n", index, r, r)
}
```

> Индексы будут `0`, `1` и `3`, а не `0`, `1` и `2`.

Если нужен только индекс:

```go
for index := range s {
	fmt.Println(index)
}
```

Если нужны только руны:

```go
for _, r := range s {
	fmt.Println(r)
}
```

При некорректной UTF-8 последовательности `range` выдаёт `unicode.ReplacementChar`, то есть `U+FFFD`, и продвигается на один байт. Пакет `unicode/utf8` предоставляет `ValidString`, `DecodeRuneInString`, `RuneCountInString` и другие операции для явной работы с кодировкой.

### Преобразования строки

Преобразование в `[]byte` даёт байты UTF-8, а в `[]rune` — декодированные code points:

```go
s := "Aя"
bytes := []byte(s) // [65 209 143]
runes := []rune(s) // [65 1103]
```

Обратные преобразования:

```go
s1 := string([]byte{0x47, 0x6f})
s2 := string([]rune{'G', 'o'})
```

Обычная семантика преобразования между строкой и срезом предполагает отдельное изменяемое представление среза: изменение `[]byte` не должно менять исходную строку. Компилятор может устранять фактическое копирование, если способен сохранить наблюдаемое поведение программы.

Преобразование отдельного целого в `string` трактует число как code point, а не как десятичную запись:

```go
fmt.Println(string(65))          // A
fmt.Println(strconv.Itoa(65))    // 65
fmt.Println(fmt.Sprint(65))      // 65
```

Недопустимое значение code point при таком преобразовании заменяется на `U+FFFD`.

### Срез строки работает по байтам

```go
s := "Привет"
first := s[:2]
fmt.Println(first) // П
```

Границы являются байтовыми. Компилятор не проверяет, совпадают ли они с границами UTF-8:

```go
broken := s[:1]
fmt.Println(utf8.ValidString(broken)) // false
```

Для извлечения по code points строку можно преобразовать в `[]rune`, но для пользовательских «символов» даже этого недостаточно из-за grapheme clusters.

Подстрока может разделять с исходной строкой одно хранилище. Небольшая подстрока поэтому способна удерживать в памяти большую исходную строку; точное решение компилятора является деталью реализации. Если это подтверждённая профилем проблема, отдельную строку можно создать через `strings.Clone`.

## §3.3. Массивы

Массив — последовательность фиксированной длины. Длина является частью типа:

```go
var first [3]int
var second [4]int
```

`[3]int` и `[4]int` — разные типы. Между ними нельзя выполнить обычное присваивание.

Нулевое значение массива состоит из нулевых значений элементов:

```go
var values [3]int
fmt.Println(values) // [0 0 0]
```

### Литералы массивов

```go
names := [3]string{"Ann", "Bob", "Cid"}
auto := [...]int{10, 20, 30}
sparse := [5]int{1: 10, 4: 40}
```

`[...]` просит компилятор вывести длину из литерала. Это по-прежнему массив, не срез.

В индексированных литералах можно смешивать явные индексы и последующие значения; следующий неявный индекс равен предыдущему явному индексу плюс один. Повторять один индекс нельзя.

### `len`, `cap` и индексация

Для массива длины `N` всегда выполняется:

```go
len(array) == N
cap(array) == N
```

Элемент `array[i]` можно читать и изменять, если массив адресуем:

```go
values := [3]int{10, 20, 30}
values[1] = 99
```

### Присваивание копирует массив

```go
first := [3]int{1, 2, 3}
second := first
second[0] = 100

fmt.Println(first)  // [1 2 3]
fmt.Println(second) // [100 2 3]
```

Передача массива функции также передаёт значение массива. Чтобы функция работала с исходным массивом, можно передать `*[N]T`, однако для большинства последовательностей удобнее срез.

### Сравнение массивов

Массив сравним, если сравним тип его элементов:

```go
fmt.Println([2]int{1, 2} == [2]int{1, 2}) // true
```

Массив с элементами-срезами несравним, поскольку срезы несравнимы. Сравнимый массив может быть ключом `map`.

### Перебор массива

```go
values := [3]int{10, 20, 30}
for i, value := range values {
	fmt.Println(i, value)
}
```

Переменная `value` получает копию элемента. Изменение её самой не меняет массив:

```go
for _, value := range values {
	value++ // меняется только локальная копия
}
```

При `range` по значению массива выражение массива вычисляется и копируется перед циклом, за исключением специального случая, когда используется не более одного iteration variable и выражение `len`-постоянно: тогда выражение может вообще не вычисляться. Если важно менять исходный массив, перебирают индексы либо указатель на массив.

## §3.4. Срезы: представление, длина и ёмкость

Срез `[]T` — не массив и не владелец фиксированного числа элементов. Концептуально значение среза содержит три части:

```text
указатель на часть underlying array + длина + ёмкость
```

Это модель поведения, а не обещание о доступной программе структуре полей.

- `len(s)` — число элементов, к которым сейчас разрешён доступ через индексы `0..len(s)-1`;
- `cap(s)` — максимальная длина, до которой этот срез можно расширить вправо без смены underlying array;
- underlying array — массив, в котором фактически лежат элементы.

### Нулевой срез

```go
var s []int
fmt.Println(s == nil) // true
fmt.Println(len(s))   // 0
fmt.Println(cap(s))   // 0
```

Нулевой срез пригоден для чтения длины, `range`, `append`, `copy` и `clear`. Индексация невозможна, потому что длина равна нулю.

### Литерал и `make`

```go
literal := []int{10, 20, 30}
withLength := make([]int, 3)
withCapacity := make([]int, 3, 8)
```

У `withLength` длина и ёмкость равны 3. У `withCapacity` длина 3, ёмкость 8; доступными являются только индексы `0`, `1`, `2`. Остальная ёмкость ещё не входит в длину.

```go
// withCapacity[3] = 10 // panic: индекс вне длины
withCapacity = append(withCapacity, 10)
```

Для `make([]T, length, capacity)` должно выполняться `0 <= length <= capacity`. Если третий аргумент отсутствует, capacity равна length.

Пустой, но ненулевой срез можно создать несколькими способами:

```go
a := []int{}
b := make([]int, 0)
c := make([]int, 0, 16)
```

У всех длина 0, но только конкретное устройство хранения и `nil`-состояние различаются.

## §3.5. Обычные срезы `[low:high]`

Для среза `s` выражение:

```go
t := s[low:high]
```

создаёт новое значение-срез, которое разделяет underlying array с `s`. Формулы:

```text
len(t) = high - low
cap(t) = cap(s) - low
```

Допустимые границы для среза:

```text
0 <= low <= high <= cap(s)
```

Важная тонкость: `high` может быть больше `len(s)`, если он не больше `cap(s)`. Так выполняется повторное расширение среза.

```go
s := make([]int, 3, 6)
t := s[1:5]

fmt.Println(len(t), cap(t)) // 4 5
```

Для строки и массива обычная верхняя граница ограничена `len`, а не скрытым запасом. При срезе адресуемого массива результатом становится срез.

### Пропущенные границы

```go
s[2:] // s[2:len(s)]
s[:3] // s[0:3]
s[:]  // s[0:len(s)]
```

Пропущенный `high` равен текущей длине, не ёмкости. Чтобы расширить срез до всей ёмкости:

```go
s = s[:cap(s)]
```

### Как меняются `len` и `cap`

Пусть:

```go
s := make([]int, 5, 8)
```

Тогда:

| Выражение | `len` | `cap` | Объяснение |
|---|---:|---:|---|
| `s` | 5 | 8 | исходный срез |
| `s[:3]` | 3 | 8 | начало не сдвинуто |
| `s[2:]` | 3 | 6 | начало сдвинуто на 2 |
| `s[2:4]` | 2 | 6 | `cap` не зависит от `high` |
| `s[:cap(s)]` | 8 | 8 | расширение до ёмкости |
| `s[5:5]` | 0 | 3 | пустой срез в середине массива |
| `s[8:8]` | 0 | 0 | пустой срез в самом конце |

Операция среза не меняет `len` и `cap` исходного значения `s`: она создаёт другой descriptor. Но оба descriptor могут видеть одни элементы массива.

### Совместное underlying array

```go
base := []int{10, 20, 30, 40}
left := base[:3]
right := base[1:]

right[0] = 999
fmt.Println(base) // [10 999 30 40]
fmt.Println(left) // [10 999 30]
```

Это aliasing: разные значения дают доступ к одной памяти. Передача среза функции копирует descriptor, но не копирует элементы.

```go
func change(s []int) {
	s[0] = 100
}
```

Функция изменит доступный элемент исходного массива. Однако присваивание самой локальной переменной `s` не заменит срез вызывающей стороны.

## §3.6. Полный срез `[low:high:max]`

Полное slice expression существует для массивов, указателей на массив и срезов, но не для строк:

```go
t := s[low:high:max]
```

Формулы:

```text
len(t) = high - low
cap(t) = max - low
```

Условия:

```text
0 <= low <= high <= max <= cap(s)
```

Только `low` разрешено опустить.

Главное назначение `max` — ограничить, какую часть общего массива последующий `append` имеет право использовать:

```go
base := []int{10, 20, 30, 40}
part := base[:2:2] // len=2, cap=2
part = append(part, 99)

fmt.Println(base) // [10 20 30 40]
fmt.Println(part) // [10 20 99]
```

Так как свободной ёмкости у `part` не было, `append` выделил другой массив и не затёр `base[2]`. Без третьего индекса `base[:2]` имел бы capacity 4, и append использовал бы общий массив.

## §3.7. `append` и рост среза

`append` возвращает новый descriptor:

```go
s = append(s, 10)
s = append(s, 20, 30)
```

Результат обязательно нужно сохранить. Старый descriptor не получает новую длину автоматически:

```go
func wrong(s []int) {
	append(s, 1) // ошибка компиляции: результат не использован
}
```

Если вызывающая функция должна увидеть изменившуюся длину, новый срез обычно возвращают:

```go
func add(s []int, value int) []int {
	return append(s, value)
}

s = add(s, 42)
```

### Два сценария `append`

Если `len(s)+числоДобавляемых <= cap(s)`, элементы помещаются в существующий underlying array. Возвращённый срез разделяет его с исходным.

Если ёмкости недостаточно, runtime выделяет более крупный массив, копирует существующие элементы и добавляет новые. Возвращённый срез уже ссылается на новый массив.

```go
base := []int{1, 2, 3, 4}
a := base[:2]       // len=2, cap=4
b := append(a, 99)  // использован base[2]

fmt.Println(base) // [1 2 99 4]
fmt.Println(b)    // [1 2 99]
```

Из-за этого код не должен предполагать, сохранит ли append общий массив, если это не следует из capacity. Стабильность адресов элементов после append не гарантируется.

### Новая ёмкость не задаётся спецификацией

После роста выполняется лишь `cap(result) >= len(result)`. Конкретный коэффициент, пороги и округления являются деталями runtime и менялись между версиями. Нельзя писать алгоритм, правильность которого зависит от удвоения capacity.

Если приблизительный итоговый размер известен, запас можно дать заранее:

```go
result := make([]int, 0, expected)
```

Capacity — подсказка для размещения, а не ограничение: append всё равно может вырасти дальше.

### Добавление другого среза

```go
dst = append(dst, src...)
```

`...` раскрывает элементы `src`. Допустимы и перекрывающиеся области, включая:

```go
s = append(s, s...)
```

К строке байтов можно добавить байты строки специальной формой:

```go
buffer := []byte{'G'}
buffer = append(buffer, "opher"...)
```

## §3.8. Копирование, очистка и изменение срезов

### `copy`

```go
n := copy(destination, source)
```

Копируется `min(len(destination), len(source))` элементов, а `n` сообщает фактическое число. `copy` не увеличивает длину destination:

```go
src := []int{1, 2, 3}
dst := make([]int, 2)
n := copy(dst, src)

fmt.Println(dst, n) // [1 2] 2
```

Перекрытие разрешено, поэтому copy подходит для сдвига:

```go
s := []int{1, 2, 3, 4}
copy(s[1:], s[:3])
fmt.Println(s) // [1 1 2 3]
```

Из строки можно копировать байты непосредственно в `[]byte`:

```go
dst := make([]byte, 2)
copy(dst, "Go")
```

### Независимая копия

```go
clone := make([]int, len(source))
copy(clone, source)
```

В Go 1.21+ то же намерение выражает `slices.Clone(source)`. Для ненулевого пустого среза точное сохранение nil-формы следует проверять по контракту выбранной функции; `slices.Clone` сохраняет nil.

### `clear`

`clear(s)` устанавливает в нулевое значение все элементы `s[:len(s)]`. Длина и ёмкость не меняются:

```go
s := []int{1, 2, 3}
clear(s)
fmt.Println(s, len(s), cap(s)) // [0 0 0] 3 3
```

Элементы за пределами длины, но внутри capacity, не очищаются.

### Удаление с сохранением порядка

```go
s = append(s[:i], s[i+1:]...)
```

Если элементы содержат указатели, удалённое значение может остаться в неиспользуемом хвосте underlying array и удерживать объект для GC. Хвост очищают:

```go
copy(s[i:], s[i+1:])
clear(s[len(s)-1:])
s = s[:len(s)-1]
```

Стандартный пакет `slices` предоставляет `Delete`; современные версии очищают освобождённую область, но всегда следует ориентироваться на документацию используемой версии.

### Быстрое удаление без сохранения порядка

```go
s[i] = s[len(s)-1]
clear(s[len(s)-1:])
s = s[:len(s)-1]
```

Операция постоянного времени, но порядок элементов меняется.

### Вставка

```go
s = append(s, 0)       // увеличить длину
copy(s[i+1:], s[i:])   // сдвинуть хвост
s[i] = value
```

Для готовых общих операций есть пакет `slices`: `Insert`, `Delete`, `Replace`, `Contains`, `Index`, `Sort`, `Compact` и другие. Он не меняет фундаментальных правил aliasing и capacity.

## §3.9. `nil`, пустые срезы и сравнение

```go
var nilSlice []int
emptySlice := []int{}

fmt.Println(len(nilSlice), len(emptySlice)) // 0 0
fmt.Println(nilSlice == nil)                // true
fmt.Println(emptySlice == nil)              // false
```

Оба нормально работают с `range`, `append`, `copy` и `len`. Но внешние форматы могут различать их: например, `encoding/json` обычно кодирует nil slice как `null`, а ненулевой пустой — как `[]`.

Срезы нельзя сравнивать друг с другом оператором `==`; разрешено только сравнение с `nil`:

```go
// fmt.Println(a == b) // ошибка компиляции
fmt.Println(a == nil)
```

Для сравнения элементов применяют `slices.Equal`, а для несравнимых элементов — `slices.EqualFunc`.

### Удержание большого массива

```go
large := make([]byte, 100<<20)
small := large[:10]
large = nil
```

Пока `small` ссылается на underlying array, весь массив может оставаться достижимым. Если нужны только 10 байтов надолго:

```go
small = bytes.Clone(small)
```

Не следует копировать каждый подсрез «на всякий случай»: сначала учитывают время жизни данных и измеряют память.

## §3.10. Перебор срезов и многомерные срезы

```go
for i, value := range s {
	// i — индекс, value — копия s[i]
}
```

Чтобы изменить элемент, используют индекс:

```go
for i := range s {
	s[i] *= 2
}
```

В Go 1.22+ переменные, объявленные через `:=` в заголовке `range`, создаются заново для каждой итерации. Это устранило старую ловушку с замыканиями над одной общей iteration variable. Если переменные объявлены заранее и в `range` используется `=`, присваивание по-прежнему идёт в существующие переменные.

Число итераций по срезу определяется длиной range expression, вычисленной до цикла. Append внутри тела не заставляет range автоматически пройти новые элементы. Изменения уже существующих элементов общего массива могут быть видны последующим итерациям.

Срез срезов не обязан быть прямоугольным:

```go
matrix := [][]int{
	{1, 2},
	{3, 4, 5},
	{},
}
```

Каждая строка имеет собственные length, capacity и underlying array. Иногда для локальности создают один большой плоский срез и несколько строк-представлений поверх него.

## §3.11. Карты (`map`)

Карта хранит соответствие ключей значениям:

```go
var ages map[string]int
```

Тип читается как «map из `string` в `int`». Нулевое значение карты — `nil`.

### Создание

```go
ages := make(map[string]int)
scores := make(map[string]int, 100)
colors := map[string]string{
	"red":   "#ff0000",
	"green": "#00ff00",
}
```

Второй аргумент `make` — подсказка о начальном количестве элементов. Это не length, не capacity в смысле среза и не предел роста. У карты нет встроенной `cap`.

### Чтение и отсутствие ключа

```go
age := ages["Ann"]
```

Если ключа нет, выражение возвращает нулевое значение типа элемента. Чтобы отличить отсутствие от сохранённого нуля, используют comma-ok form:

```go
age, ok := ages["Ann"]
if !ok {
	fmt.Println("ключ отсутствует")
}
```

В кратком условии область видимости обеих переменных ограничена `if` и его ветвями:

```go
if age, ok := ages["Ann"]; ok {
	fmt.Println(age)
}
```

### Добавление, обновление и удаление

```go
ages["Ann"] = 30 // добавить или заменить
ages["Ann"]++    // прочитать, увеличить и записать
delete(ages, "Ann")
clear(ages)
```

`delete` отсутствующего ключа безопасен. `clear` удаляет все записи. Ни одна операция не обещает немедленно вернуть внутреннюю память операционной системе.

`len(m)` возвращает текущее число записей.

### Nil map

Из nil map можно читать, по ней можно выполнять `range`, `len`, `delete` и `clear`:

```go
var m map[string]int
fmt.Println(m["x"]) // 0
fmt.Println(len(m))  // 0
delete(m, "x")      // допустимо
clear(m)            // допустимо
```

Запись вызывает panic:

```go
// m["x"] = 1 // panic: assignment to entry in nil map
```

Перед записью карту инициализируют через `make` или литерал.

## §3.12. Ключи и значения карты

Тип ключа должен быть comparable. Допустимы, например, числа, bool, строки, указатели, каналы, а также массивы и структуры, если все их составляющие сравнимы.

Срезы, карты и функции нельзя использовать как ключи:

```go
// var bad map[[]byte]int // ошибка компиляции
```

Структура часто образует удобный составной ключ:

```go
type Coordinate struct {
	X int
	Y int
}

visited := map[Coordinate]bool{
	{X: 10, Y: 20}: true,
}
```

Интерфейсный тип формально comparable и может быть типом ключа. Но если динамическое значение внутри интерфейса несравнимо, попытка использовать его как ключ вызовет panic:

```go
m := make(map[any]string)
// m[[]int{1, 2}] = "x" // panic: hash of unhashable type []int
```

Значением карты может быть значение любого типа.

### Особенность floating-point ключей

`float64` является comparable, однако `NaN != NaN`. Запись с NaN-ключом нельзя надёжно получить обычным lookup с тем же числовым значением и трудно удалить по ключу. Это одна из причин избегать NaN в роли ключа. `clear` способен удалить и такие записи.

### Элемент карты не адресуем

Нельзя взять адрес элемента или изменить поле структуры прямо внутри карты:

```go
type User struct {
	Age int
}

users := map[string]User{"Ann": {Age: 30}}
// users["Ann"].Age++ // ошибка компиляции
// p := &users["Ann"]  // ошибка компиляции
```

Runtime может перемещать записи при росте. Язык не предоставляет стабильный адрес слота. Для значения-структуры применяют read-modify-write:

```go
user := users["Ann"]
user.Age++
users["Ann"] = user
```

Или хранят указатели, если именно совместно изменяемый объект соответствует модели данных:

```go
users := map[string]*User{"Ann": {Age: 30}}
users["Ann"].Age++
```

Если значением является срез, изменение его элемента допустимо, потому что lookup возвращает копию descriptor, всё ещё указывающую на общий массив:

```go
m := map[string][]int{"x": {1, 2}}
m["x"][0] = 99
```

Но изменившуюся после append длину необходимо записать обратно:

```go
m["x"] = append(m["x"], 3)
```

## §3.13. Присваивание, передача и копирование карт

Присваивание карты не копирует все записи:

```go
first := map[string]int{"x": 1}
second := first
second["x"] = 100

fmt.Println(first["x"]) // 100
```

Функция тоже получает копию небольшого значения, ссылающегося на ту же внутреннюю карту. Поэтому для изменения записей `*map[K]V` обычно не нужен:

```go
func increment(m map[string]int, key string) {
	m[key]++
}
```

Указатель на map требуется редко — например, если функция должна заменить саму map переменную вызывающей стороны, — и часто понятнее вернуть новое значение.

Для независимой поверхностной копии:

```go
clone := maps.Clone(original)
```

Копия поверхностная: вложенные срезы, карты и указатели всё ещё могут вести к общим данным.

Карты нельзя сравнивать между собой, только с `nil`. Для сравнения содержимого существуют `maps.Equal` и `maps.EqualFunc`.

## §3.14. Итерация и конкурентный доступ к картам

```go
for key, value := range m {
	fmt.Println(key, value)
}
```

Порядок не определён спецификацией и не гарантируется одинаковым между двумя проходами. Если нужен стабильный вывод, ключи собирают в срез и сортируют.

Изменение карты в той же горутине во время итерации имеет определённые границы поведения:

- запись, удалённая до того, как range дошёл до неё, выдана не будет;
- запись, добавленная во время цикла, может быть выдана, а может не быть;
- выбор может различаться между итерациями.

Для обновлённого значения спецификация формулирует iteration value как значение соответствующей записи в момент итерации; нельзя строить алгоритм на внутреннем расположении элементов.

### Конкурентность

Несколько горутин могут одновременно только читать карту, если никто её не меняет. Если хотя бы одна горутина пишет, доступ нужно синхронизировать, например `sync.Mutex` или `sync.RWMutex`, либо выбрать иную модель владения.

Одновременные чтение и запись или две записи без синхронизации являются data race. Runtime часто завершает программу сообщением вроде `concurrent map read and map write`, но обнаружение runtime не заменяет проверку `go test -race` и не является механизмом восстановления.

`sync.Map` предназначена для специальных конкурентных сценариев, а не как автоматическая замена каждой `map` с mutex.

## §3.15. Как устроены Swiss Tables в Go

Этот раздел описывает реализацию стандартного toolchain, а не дополнительные гарантии языка. Он опирается на [официальную статью Go о Swiss Tables](https://go.dev/blog/swisstable), [release notes Go 1.24](https://go.dev/doc/go1.24), указанную обзорную [статью на Habr](https://habr.com/ru/companies/oleg-bunin/articles/934906/) и пошаговый разбор [How Go’s Built-in Map Works with Swiss Tables](https://victoriametrics.com/blog/go-swiss-table-map/), на который перенаправляет короткая ссылка из задания. Нормативными источниками остаются спецификация и официальная документация Go.

Go 1.24 заменил прежнюю внутреннюю реализацию встроенных карт на вариант Swiss Table. Синтаксис `map[K]V` и рассмотренное выше поведение не изменились.

### Хеш и группы

Для ключа вычисляется hash. В упрощённой модели он делится на две части:

- `h1`, старшие биты, помогает выбрать начальную группу и таблицу;
- `h2`, младшие 7 бит, служит коротким fingerprint ключа.

Записи организованы группами по 8 слотов. Рядом с каждой группой хранится 64-битное control word: по одному управляющему байту на слот. Байты отмечают, что слот:

- свободен;
- удалён и является tombstone;
- занят — тогда metadata содержит `h2`.

При поиске runtime сравнивает искомый `h2` сразу со всеми восемью управляющими байтами с помощью битовых операций или подходящих инструкций. Полные ключи сравниваются только в слотах-кандидатах. Совпадение 7-битного fingerprint ещё не доказывает равенство: возможна коллизия, поэтому окончательная проверка ключа обязательна.

### Probing и tombstones

Если в первой выбранной группе ключ не найден, алгоритм переходит к следующим группам по probe sequence. Встреча действительно пустого слота означает, что искомого ключа дальше в этой последовательности нет.

После удаления слот не всегда можно немедленно считать изначально пустым. Tombstone сохраняет непрерывность probe sequence: иначе поиск ключа, вытесненного дальше из-за коллизии, мог бы остановиться слишком рано. При последующем обслуживании таблицы tombstones могут быть переиспользованы или устранены.

### Почему это быстрее

Основные причины:

- metadata компактна и хорошо попадает в CPU cache;
- одна операция быстро отсеивает сразу несколько слотов;
- полное сравнение выполняется для меньшего числа ключей;
- допустима более высокая заполненность, что уменьшает расход памяти;
- данные размещены плотнее, чем в схеме с длинными цепочками указателей.

Это преимущества типичных нагрузок, не обещание фиксированного ускорения каждой программы. В официальных измерениях перед Go 1.24 отдельные map microbenchmarks ускорялись вплоть до 60%, а среднее улучшение CPU time полноценных приложений было примерно 1,5%; у отдельных случаев наблюдались регрессии.

### Несколько таблиц и постепенный рост

Классическая Swiss Table обычно растёт целиком, но копирование гигантской карты за одну вставку создало бы большую задержку. Go добавляет уровень directory и делит map на несколько независимых tables — вариант extendible hashing.

Отдельная table хранит не более 1024 записей. Старшие биты hash выбирают table. Когда она переполняется, runtime может вырастить или разделить только её, не перехешируя немедленно всю map. Так объём работы одной вставки ограничен ростом таблицы размером до 1024 записей.

Небольшая map может использовать особенно компактное представление одной группы без полноценного directory. Все эти числа и структуры — детали текущей реализации и могут измениться.

### Коэффициент заполнения

Обычная table обслуживается до средней занятости `7/8`, то есть 87,5%. При подсчёте учитываются как живые записи, так и tombstones. Свободные слоты нужны не только для вставки: обнаружив `empty`, неуспешный lookup может закончить probing раньше. Чем плотнее таблица, тем меньше лишней памяти, но тем длиннее в среднем поиск свободного слота и отсутствующего ключа.

Это значение не является свойством типа `map` и недоступно через API. Runtime может изменить его в последующих версиях.

### Эксперимент с раздельным размещением ключей и значений

В базовой реализации группа концептуально содержит восемь пар `{key, value}`. Go 1.27 также содержит эксперимент `GOEXPERIMENT=mapsplitgroup`, при котором ключи и значения располагаются отдельными массивами внутри группы.

При lookup сначала нужны metadata и ключи-кандидаты; значение читается лишь после полного совпадения ключа. Раздельное размещение способно улучшить локальность ключей и убрать часть padding, особенно у `map[K]struct{}`. Эксперимент не меняет алгоритм probing или семантику map. Как и любой `GOEXPERIMENT`, он не является стабильным пользовательским контрактом и в будущей версии может измениться, стать стандартным либо исчезнуть.

### Итерация при росте

Go разрешает добавлять и удалять записи во время range в одной горутине. Это усложняет Swiss Table: рост меняет расположение записей.

Итератор может продолжить обход старой таблицы для сохранения позиции, а перед выдачей проверить актуальную таблицу, чтобы не вернуть удалённое или устаревшее значение. Новая запись может не попасть в обход, что разрешено спецификацией.

### Что нельзя выводить из устройства Swiss Table

Из описания реализации нельзя заключать, что:

- порядок range связан с hash или физическими слотами;
- адрес элемента стабилен;
- capacity карты доступна программе;
- конкретный коэффициент загрузки является частью API;
- операция всегда занимает строго постоянное время;
- карта автоматически безопасна для конкурентной записи.

Правильность программы должна зависеть только от языковых гарантий. Знание внутренностей полезно для понимания производительности и профилей.

## §3.16. Ошибка как значение

В Go ожидаемая неудача обычно возвращается обычным значением типа `error`:

```go
type error interface {
	Error() string
}
```

Это предопределённый интерфейс. Любой тип с методом `Error() string` удовлетворяет ему.

Соглашение:

- `nil` означает успех;
- ненулевой `error` описывает неудачу.

```go
value, err := strconv.Atoi("42")
if err != nil {
	fmt.Println("не удалось разобрать число:", err)
	return
}
fmt.Println(value)
```

Проверку обычно выполняют сразу и завершают неуспешную ветвь раньше. Основной путь остаётся без глубокой вложенности.

### Создание простой ошибки

```go
err := errors.New("configuration is empty")
```

Каждый вызов `errors.New`, даже с одинаковым текстом, создаёт отдельное значение ошибки. Сравнивать ошибки только по строке не следует.

Форматированное сообщение:

```go
err := fmt.Errorf("invalid port %d", port)
```

Текст ошибок в Go по соглашению начинается со строчной буквы и не заканчивается точкой или переводом строки: вызывающий код может добавить контекст и оформить итоговое сообщение.

## §3.17. Возврат и распространение ошибок

Типичная сигнатура возвращает полезное значение и ошибку:

```go
func load(path string) ([]byte, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, err
	}
	return data, nil
}
```

При ошибке остальные результаты обычно имеют нулевые значения, но это соглашение конкретной функции, а не универсальное правило языка. Некоторые API возвращают одновременно частичный результат и ошибку; их документацию нужно читать отдельно.

### Добавление контекста

```go
data, err := os.ReadFile(path)
if err != nil {
	return nil, fmt.Errorf("read configuration %q: %w", path, err)
}
```

`%w` сохраняет исходную ошибку в цепочке. `%v` только включает её текст:

```go
fmt.Errorf("read configuration: %v", err) // без оборачивания
```

Выбор — часть API. `%w` позволяет вызывающему коду распознавать внутреннюю ошибку и тем самым делает её наблюдаемой частью контракта. Иногда это желательно, иногда реализацию намеренно скрывают.

Не следует одновременно логировать ошибку на каждом уровне и возвращать её выше: одна неудача превратится в несколько одинаковых записей. Обычно нижние уровни добавляют контекст и возвращают, а граница приложения логирует или показывает результат пользователю.

### Несколько `%w`

`fmt.Errorf` с несколькими глаголами `%w` создаёт ошибку, оборачивающую несколько причин. `errors.Is` и `errors.As` обходят всё дерево. Порядок обхода — сама ошибка, затем depth-first её дочерние ошибки.

## §3.18. Sentinel errors и `errors.Is`

Sentinel error — опубликованное заранее значение, которое обозначает распознаваемое условие:

```go
var ErrNotFound = errors.New("not found")
```

Функция может вернуть его напрямую или обернуть:

```go
return fmt.Errorf("user %q: %w", id, ErrNotFound)
```

Прямое сравнение видит только тот же самый верхний объект:

```go
if err == ErrNotFound { /* ... */ }
```

Для цепочки используют:

```go
if errors.Is(err, ErrNotFound) {
	// ErrNotFound находится в дереве либо ошибка объявила совпадение
}
```

`errors.Is` последовательно рассматривает ошибку и результаты методов:

```go
Unwrap() error
```

или

```go
Unwrap() []error
```

Тип ошибки может также реализовать `Is(target error) bool` для собственного правила совпадения. Такой метод должен выполнять неглубокое сравнение и не вызывать `Unwrap` у target.

Sentinel удобен, но опубликованное значение и обещание его возвращать связывают API. Иногда лучше собственный тип ошибки или метод-предикат пакета.

## §3.19. Собственные типы ошибок и `errors.As`

Собственный тип хранит структурированные данные:

```go
type ParseError struct {
	Input string
	Pos   int
	Err   error
}

func (e *ParseError) Error() string {
	return fmt.Sprintf("parse %q at byte %d: %v", e.Input, e.Pos, e.Err)
}

func (e *ParseError) Unwrap() error {
	return e.Err
}
```

Проверка типа с учётом обёрток:

```go
var parseErr *ParseError
if errors.As(err, &parseErr) {
	fmt.Println(parseErr.Pos)
}
```

В `errors.As` передаётся указатель на переменную, куда будет записано найденное значение. Для типа `*ParseError` target имеет тип `**ParseError`; именно поэтому используется `&parseErr`.

Начиная с Go 1.26 доступна типобезопасная generic-форма:

```go
if parseErr, ok := errors.AsType[*ParseError](err); ok {
	fmt.Println(parseErr.Pos)
}
```

Она убирает неудобную двойную адресацию и часть runtime-проверок неправильного target.

Тип может реализовать `As(target any) bool`, чтобы объявить специальное преобразование. Это мощный механизм; реализация обязана корректно установить target и обычно нужна только для совместимости API.

### Pointer receiver или value receiver

Если `Error` объявлен на `*ParseError`, интерфейсу `error` удовлетворяет указатель, но не значение:

```go
func (e *ParseError) Error() string { /* ... */ }
```

Это часто полезно: ошибка с полями не копируется случайно, а `errors.As` ожидаемо ищет `*ParseError`. Если метод объявлен на значении, и значение, и указатель имеют этот метод; нужно последовательно решить, что фактически возвращает API.

## §3.20. Объединение ошибок

`errors.Join` создаёт одну ошибку из нескольких:

```go
err := errors.Join(firstErr, secondErr)
```

Nil-аргументы игнорируются. Если все аргументы nil, результат nil. Ненулевой результат реализует `Unwrap() []error`, поэтому:

```go
errors.Is(err, firstErr)
errors.As(err, &target)
```

могут находить любую причину.

Join полезен, когда несколько независимых действий могли завершиться неудачей, например основная операция и закрытие ресурса:

```go
func writeFile(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() {
		err = errors.Join(err, f.Close())
	}()

	_, err = f.Write(data)
	return err
}
```

Конкретное форматирование joined error не следует разбирать программно. Для решений используют `Is`, `As` и структурированные данные.

`errors.Unwrap` вызывает только `Unwrap() error`; для ошибки с `Unwrap() []error` он возвращает nil. Для обычной проверки дерева это не проблема: `Is` и `As` понимают обе формы.

## §3.21. Ловушка typed nil

Интерфейс равен nil, только если и его динамический тип, и динамическое значение отсутствуют.

```go
type MyError struct{}

func (*MyError) Error() string { return "failed" }

func bad() error {
	var e *MyError = nil
	return e
}

fmt.Println(bad() == nil) // false
```

Возвращённый интерфейс содержит динамический тип `*MyError` и нулевой указатель как динамическое значение, поэтому сам интерфейс ненулевой.

Правильнее возвращать настоящий `nil`:

```go
func good() error {
	var e *MyError
	if e == nil {
		return nil
	}
	return e
}
```

Метод `Error` иногда делают устойчивым к nil receiver, но это не превращает содержащий typed nil интерфейс в nil.

### Сравнимость ошибок

Интерфейсные значения можно сравнить, но сравнение паникует, если их одинаковый динамический тип несравним. Пользовательский error-тип со срезом или map внутри может быть несравнимым. Поэтому для смысловой классификации ошибок предпочтительны `errors.Is` и `errors.As`, а не произвольное `==`.

## §3.22. Ошибки при освобождении ресурсов

`defer` гарантирует попытку cleanup при любом обычном выходе и при раскрутке panic, но ошибка cleanup не должна теряться автоматически.

Для чтения файла ошибка `Close` часто несущественна. Для записи она может означать, что буферизация или финальная синхронизация не удалась:

```go
func save(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return fmt.Errorf("create %q: %w", path, err)
	}

	defer func() {
		if closeErr := f.Close(); closeErr != nil {
			err = errors.Join(err, fmt.Errorf("close %q: %w", path, closeErr))
		}
	}()

	if _, err = f.Write(data); err != nil {
		return fmt.Errorf("write %q: %w", path, err)
	}
	return nil
}
```

Именованный результат позволяет deferred closure изменить возвращаемую ошибку после вычисления return values, но до фактического возврата. Такой код требует аккуратности: затенение `err` через неуместное `:=` может скрыть нужную переменную.

Не каждое API допускает повторный `Close`, а некоторые требуют отдельный `Flush` или `Commit`. Всегда важен контракт ресурса.

## §3.23. `panic` и `recover`

`panic` предназначен не для обычной ветви «файл не найден», а для ситуации, когда выполнение текущего пути не может разумно продолжаться, либо для нарушения внутреннего инварианта.

```go
panic("unreachable state")
```

Panic также возникает автоматически при выходе за границы, разыменовании nil pointer, записи в nil map, некоторых неправильных type assertions и других runtime-ошибках.

### Раскрутка стека

После panic обычное выполнение функции прекращается. Выполняются её deferred calls в обратном порядке, затем процесс повторяется у вызывающей функции. Если panic не восстановлен, программа печатает значение panic и stack trace и завершается.

### Восстановление

`recover` останавливает текущую раскрутку только при прямом вызове из deferred function той же горутины:

```go
func guarded() {
	defer func() {
		if value := recover(); value != nil {
			fmt.Println("recovered:", value)
		}
	}()

	panic("boom")
}
```

Вызов `recover` вне нужного deferred контекста возвращает nil. Нельзя восстановить panic другой горутины: у каждой потенциально аварийной goroutine должна быть собственная граница восстановления.

Начиная с Go 1.21 `panic(nil)` приводит к ненулевому значению типа `*runtime.PanicNilError` при recover, поэтому стандартная проверка `recover() != nil` не теряет такой panic.

### Когда recover уместен

Типичные границы:

- сервер не хочет, чтобы panic одного запроса завершил весь процесс;
- framework превращает внутренний panic в контролируемый ответ;
- пакет использует panic только внутри рекурсивного алгоритма и преобразует его в error на публичной границе.

После recover нужно решить, остаётся ли состояние корректным. Безусловное подавление всех panic может скрыть баг, оставить частично изменённые данные и затруднить диагностику. Обычно граница записывает stack trace и возвращает контролируемую ошибку либо завершает только изолированную единицу работы.

`recover` не ловит фатальные ошибки runtime, которые не представлены обычной panic, и не исправляет data races.

## §3.24. Проектирование error API

Полезные правила:

1. Возвращать `error` для ожидаемой неудачи, которую вызывающий код способен обработать.
2. Использовать panic для нарушенного инварианта или невозможности корректно продолжить, а не как замену каждому `if err != nil`.
3. Добавлять контекст на границе абстракции: что делали и с каким объектом.
4. Использовать `%w`, только если причина должна оставаться доступной вызывающему коду.
5. Предоставлять sentinel, собственный тип или предикат, если от вида ошибки зависит логика.
6. Проверять категории через `errors.Is` и данные через `errors.As`/`AsType`, не по тексту.
7. Документировать частичные результаты, возможные error types и состояние объекта после неудачи.
8. Не игнорировать ошибку без явной причины. Если она заведомо несущественна, это полезно объяснить комментарием.
9. Логировать ошибку один раз на подходящей внешней границе; внутренние уровни обычно возвращают её с контекстом.
10. Не включать секреты в текст ошибки: пути, запросы, токены и пользовательские данные могут попасть в логи.

### Ошибка — не обязательно исключительная ситуация

`io.Reader` может вернуть одновременно `n > 0` и `io.EOF`: сначала нужно обработать прочитанные байты, затем завершить цикл. Некоторые функции используют отдельный `ok`, когда отсутствие не является ошибкой, как lookup карты:

```go
value, ok := m[key]
```

Выбор между `error`, `bool`, нулевым значением и panic выражает смысл API, а не только техническую возможность.

### Ошибки из горутин

Возвращаемое значение горутины никто автоматически не получает, а panic одной горутины нельзя recover в другой. Ошибки передают через канал, группу задач или другой явно выбранный механизм. Конкретные шаблоны синхронизации будут рассмотрены вместе с конкурентностью.

## §3.25. Итоговая модель

Строка — неизменяемая последовательность байтов; `range` интерпретирует её как UTF-8. Rune представляет code point, но не обязательно один видимый символ. Массив содержит фиксированное число элементов и копируется как значение.

Срез — descriptor над underlying array. Его `len` ограничивает доступные индексы, `cap` — возможное расширение без смены массива. Обычный срез задаёт новую длину и сохраняет остаточную capacity; полный срез позволяет ограничить capacity. `append` либо использует общий массив, либо создаёт новый, поэтому aliasing всегда нужно учитывать явно.

Map сопоставляет comparable keys значениям. Нулевую map можно читать, но нельзя изменять; порядок range не определён; элементы не имеют доступного стабильного адреса; конкурентная запись требует синхронизации. Swiss Tables — быстрая современная реализация этих правил, а не новые правила языка.

Ошибка в Go — значение. Её можно вернуть, снабдить контекстом, обернуть, объединить и исследовать через `errors.Is`, `errors.As` и `errors.AsType`. `panic` и `recover` образуют отдельный механизм аварийного выхода и не заменяют обычную обработку ошибок.
