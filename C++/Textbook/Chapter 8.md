# VIII. Контейнеры и итераторы

Стандартные контейнеры предоставляют готовые структуры данных с определёнными гарантиями сложности, временем жизни элементов и правилами инвалидации указателей, ссылок и итераторов. Чтобы правильно выбирать контейнер и безопасно изменять его, недостаточно помнить названия методов: важно понимать, как контейнер может быть устроен внутри и какие свойства следуют из этого устройства.

Стандарт обычно не предписывает конкретную реализацию. Например, он не требует буквально хранить `std::map` в красно-чёрном дереве. Он задаёт наблюдаемое поведение и асимптотические гарантии, а библиотека выбирает структуру, которая эти требования выполняет. Поэтому схемы реализаций в этой главе следует воспринимать как типичные, а не как часть переносимого интерфейса C++.

## §8.1. Устройство `std::vector`

`std::vector<T>` хранит элементы `T` в одном непрерывном участке памяти. Для непустого вектора адреса элементов образуют обычный массив:

```cpp
std::vector<int> values{10, 20, 30};

int* first = values.data();
assert(first + 1 == &values[1]);
```

Благодаря непрерывному хранению вектор поддерживает обращение по индексу за `O(1)`, хорошо использует кэш процессора и может передавать данные интерфейсам, ожидающим указатель на массив.

Упрощённо объект вектора можно представить тремя указателями:

```cpp
T* begin_;     // начало созданных элементов
T* end_;       // позиция после последнего созданного элемента
T* capacity_;  // конец выделенной сырой памяти
```

Эквивалентное представление — указатель, размер и вместимость:

```cpp
T* data_;
std::size_t size_;
std::size_t capacity_;
```

Здесь нужно различать три понятия:

- `size()` — количество уже существующих объектов `T`;
- `capacity()` — количество объектов, для которых зарезервировано место;
- выделенная память между `size()` и `capacity()` ещё не содержит объектов `T`.

Поэтому `reserve(100)` и `resize(100)` выполняют разные задачи. `reserve` увеличивает вместимость, не добавляя элементы. `resize` изменяет количество элементов и при увеличении действительно создаёт новые объекты.

### Почему нельзя просто выполнить `new T[capacity]`

Выражение `new T[capacity]` сразу создаёт `capacity` объектов. Это потребовало бы доступного конструктора по умолчанию и означало бы, что `size()` фактически равен `capacity()`.

Вектору нужна другая последовательность:

1. получить сырую память нужного размера;
2. создавать объекты только в занятых позициях;
3. отдельно уничтожать созданные объекты;
4. освободить сам блок памяти.

Объект появляется в сырой памяти после явного конструирования по выбранному адресу. Такое конструирование часто называют placement construction; традиционная запись использует placement `new`:

```cpp
::new (static_cast<void*>(place)) T(value);
```

Она не выделяет новый блок памяти. Она лишь вызывает конструктор `T`, размещая объект по адресу `place`.

Присваивание вместо конструирования некорректно:

```cpp
new_data[index] = old_data[index]; // В new_data[index] ещё нет объекта T.
```

Оператор присваивания изменяет уже существующий объект. Если время жизни объекта `T` по этому адресу ещё не началось, присваивать нечему.

После переноса элементов старые объекты уничтожают отдельно:

```cpp
old_data[index].~T();
```

Затем освобождают сырую память тем механизмом, которым она была получена. Смешивать, например, `new[]` с обычным `delete` нельзя.

### Упрощённая реализация `reserve`

Ниже показана учебная схема. Настоящий `std::vector` решает те же задачи через внутренние средства управления памятью стандартной библиотеки. Чтобы не заходить в тему следующей главы, пример не реализует отдельную поддержку типов с расширенным требованием к выравниванию.

```cpp
template <typename T>
class MyVector {
private:
    T* data_ = nullptr;
    std::size_t size_ = 0;
    std::size_t capacity_ = 0;

public:
    void reserve(std::size_t new_capacity) {
        if (new_capacity <= capacity_) {
            return;
        }

        T* new_data = static_cast<T*>(
            ::operator new(new_capacity * sizeof(T))
        );

        std::size_t constructed = 0;

        try {
            for (; constructed < size_; ++constructed) {
                ::new (static_cast<void*>(new_data + constructed))
                    T(std::move_if_noexcept(data_[constructed]));
            }
        } catch (...) {
            while (constructed != 0) {
                --constructed;
                new_data[constructed].~T();
            }

            ::operator delete(new_data);
            throw;
        }

        for (std::size_t index = 0; index < size_; ++index) {
            data_[index].~T();
        }

        ::operator delete(data_);
        data_ = new_data;
        capacity_ = new_capacity;
    }
};
```

Сначала создаётся новый блок. Пока все элементы успешно не перенесены, старый блок остаётся нетронутым. Если конструктор очередного элемента выбросит исключение, уже созданные новые элементы уничтожаются, новый блок освобождается, а исключение передаётся дальше.

`std::move_if_noexcept` выбирает перемещение, если оно объявлено `noexcept` либо копирование невозможно. Иначе он предпочитает копирование. Причина связана с гарантией исключений: если перемещающий конструктор сначала изменит старый элемент, а затем выбросит исключение, полностью восстановить исходный вектор может быть невозможно.

Если `T` нельзя скопировать, а его перемещающий конструктор способен выбросить исключение, гарантии операции при неудачном перемещении слабее. Контейнер не может получить прежние значения уже изменённых объектов магическим образом.

Placement `new` сам по себе память не выделяет, но вызываемый им конструктор `T` может выбросить исключение. Обычный деструктор должен быть невыбрасывающим: выход исключения из деструктора во время обработки другого исключения приводит к `std::terminate`.

### `push_back` и рост вместимости

Если свободное место есть, `push_back` конструирует один объект в позиции `data_ + size_` и затем увеличивает размер:

```cpp
void push_back(const T& value) {
    if (size_ == capacity_) {
        reserve(capacity_ == 0 ? 1 : capacity_ * 2);
    }

    ::new (static_cast<void*>(data_ + size_)) T(value);
    ++size_;
}
```

Важен порядок: `size_` увеличивается только после успешного конструирования. Если конструктор `T` выбросит исключение, размер останется прежним.

Конкретный коэффициент роста стандартом не закреплён. Реализации обычно увеличивают вместимость геометрически. Благодаря этому последовательность из `n` добавлений требует суммарно `O(n)` переносов, а один `push_back` имеет амортизированную сложность `O(1)`.

Слово «амортизированную» означает, что отдельный вызов при реаллокации остаётся линейным, но дорогие вызовы происходят достаточно редко. Если увеличивать вместимость ровно на единицу, пришлось бы почти при каждом добавлении переносить все предыдущие элементы, и суммарная сложность стала бы квадратичной.

`reserve` позволяет заранее исключить промежуточные реаллокации, если ожидаемый размер известен:

```cpp
std::vector<std::string> words;
words.reserve(1000);

for (int i = 0; i < 1000; ++i) {
    words.push_back(read_word());
}
```

Вызов `reserve` с аргументом, не превышающим текущую вместимость, ничего не уменьшает. `shrink_to_fit` является лишь запросом на уменьшение вместимости: стандарт не обязывает реализацию его удовлетворять.

### Инвалидация указателей, ссылок и итераторов

При реаллокации элементы оказываются в новом блоке. Поэтому все указатели, ссылки и итераторы на элементы прежнего блока становятся недействительными:

```cpp
std::vector<int> values;
values.reserve(1);
values.push_back(10);

int* pointer = &values[0];
values.push_back(20); // Скорее всего потребуется реаллокация.

std::cout << *pointer; // UB: pointer относится к освобождённому блоку.
```

Опасность заключается не в самом старом числовом адресе, а в том, что время жизни находившегося там объекта закончилось и память могла быть освобождена или использована повторно.

Если `push_back` не вызывает реаллокацию, ссылки и итераторы на существующие элементы сохраняются, но прежний `end()` инвалидируется. Операции вставки и удаления в середине дополнительно инвалидируют позиции в точке изменения и после неё, поскольку элементы сдвигаются.

Нельзя определять безопасность только по названию метода. Нужно учитывать конкретную операцию, наличие реаллокации и положение элемента относительно вставки или удаления.

### Специализация `std::vector<bool>`

Обычный `vector<T>` хранит каждый элемент как отдельный объект `T`. Для `bool` стандарт разрешает специальное уплотнённое представление: несколько логических значений могут храниться в битах одного машинного слова.

У отдельного бита нет самостоятельного адреса, который можно представить как `bool*`. Поэтому неконстантный `operator[]` возвращает не `bool&`, а прокси-объект, ведущий себя похоже на ссылку:

```cpp
class BitReference {
private:
    unsigned char* byte_;
    unsigned char mask_;

public:
    BitReference(unsigned char* byte, unsigned char mask)
        : byte_(byte), mask_(mask) {}

    BitReference& operator=(bool value) {
        if (value) {
            *byte_ |= mask_;
        } else {
            *byte_ &= static_cast<unsigned char>(~mask_);
        }
        return *this;
    }

    operator bool() const {
        return (*byte_ & mask_) != 0;
    }
};
```

Отсюда следует нетривиальный эффект:

```cpp
std::vector<bool> flags{true, false};
auto value = flags[0];
```

`value` здесь может оказаться прокси, а не независимым `bool`. Если нужен именно снимок значения, тип можно указать явно:

```cpp
bool value = flags[0];
```

`vector<bool>` сохраняет контейнерный интерфейс настолько, насколько это возможно, но предположение «разыменование всегда даёт настоящий `T&`» для него неверно.

## §8.2. Устройство `std::deque`

`std::deque<T>` поддерживает быстрые вставку и удаление с обоих концов, а также обращение по индексу за `O(1)`. При этом его элементы не обязаны лежать в одном непрерывном блоке.

Типичная реализация состоит из:

- массива указателей на блоки;
- нескольких блоков, каждый из которых содержит место для некоторого количества элементов `T`;
- информации о позиции первого и позиции после последнего элемента.

Схематично:

```text
карта блоков: [ * ][ * ][ * ][ * ]
                  |    |    |
                  v    v    v
                [T T][T T][T T]
```

Чтобы найти элемент по индексу, реализация вычисляет номер блока и смещение внутри него. Это больше действий, чем сложение указателя у `vector`, но количество действий не зависит от размера дека, поэтому сложность остаётся `O(1)`.

При добавлении в конец или начало обычно конструируется один новый элемент в свободной позиции соответствующего крайнего блока. Когда крайний блок заполнен, создаётся ещё один блок. Если заполнена сама карта указателей, реаллоцируется карта, но уже созданные объекты `T` при этом не обязаны перемещаться.

Именно поэтому добавление на концах дека не инвалидирует ссылки и указатели на существующие элементы. Однако итераторы при такой вставке инвалидируются: итератор дека обычно содержит сведения не только об адресе элемента, но и о блоке либо карте блоков.

Правила отличаются в зависимости от операции:

- вставка на одном из концов не инвалидирует ссылки и указатели на существующие элементы, но инвалидирует итераторы;
- вставка в середину инвалидирует все итераторы и ссылки;
- удаление в середине также инвалидирует все итераторы и ссылки;
- удаление на конце затрагивает как минимум удалённые элементы, а правила для итераторов требуют отдельной осторожности.

Таким образом, фраза «`deque` никогда не инвалидирует адреса» неверна. Его преимущество относится прежде всего к добавлению элементов на концах.

### Почему операции на концах имеют константную сложность

`push_back` и `push_front` работают за константное амортизированное время. Иногда нужно выделить блок или увеличить карту указателей, но не требуется переносить все существующие элементы `T`, как при росте `vector`.

При оценке сложности учитываются и служебные операции реализации. Однако увеличение карты происходит редко, поэтому стоимость также амортизируется. Утверждение, будто операции с сырой памятью или указателями вообще не учитываются, неверно: они учитываются, просто их число в среднем ограничено.

### Адаптеры контейнеров

`std::stack`, `std::queue` и `std::priority_queue` называются адаптерами: они хранят другой контейнер и предоставляют только интерфейс нужной структуры данных.

По умолчанию:

- `std::stack<T>` использует `std::deque<T>`;
- `std::queue<T>` использует `std::deque<T>`;
- `std::priority_queue<T>` использует `std::vector<T>`.

Базовый контейнер можно заменить, если он поддерживает необходимые операции:

```cpp
std::stack<int, std::vector<int>> stack;
std::queue<int, std::list<int>> queue;
```

У `stack` метод `pop()` ничего не возвращает. Получение и удаление разделены:

```cpp
int value = stack.top();
stack.pop();
```

Если бы `pop` сначала удалял элемент, а затем возвращал его по значению, исключение при копировании возвращаемого объекта могло бы привести к потере уже удалённого элемента. Раздельный интерфейс позволяет сначала успешно получить значение, а потом явно изменить контейнер. Кроме того, вызывающий код не платит за копирование, если значение ему не требуется.

## §8.3. Итераторы и их категории

Итератор — объект, обозначающий позицию в последовательности и предоставляющий операции перехода между позициями. Алгоритмы стандартной библиотеки работают с итераторами, а не с конкретными контейнерами, поэтому один алгоритм можно применять к массивам, векторам, спискам и потокам.

Обычный указатель удовлетворяет требованиям многих итераторов:

```cpp
int values[] = {3, 1, 4};
std::sort(values, values + 3);
```

Здесь `values` и `values + 3` задают полуинтервал `[begin, end)`: начало включено, конечная позиция не является элементом диапазона.

Итератор `end()` разрешено сравнивать и использовать как границу, но нельзя разыменовывать:

```cpp
auto iterator = values.end();
std::cout << *iterator; // UB
```

### Иерархия категорий

Категория описывает не конкретный класс, а гарантированный набор операций.

#### Input iterator

Итератор ввода позволяет прочитать элемент и перейти вперёд. Он может быть однопроходным: после продвижения копии итератора прежнее значение не обязано оставаться доступным независимо. Типичный пример — чтение из потока.

#### Forward iterator

Forward iterator поддерживает многопроходность. Две равные копии, проходящие по неизменяемому диапазону, наблюдают одну и ту же последовательность.

Такие итераторы предоставляют, например, `std::forward_list` и unordered-контейнеры.

#### Bidirectional iterator

В дополнение к движению вперёд поддерживает `--iterator`. Такие итераторы есть у `std::list`, `std::set` и `std::map`.

#### Random access iterator

Поддерживает переход на произвольное расстояние, разность, индексирование и упорядочивающее сравнение позиций:

```cpp
iterator += n;
iterator[n];
last - first;
first < last;
```

Эти операции выполняются за константное время. `std::deque` предоставляет random access iterator, хотя его элементы не образуют непрерывный массив.

#### Contiguous iterator

Дополнительно гарантирует физическую непрерывность элементов. К этой категории относятся итераторы `std::vector`, `std::array` и обычные указатели.

Каждая следующая категория усиливает предыдущую. Алгоритм, которому достаточно движения вперёд, может принять random access iterator, но алгоритм вроде `std::sort`, которому нужен произвольный доступ, не может работать с итератором `std::list`.

### Range-based `for`

Цикл по диапазону приблизительно преобразуется в следующий код:

```cpp
for (int value : container) {
    use(value);
}
```

```cpp
auto&& range = container;
auto begin = range.begin();
auto end = range.end();

for (; begin != end; ++begin) {
    int value = *begin;
    use(value);
}
```

Если написать `int& value`, результат разыменования должен позволять привязать соответствующую ссылку. Если написать `auto`, можно получить прокси-тип, как у `vector<bool>`.

Граница вычисляется перед циклом, но это не делает изменение контейнера безопасным. Если операция инвалидирует `begin` или сохранённый `end`, последующее сравнение или разыменование уже недействительного итератора приводит к UB:

```cpp
std::vector<int> values{1, 2, 3};

for (int value : values) {
    values.push_back(value); // Возможная реаллокация инвалидирует итераторы цикла.
}
```

Это не корректный бесконечный цикл: поведение становится неопределённым раньше, чем можно рассуждать о числе итераций.

### `iterator_traits`

Обобщённому коду нужны связанные с итератором типы: тип значения, тип разности, категория и другие. `std::iterator_traits<Iterator>` предоставляет единый способ получить их и работает в том числе для обычных указателей.

Например, классическая реализация `distance` может выбрать алгоритм по категории:

```cpp
template <typename Iterator>
typename std::iterator_traits<Iterator>::difference_type
my_distance(Iterator first, Iterator last) {
    using Category = typename
        std::iterator_traits<Iterator>::iterator_category;
    using Difference = typename
        std::iterator_traits<Iterator>::difference_type;

    if constexpr (std::is_base_of_v<
                      std::random_access_iterator_tag,
                      Category>) {
        return last - first;
    } else {
        Difference result = 0;
        for (; first != last; ++first) {
            ++result;
        }
        return result;
    }
}
```

Для random access iterator расстояние вычисляется за `O(1)`. Для более слабого итератора требуется пройти диапазон, поэтому сложность равна `O(n)`.

`difference_type` обычно является знаковым типом: расстояние между позициями может быть отрицательным. Использовать для него безусловно `int` или `size_t` неправильно.

### Устройство собственного итератора

Итератор упрощённого непрерывного контейнера может хранить указатель:

```cpp
template <typename T>
class MyVectorIterator {
private:
    T* pointer_ = nullptr;

public:
    explicit MyVectorIterator(T* pointer) : pointer_(pointer) {}

    T& operator*() const {
        return *pointer_;
    }

    T* operator->() const {
        return pointer_;
    }

    MyVectorIterator& operator++() {
        ++pointer_;
        return *this;
    }

    MyVectorIterator operator++(int) {
        MyVectorIterator old = *this;
        ++*this;
        return old;
    }

    friend bool operator==(MyVectorIterator left,
                           MyVectorIterator right) {
        return left.pointer_ == right.pointer_;
    }
};
```

Префиксный `operator++` возвращает `*this` по ссылке. Возвращать `this` нельзя: `this` является указателем на объект итератора.

Константность самого итератора и константность элемента — разные вещи:

```cpp
const std::vector<int>::iterator iterator = values.begin();
*iterator = 10; // Допустимо: нельзя передвинуть iterator, но элемент изменяем.
```

`const_iterator` запрещает изменение элемента через разыменование. Чтобы не дублировать реализацию, пару `iterator`/`const_iterator` часто строят из одного шаблона:

```cpp
template <bool IsConst>
class BaseIterator {
    using Pointer = std::conditional_t<IsConst, const T*, T*>;
    using Reference = std::conditional_t<IsConst, const T&, T&>;

    Pointer pointer_ = nullptr;

public:
    Reference operator*() const {
        return *pointer_;
    }
};
```

Неконстантный итератор должен неявно преобразовываться в константный, но не наоборот. Иначе через `const_iterator` можно было бы вернуть возможность изменять объект.

Методы контейнера обычно имеют пары перегрузок:

```cpp
iterator begin();
const_iterator begin() const;
const_iterator cbegin() const;
```

Возвращать `const iterator` по значению вместо `const_iterator` недостаточно: верхнеуровневый `const` у временного объекта не обеспечивает константность элемента.

### Обратные итераторы

`std::reverse_iterator<Iterator>` — адаптер над обычным итератором. Контейнер может определить:

```cpp
using reverse_iterator = std::reverse_iterator<iterator>;
using const_reverse_iterator = std::reverse_iterator<const_iterator>;
```

Внутри reverse iterator хранит базовый итератор, указывающий на позицию после логически текущего элемента. Поэтому выполняется соотношение:

```cpp
&*reverse_iterator == &*(reverse_iterator.base() - 1)
```

для итератора с произвольным доступом. Такая асимметрия нужна, чтобы `rbegin()` можно было построить из `end()`, а `rend()` — из `begin()` без создания позиции «до начала» обычного диапазона.

### Инвалидация и `swap`

Хранение индекса вместо позиции не является универсальным способом избежать инвалидации. После вставки индекс может обозначать уже другой элемент, а требования контейнеров после `swap` связывают итератор с элементом, а не с прежним объектом контейнера.

Правила инвалидации являются частью контракта каждого контейнера. Нельзя переносить правило `vector` на `list` или правило `deque` на `unordered_map` только потому, что во всех случаях используется слово «итератор».

### Output iterator

Output iterator предназначен для записи. Алгоритм может присвоить значение через разыменование и затем продвинуть итератор:

```cpp
*result = value;
++result;
```

Пустой вектор не предоставляет готовых элементов для записи:

```cpp
int source[] = {1, 2, 3};
std::vector<int> destination;

std::copy(std::begin(source), std::end(source), destination.begin()); // UB
```

`destination.begin() == destination.end()`, и разыменовывать эту позицию нельзя. Если заранее создать три элемента, запись станет допустимой:

```cpp
std::vector<int> destination(3);
std::copy(std::begin(source), std::end(source), destination.begin());
```

Если элементы нужно именно добавлять, используют `std::back_inserter`:

```cpp
std::vector<int> destination;
std::copy(std::begin(source), std::end(source),
          std::back_inserter(destination));
```

Адаптер хранит ссылку на контейнер, а присваивание вызывает `push_back`. Разыменование и инкремент возвращают сам адаптер, поскольку реальная позиция определяется очередным добавлением:

```cpp
template <typename Container>
class BackInsertIterator {
private:
    Container* container_;

public:
    explicit BackInsertIterator(Container& container)
        : container_(&container) {}

    BackInsertIterator& operator=(
        const typename Container::value_type& value) {
        container_->push_back(value);
        return *this;
    }

    BackInsertIterator& operator*() {
        return *this;
    }

    BackInsertIterator& operator++() {
        return *this;
    }

    BackInsertIterator operator++(int) {
        return *this;
    }
};
```

Аналогично `std::front_inserter` вызывает `push_front`, а `std::inserter` вставляет перед заданной позицией.

## §8.4. Потоки ввода и вывода

`std::cin`, `std::cout` и `std::cerr` — глобальные объекты потоков:

- `std::cin` обычно связан со стандартным вводом процесса;
- `std::cout` — со стандартным выводом;
- `std::cerr` — со стандартным потоком ошибок.

В Unix-подобной командной оболочке этим потокам соответствуют файловые дескрипторы `0`, `1` и `2`. Это свойство окружения процесса, а не нумерация объектов в самом языке C++.

Командная оболочка позволяет перенаправлять потоки:

```sh
./program > output.txt
./program >> output.txt
./program 2> errors.txt
./producer | ./consumer
./program | tee output.txt
```

`>` перезаписывает файл, `>>` дописывает в конец, `2>` перенаправляет стандартный поток ошибок, а `|` соединяет стандартный вывод первой программы со стандартным вводом второй. `tee` одновременно пишет полученные данные в файл и в свой стандартный вывод.

Эти операторы интерпретирует оболочка до запуска программы. C++-код продолжает писать в `std::cout`, не зная, подключён к нему терминал, файл или канал другой программы.

### Буферизация

Вывод отдельного символа в терминал или файл может быть значительно дороже записи символа в память. Поэтому поток накапливает данные в буфере и передаёт их внешнему устройству порциями.

```cpp
std::cout << "processing...";
```

После этой строки символы не обязаны уже отображаться на экране. Принудительно передать накопленные данные можно через:

```cpp
std::cout.flush();
```

Манипулятор `std::endl` сначала выводит перевод строки, а затем очищает буфер:

```cpp
std::cout << "done" << std::endl;
```

Обычный `\n` сам по себе не требует безусловного `flush`, поэтому в цикле вывода он обычно дешевле:

```cpp
std::cout << value << '\n';
```

При нормальном завершении программы стандартные потоки очищаются. При аварийном завершении, например через `std::abort`, рассчитывать на это нельзя.

### Связывание потоков и синхронизация с C

По умолчанию `std::cin` связан с `std::cout`: перед операцией ввода связанный поток вывода очищается. Это позволяет пользователю увидеть приглашение, даже если код не вызвал `flush` явно:

```cpp
std::cout << "Enter value: ";
int value;
std::cin >> value; // Перед чтением cout обычно будет очищен.
```

Связь направлена от входного потока к выходному. Утверждение, что `cin` и `cout` обязательно хранят указатели друг на друга, неверно.

Для производительности связь можно убрать:

```cpp
std::cin.tie(nullptr);
```

После этого приглашение при необходимости нужно очищать вручную.

Потоки C++ по умолчанию синхронизированы с потоками C, чтобы допустимо было согласованно смешивать, например, `std::cout` и `std::printf`. Синхронизацию часто отключают в программах с большим объёмом ввода:

```cpp
std::ios_base::sync_with_stdio(false);
std::cin.tie(nullptr);
```

После отключения не следует рассчитывать на согласованный порядок смешанного вывода через C и C++ без дополнительных мер. Эти настройки обычно выполняют один раз в начале программы, до операций с потоками.

### Состояние потока

Операция ввода возвращает ссылку на поток. В условии поток проверяет своё состояние:

```cpp
int value;

while (std::cin >> value) {
    use(value);
}
```

Цикл завершается, если чтение не удалось: достигнут конец данных либо вход нельзя преобразовать в `int`. Это не означает, что `operator>>` буквально возвращает `bool`; возвращается `std::istream&`, который допускает контекстное преобразование в `bool`.

После ошибки поток сохраняет флаги состояния. Пока они не сброшены через `clear()`, последующие операции чтения также не будут успешными. Неподходящие символы при ошибке преобразования могут остаться во входной последовательности, поэтому одного `clear()` иногда недостаточно — нужно ещё удалить или прочитать проблемный ввод.

### Файловые и строковые потоки

Файловые потоки используют тот же интерфейс форматированного ввода и вывода:

```cpp
std::ifstream input("input.txt");
std::ofstream output("output.txt");

int value;
if (input >> value) {
    output << value << '\n';
}
```

Объект нужно проверить: открытие файла может завершиться неудачей.

Строковые потоки читают из строки или формируют строку:

```cpp
std::istringstream input("10 20 30");

int first;
int second;
input >> first >> second;
```

```cpp
std::ostringstream output;
output << "x = " << 42;

std::string result = output.str();
```

Это удобно, когда нужно применить обычные правила потокового форматирования к данным в памяти.

### Потоковые итераторы

`std::istream_iterator<T>` превращает форматированный ввод в диапазон. При создании или продвижении он считывает очередной объект `T`:

```cpp
std::istream_iterator<int> begin(std::cin);
std::istream_iterator<int> end;

std::vector<int> values(begin, end);
```

Итератор, сконструированный по умолчанию, играет роль конца потока. После неудачного чтения входной итератор становится равен такому конечному итератору.

Упрощённая логика выглядит так:

```cpp
template <typename T>
class InputStreamIterator {
private:
    std::istream* input_ = nullptr;
    std::optional<T> value_;

    void read() {
        T value;
        if (input_ != nullptr && *input_ >> value) {
            value_ = std::move(value);
        } else {
            input_ = nullptr;
            value_.reset();
        }
    }

public:
    InputStreamIterator() = default;

    explicit InputStreamIterator(std::istream& input)
        : input_(&input) {
        read();
    }

    InputStreamIterator& operator++() {
        read();
        return *this;
    }

    const T& operator*() const {
        return *value_;
    }
};
```

`std::optional<T>` здесь выражает два состояния: считанное значение существует либо итератор находится в конце. Реальная реализация должна также предоставить сравнение, постфиксный инкремент и связанные типы итератора.

Потоковый итератор является однопроходным. Копирование итератора не копирует источник данных: обе копии всё равно связаны с одним потоком. Поэтому нельзя ожидать независимых повторных проходов.

`std::ostream_iterator<T>` выполняет обратную адаптацию: присваивание итератору записывает объект в поток. Необязательная строка-разделитель выводится после каждого значения:

```cpp
std::copy(values.begin(), values.end(),
          std::ostream_iterator<int>(std::cout, " "));
```

Потоковые итераторы можно объединять с алгоритмами:

```cpp
bool is_even(int value) {
    return value % 2 == 0;
}

std::ifstream input("input.txt");

std::copy_if(
    std::istream_iterator<int>(input),
    std::istream_iterator<int>(),
    std::ostream_iterator<int>(std::cout, " "),
    is_even
);
```

### Манипуляторы

Манипулятор меняет состояние потока или выполняет действие над ним:

```cpp
int value = 57179;
std::cout << std::hex << value; // df5b
```

Состояние форматирования сохраняется. Следующий целочисленный вывод через тот же поток также будет шестнадцатеричным, пока режим не вернуть:

```cpp
std::cout << std::dec;
```

Другие примеры:

- `std::setprecision(n)` задаёт точность вывода чисел с плавающей точкой;
- `std::noskipws` запрещает форматированному вводу пропускать начальные пробельные символы;
- `std::skipws` возвращает обычный режим пропуска;
- `std::flush` очищает буфер;
- `std::endl` выводит перевод строки и очищает буфер.

Некоторые манипуляторы являются функциями, принимающими и возвращающими ссылку на поток или его базовую часть. Для них у потокового `operator<<` предусмотрена перегрузка, которая вызывает переданную функцию над самим потоком.

## §8.5. Устройство `std::list`

`std::list<T>` обычно реализуется двусвязным списком. Каждый узел хранит объект `T` и ссылки на соседние узлы:

```text
[prev | T | next] <-> [prev | T | next] <-> [prev | T | next]
```

Если позиция уже известна по итератору, вставка и удаление выполняются за `O(1)`: нужно изменить фиксированное число связей. Но поиск позиции остаётся линейным. Выражение `list.insert(iterator, value)` работает за константное время не потому, что список быстро находит индекс, а потому, что итератор уже обозначает нужный узел.

У списка нет `operator[]`: чтобы добраться до `n`-го элемента, пришлось бы пройти предыдущие элементы за `O(n)`.

### Сторожевой узел

Реализацию упрощает фиктивный, или сторожевой, узел. В пустом списке он ссылается сам на себя:

```text
        +----------------+
        v                |
     [ root ] -----------+
```

В непустом списке `root.next` указывает на первый узел, а `root.prev` — на последний. `end()` обозначает `root`. Тогда вставка между двумя узлами не требует отдельных ветвей для пустого списка, начала и конца.

Фиктивный узел не должен содержать `T`, потому что для позиции `end()` нет элемента. Поэтому ссылки выносят в базовый тип:

```cpp
template <typename T>
class MyList {
private:
    struct BaseNode {
        BaseNode* next;
        BaseNode* prev;
    };

    struct Node : BaseNode {
        T value;

        explicit Node(const T& value) : value(value) {}
    };

    BaseNode root_{&root_, &root_};
    std::size_t size_ = 0;
};
```

`root_` хранится непосредственно внутри списка, поэтому создание пустого контейнера не требует отдельного динамического выделения узла. Обычный `Node` не должен повторно объявлять `next` и `prev`: он уже наследует их от `BaseNode`. Повторные поля образовали бы две независимые пары связей.

Итератор списка хранит указатель на `BaseNode`. Инкремент переходит к `next`, декремент — к `prev`, поэтому это bidirectional iterator.

### Стабильность позиций и операции списка

Вставка не перемещает существующие узлы, поэтому указатели, ссылки и итераторы на них сохраняются. Удаление инвалидирует только позиции, относящиеся к удалённым элементам.

Эта стабильность позволяет эффективно переносить готовые узлы между списками через `splice` без копирования или перемещения `T`. `merge` объединяет упорядоченные списки, а `sort` сортирует сам список.

Общий `std::sort` к `std::list` неприменим, поскольку требует random access iterator. Член `list::sort` использует структуру списка и работает с bidirectional iterator.

Константная вставка не означает, что список всегда быстрее вектора. Каждый узел требует служебных указателей и обычно отдельного выделения памяти, элементы разнесены по памяти, а поиск позиции линеен. У вектора вставка может перемещать элементы, зато последовательный обход обычно лучше использует кэш.

### `std::forward_list`

`std::forward_list<T>` — односвязный список. Узел хранит только ссылку на следующий элемент, поэтому итератор умеет двигаться лишь вперёд.

Из структуры следуют особенности интерфейса:

- нет `push_back` и `pop_back`, поскольку контейнер не обязан хранить указатель на последний узел;
- нет обычного `insert` перед позицией, зато есть `insert_after`;
- нет `size()`, поскольку хранение счётчика увеличило бы стоимость некоторых операций переноса диапазонов либо изменило бы минималистичную модель контейнера.

`forward_list` полезен, когда действительно нужны односвязная структура и минимальные накладные расходы на узел. Он не является автоматической заменой `vector` для обычных последовательностей.

## §8.6. Устройство `std::map`

`std::map<Key, Value>` — упорядоченный ассоциативный контейнер. Каждый уникальный ключ связан с одним значением, а обход происходит в порядке, заданном компаратором.

Основные операции имеют логарифмическую сложность:

```cpp
map.insert({key, value});
map.erase(key);
map.find(key);
map.contains(key);      // C++20
map.lower_bound(key);
map.upper_bound(key);
```

`lower_bound(key)` возвращает первый элемент, который не расположен раньше `key`, а `upper_bound(key)` — первый элемент, расположенный строго после `key` в смысле компаратора.

`at` и `operator[]` различаются поведением при отсутствии ключа:

```cpp
Value& first = map.at(key); // Бросает out_of_range, если ключа нет.
Value& second = map[key];   // Вставляет Value{} при отсутствии ключа.
```

Поэтому у `operator[]` нет константной перегрузки: операция потенциально изменяет контейнер. Кроме того, она требует, чтобы отображаемый тип можно было создать нужным способом по умолчанию.

### Сбалансированное дерево

Типичная реализация использует сбалансированное дерево поиска, часто красно-чёрное. Для каждого узла ключи левого поддерева расположены раньше его ключа, а ключи правого — позже. Балансировка ограничивает высоту дерева значением `O(log n)`, поэтому поиск, вставка и удаление остаются логарифмическими.

Конкретный цвет узла, правила поворотов и способ упаковки служебных битов стандартом не закреплены. Реализация может, например, использовать свободный бит выровненного указателя, но пользовательский код не имеет права полагаться на это представление.

Упрощённая форма узла:

```cpp
template <typename Key, typename Value>
struct MapNode {
    MapNode* left;
    MapNode* right;
    MapNode* parent;
    std::pair<const Key, Value> element;
    bool red;
};
```

Указатель на родителя нужен в том числе для движения итератора назад и вперёд без отдельного стека пути. Переход к следующему элементу либо спускается к минимальному узлу правого поддерева, либо поднимается по родителям.

Отдельный `++iterator` в худшем случае может пройти несколько уровней дерева. Однако полный упорядоченный обход каждого ребра использует ограниченное число раз, поэтому последовательный проход по `n` элементам работает за `O(n)`, а инкремент имеет амортизированную константную сложность.

### Почему ключ константный

Разыменование итератора `map` даёт объект типа:

```cpp
std::pair<const Key, Value>
```

Значение изменить можно, ключ — нельзя:

```cpp
auto iterator = map.find(key);
iterator->second = new_value; // Допустимо.
// iterator->first = new_key; // CE.
```

Положение узла выбрано на основании ключа. Если изменить ключ на месте, структура перестанет соответствовать порядку: `find` может пойти в другое поддерево и не обнаружить физически существующий элемент. Поэтому смена ключа должна происходить через контролируемые операции контейнера, а не через обычный итератор.

При обходе лучше не указывать ошибочный тип пары вручную:

```cpp
for (const auto& [key, value] : map) {
    // Нет лишней временной пары.
}
```

Запись `const std::pair<Key, Value>&` не совпадает с настоящим `pair<const Key, Value>` и может приводить к созданию временного объекта на каждой итерации.

### Требования к компаратору

`Compare` должен задавать строгий слабый порядок. Равенство ключей контейнер определяет не через `operator==`, а так:

```cpp
!compare(left, right) && !compare(right, left)
```

Компаратор обязан вести себя согласованно: в частности, `compare(x, x)` должен быть ложным, а отношение должно сохранять необходимые свойства транзитивности. Если результат зависит от случайного состояния или меняется между вызовами для тех же ключей, дерево не может поддерживать свои инварианты.

```cpp
struct BadCompare {
    bool operator()(int left, int right) const {
        return left <= right; // Ошибка: compare(x, x) возвращает true.
    }
};
```

Требование относится и к неизменности наблюдаемого порядка уже хранящихся ключей.

### Итераторы и исключения

Вставка и удаление элементов `map` не перемещают остальные узлы. Поэтому они не инвалидируют итераторы, ссылки и указатели на остальные элементы. Инвалидируются только позиции удалённого элемента.

При вставке сравнения выполняются до окончательного изменения структуры. Если компаратор или конструктор элемента выбросит исключение, контейнер должен остаться корректным. Балансировочные повороты можно выполнять после всех потенциально выбрасывающих действий, поскольку сами перестановки служебных указателей исключений не создают.

`std::set` использует ту же идею, но хранит только ключ. `std::multimap` и `std::multiset` разрешают несколько эквивалентных ключей.

## §8.7. Устройство `std::unordered_map`

`std::unordered_map<Key, Value>` хранит пары ключ–значение в хеш-таблице. В отличие от `map`, он не поддерживает упорядоченный обход, но предоставляет поиск, вставку и удаление со средней сложностью `O(1)`.

Это именно средняя, а не безусловная гарантия. Если множество ключей даёт много коллизий, операции могут потребовать `O(n)`.

### §8.7.1. Хеш-таблица

Хеш-функция преобразует ключ в целое значение:

```cpp
std::size_t hash = std::hash<Key>{}(key);
```

Затем реализация выбирает бакет, например с помощью остатка от деления:

```cpp
std::size_t bucket = hash % bucket_count;
```

Количество бакетов не обязано быть простым числом. Одни реализации используют простые размеры, другие — степени двойки и извлекают часть битов хеша. Пользовательскому коду важно не конкретное правило, а равномерное распределение результата хеш-функции.

Когда разные ключи попадают в один бакет, возникает коллизия. Коллизия не является ошибкой: контейнер обязан дополнительно сравнить ключи и различить их.

Распространены две стратегии разрешения коллизий.

#### Открытая адресация

Все элементы размещаются непосредственно в массиве таблицы. Если выбранная ячейка занята, алгоритм проверяет другие ячейки по определённой последовательности.

Для удаления недостаточно сделать ячейку обычной пустой: это могло бы преждевременно остановить поиск элемента, размещённого дальше из-за прежней коллизии. Поэтому часто требуется отдельное состояние «элемент был удалён».

#### Метод цепочек

Каждый бакет связан с последовательностью элементов, получивших соответствующий индекс. Поиск выбирает бакет, а затем сравнивает ключи внутри его цепочки.

Стандарт не требует от `unordered_map` буквально хранить отдельный `forward_list` в каждом бакете. Реализации оптимизируют расположение узлов и служебных указателей, сохраняя требуемое поведение.

### Согласованность хеша и равенства

Контейнер использует два функциональных объекта:

- `Hash` вычисляет хеш;
- `KeyEqual` определяет эквивалентность ключей.

Если `KeyEqual{}(left, right)` возвращает `true`, хеши этих ключей обязаны совпадать. Иначе контейнер может искать эквивалентный ключ в одном бакете, хотя существующий элемент лежит в другом.

Обратное не требуется: одинаковый хеш у неравных ключей является обычной коллизией.

Для пользовательского типа можно передать собственные объекты:

```cpp
struct Point {
    int x;
    int y;
};

struct PointHash {
    std::size_t operator()(const Point& point) const noexcept {
        std::size_t first = std::hash<int>{}(point.x);
        std::size_t second = std::hash<int>{}(point.y);
        return first ^ (second << 1);
    }
};

struct PointEqual {
    bool operator()(const Point& left, const Point& right) const noexcept {
        return left.x == right.x && left.y == right.y;
    }
};

std::unordered_map<Point, int, PointHash, PointEqual> values;
```

Также для пользовательского типа разрешено предоставить полную специализацию `std::hash` в `namespace std`. Добавлять в `std` произвольные функции или специализации для стандартных типов нельзя; разрешение для `std::hash` относится к специализации для пользовательского типа и требует соблюдения контракта хешера.

### §8.7.2. Типичная реализация `unordered_map`

Наивная схема — вектор отдельных односвязных списков:

```cpp
std::vector<std::forward_list<Node>> buckets;
```

Она естественно выражает метод цепочек, но усложняет единый проход по всем элементам: итератор должен знать текущий бакет и при завершении его списка искать следующий непустой бакет.

Одна из практических схем хранит все узлы в едином односвязном списке, группируя элементы одинаковых бакетов рядом. Массив бакетов хранит служебные указатели, позволяющие быстро найти начало нужной группы:

```text
бакеты: [ * ][   ][ * ][ * ]
          |         |    |
          v         v    v
список: [node] -> [node] -> [node] -> [node]
```

Узел может сохранять уже вычисленный хеш:

```cpp
template <typename Key, typename Value>
struct UnorderedMapNode {
    std::pair<const Key, Value> element;
    std::size_t hash;
    UnorderedMapNode* next;
};
```

Это позволяет не вычислять дорогой хеш повторно при некоторых внутренних операциях. Однако конкретное представление, хранение хеша и направление служебных указателей зависят от реализации.

Как и у `map`, ключ в паре константный. Изменение ключа на месте могло бы сделать сохранённый бакет и хеш неправильными.

### Коэффициент заполнения и `rehash`

Коэффициент заполнения определяется как:

```text
load_factor = size / bucket_count
```

Чем больше элементов приходится на бакет, тем длиннее в среднем поиск внутри цепочки. `max_load_factor()` задаёт порог, при превышении которого контейнер обычно увеличивает число бакетов и выполняет `rehash`.

При `rehash` узлы распределяются по новой таблице. Значения `T` при узловой реализации можно не копировать и не перемещать: достаточно пересвязать существующие узлы. Поэтому ссылки и указатели на элементы сохраняются, а итераторы инвалидируются.

`reserve(n)` подбирает число бакетов так, чтобы контейнер мог вместить как минимум `n` элементов без превышения максимального коэффициента заполнения:

```cpp
std::unordered_map<int, std::string> values;
values.reserve(1000);
```

Это резервирование количества элементов, а не прямое указание числа бакетов. Для прямого управления числом бакетов существует `rehash`.

Вызвать `rehash` может явная операция или вставка, после которой требуется рост таблицы. Поэтому итератор, сохранённый до `insert`, нельзя безусловно использовать после него: сначала нужно знать, произошёл ли rehash.

Основные правила инвалидации:

- `rehash` инвалидирует все итераторы, но не ссылки и указатели на элементы;
- вставка инвалидирует итераторы, если вызвала `rehash`;
- удаление инвалидирует только итераторы и ссылки на удалённые элементы.

`unordered_set` хранит только ключи, а `unordered_multimap` и `unordered_multiset` разрешают эквивалентные ключи. Для всех этих контейнеров качество хеш-функции и согласованность с проверкой равенства непосредственно влияют на корректность и производительность.
