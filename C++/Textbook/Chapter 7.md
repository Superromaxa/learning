# VII. Исключения

Исключение позволяет сообщить об ошибке отдельно от обычного возвращаемого значения функции. Вместо того чтобы проверять код ошибки после каждого вызова, программа может передать управление ближайшему подходящему обработчику.

Исключения не заменяют все способы обработки ошибок. Возвращаемое значение, `std::optional`, ожидаемый результат с ошибкой и исключение подходят для разных интерфейсов. Эта глава рассматривает именно встроенный механизм исключений C++.

## §7.1. Введение

В C-подобном интерфейсе функция часто возвращает специальный код:

```cpp
bool divide(int left, int right, int& result) {
    if (right == 0) {
        return false;
    }

    result = left / right;
    return true;
}
```

Вызывающий код обязан проверить `false`. Если проверку забыть, функция не может заставить программу обработать ошибку.

В C++ функция может выбросить исключение:

```cpp
int divide(int left, int right) {
    if (right == 0) {
        throw std::logic_error("division by zero");
    }

    return left / right;
}
```

После `throw` обычное выполнение функции прекращается. Инструкции после него не выполняются, а управление ищет подходящий обработчик:

```cpp
try {
    std::cout << divide(10, 0) << '\n';
    std::cout << "after division\n";
} catch (const std::logic_error& error) {
    std::cout << error.what() << '\n';
}
```

> Вывод: `division by zero`.

Строка `after division` не выполняется. Исключение покидает `divide`, затем блок `try`, после чего находится соответствующий `catch`.

### `try` и `catch`

`try` отмечает область, исключения из которой нужно обработать. Сразу за ним располагаются один или несколько обработчиков:

```cpp
try {
    operation();
} catch (const std::logic_error& error) {
    // Обработка logic_error и подходящих производных типов.
} catch (const std::exception& error) {
    // Обработка остальных стандартных исключений.
} catch (...) {
    // Обработка любого исключения.
}
```

Обработчики проверяются сверху вниз. Выполняется первый подходящий, поэтому более конкретные типы нужно располагать раньше общих.

Исключения классов обычно ловят по `const`-ссылке:

```cpp
catch (const std::exception& error)
```

Это не создаёт лишнюю копию и не срезает производную часть объекта исключения. `const` подходит, потому что обработчику обычно достаточно прочитать информацию об ошибке.

`catch (...)` не предоставляет объект и поэтому не позволяет вызвать `what()` или узнать тип напрямую. Его используют, когда нужно выполнить общее действие независимо от типа исключения.

### Где стандартная библиотека использует исключения

Некоторые операции могут выбрасывать стандартные исключения:

- обычный `new` при неудаче обычно выбрасывает `std::bad_alloc`;
- неудачный `dynamic_cast` к ссылке выбрасывает `std::bad_cast`;
- `typeid(*pointer)` для нулевого указателя на полиморфный тип выбрасывает `std::bad_typeid`;
- контейнерные операции вроде `at` могут выбрасывать `std::out_of_range`;
- выражение `throw` создаёт и выбрасывает указанный объект исключения.

Если подходящего обработчика не найдено, вызывается `std::terminate`. По умолчанию программа после этого аварийно завершается.

## §7.2. Ошибка во время выполнения и исключение

Не каждая проблема, возникшая во время работы программы, является исключением C++.

`catch` обрабатывает только исключения, выброшенные механизмом языка. Он не обязан ловить:

- обращение за границу встроенного массива;
- разыменование `nullptr`;
- использование уже освобождённой памяти;
- переполнение стека;
- знаковое целочисленное переполнение;
- целочисленное деление на ноль;
- сигнал операционной системы или аварийное завершение процесса.

Многие такие операции приводят к UB. Программа может получить segmentation fault или другой системный сигнал, но это лишь одно из возможных проявлений. Стандарт C++ не превращает UB в объект, который можно надёжно перехватить через `catch`.

```cpp
try {
    int* pointer = nullptr;
    *pointer = 1; // UB
} catch (...) {
    // Нет гарантии, что управление попадёт сюда.
}
```

Некоторые платформы предоставляют собственные механизмы сигналов или системных исключений, но их связь с исключениями C++ не является переносимой частью языка.

Термин floating-point exception в сообщениях операционной системы исторически может обозначать арифметический сигнал, включая целочисленное деление на ноль. Обычное деление `double` на ноль на распространённых IEC 60559-реализациях часто даёт бесконечность или NaN, а не C++-исключение.

### Иерархия стандартных исключений

`std::exception` — базовый класс многих стандартных исключений. Он содержит виртуальный деструктор и виртуальную функцию `what()`:

```cpp
try {
    operation();
} catch (const std::exception& error) {
    std::cerr << error.what() << '\n';
}
```

Распространённые стандартные типы:

- `std::logic_error` — семейство ошибок, связанных с нарушением ожидаемых условий интерфейса;
- `std::runtime_error` — семейство ошибок, обнаруживаемых во время выполнения;
- `std::bad_alloc` — неудачное выделение памяти;
- `std::bad_cast` — неудачный `dynamic_cast` к ссылке;
- `std::bad_typeid` — специальный неудачный случай `typeid`;
- `std::out_of_range` — индекс или позиция за допустимой границей.

Пользовательские исключения тоже часто наследуют от `std::exception` или одного из её потомков, чтобы общий обработчик мог получить сообщение через `what()`.

### `abort` и `terminate`

`std::abort()` немедленно инициирует аварийное завершение и не является исключением.

Неудачный `assert(condition)` обычно вызывает `std::abort`, если проверки `assert` не отключены макросом `NDEBUG`.

`std::terminate()` вызывается, в частности, когда:

- исключение покинуло `noexcept`-функцию;
- подходящий обработчик для исключения не найден;
- во время раскрутки стека из деструктора вышло второе исключение;
- нарушены некоторые другие правила механизма исключений.

Вызов чисто виртуальной функции в недопустимом состоянии является UB. Реализация часто завершает программу через служебный обработчик, но стандарт не обязан сводить этот случай именно к `std::terminate`.

## §7.3. Обработка исключений

### §7.3.1. Объект исключения и раскрутка стека

При `throw expression` создаётся отдельный объект исключения. Его время жизни не зависит от локального объекта, из которого он был создан:

```cpp
struct A {
    A() {
        std::cout << "A ";
    }

    A(const A&) {
        std::cout << "copy ";
    }

    ~A() {
        std::cout << "~A ";
    }
};

void f() {
    A local;
    throw local;
}
```

```cpp
try {
    f();
} catch (const A&) {
    std::cout << "caught ";
}
```

Локальный `local` не может оставаться на стеке функции `f`, потому что `f` завершается. Выражение `throw local` инициализирует отдельный объект исключения, который продолжает существовать во время обработки.

Компилятор может устранить копирование или использовать перемещение, поэтому точное количество вызовов копирующего конструктора нельзя определять только по исходному тексту. Размещение объекта исключения тоже является деталью реализации: стандарт не требует, чтобы он создавался обычным `new` в динамической памяти.

После создания исключения начинается **раскрутка стека**. Для полностью созданных локальных объектов в покидаемых областях вызываются деструкторы:

1. создаётся `local`;
2. создаётся объект исключения;
3. уничтожается `local` при выходе из `f`;
4. выполняется подходящий `catch`;
5. объект исключения уничтожается, когда обработка завершена и он больше не нужен.

Из-за разрешённого устранения копирования конкретная последовательность печати конструктора `copy` может отличаться, но уничтожение полностью созданных автоматических объектов при раскрутке является ключевой гарантией.

### Перехват по значению и по ссылке

```cpp
catch (A value)
```

Перехват по значению создаёт параметр обработчика из объекта исключения. Это может потребовать дополнительного копирования и для иерархии классов способно срезать производную часть.

```cpp
catch (const A& value)
```

Перехват по ссылке обращается к самому объекту исключения без дополнительной копии. Поэтому для классов обычно используется `const A&`.

### Повторный выброс

Внутри обработчика запись `throw;` повторно выбрасывает текущее исключение:

```cpp
try {
    try {
        operation();
    } catch (const std::exception& error) {
        std::cerr << error.what() << '\n';
        throw;
    }
} catch (const std::exception& error) {
    // Обработка на внешнем уровне.
}
```

После `throw;` оставшиеся обработчики того же `try` не рассматриваются: исключение продолжает поиск во внешних областях.

Важно отличать повторный выброс от нового:

```cpp
throw;       // тот же объект исключения
throw error; // новый объект, возможны копирование и срезка
```

Запись `throw;` допустима только во время обработки активного исключения. Вне обработчика она приводит к `std::terminate`.

### Необработанное исключение

Если обработчик не найден, вызывается `std::terminate`. Стандарт допускает, что раскрутка стека до этого момента может быть выполнена полностью или не выполнена. Поэтому нельзя рассчитывать, что локальные деструкторы обязательно сработают после необработанного исключения.

Именно обработанное исключение гарантирует нормальную раскрутку до найденного обработчика. Для освобождения критических внешних ресурсов всё равно нельзя полагаться на завершение процесса — состояние нужно сохранять и закрывать на контролируемых границах.

Реализации должны уметь выбросить `std::bad_alloc`, даже когда обычное выделение памяти не удалось. Конкретный механизм — зарезервированная память, специальное статическое состояние или другой подход — является деталью реализации, а не гарантированной схемой языка.

### §7.3.2. Соответствие типов обработчиков

При поиске `catch` не выполняется обычный набор числовых преобразований:

```cpp
try {
    throw 1;
} catch (double) {
    std::cout << "double\n";
} catch (long long) {
    std::cout << "long long\n";
} catch (...) {
    std::cout << "other\n";
}
```

> Вывод: `other`.

Выброшен `int`. Он не преобразуется ни в `double`, ни в `long long` ради выбора обработчика.

Класс можно поймать обработчиком его однозначной открытой базы:

```cpp
struct Mother {
    virtual ~Mother() = default;
};

struct Son : Mother {};

try {
    throw Son{};
} catch (const Mother&) {
    std::cout << "Mother\n";
} catch (const Son&) {
    std::cout << "Son\n";
}
```

> Вывод: `Mother`.

Обработчики проверяются сверху вниз. `Son` подходит к `const Mother&`, поэтому более поздний `catch (const Son&)` уже недостижим для такого исключения. Компилятор может предупредить об этом.

Правильный порядок — от производного к базовому:

```cpp
try {
    throw Son{};
} catch (const Son&) {
    std::cout << "Son\n";
} catch (const Mother&) {
    std::cout << "Mother\n";
}
```

При перехвате базы по значению производная часть параметра обработчика срезается:

```cpp
catch (Mother value)
```

Объект исключения остаётся `Son`, но локальный параметр `value` является отдельным `Mother`. Перехват по ссылке сохраняет динамический тип и позволяет виртуальным функциям работать полиморфно.

### Недоступная или неоднозначная база

Для сопоставления обработчика базовый класс должен быть открытой и однозначной базой.

```cpp
struct Mother {};
struct Son : private Mother {};

try {
    throw Son{};
} catch (const Mother&) {
    std::cout << "Mother\n";
} catch (const Son&) {
    std::cout << "Son\n";
}
```

> Вывод: `Son`.

Приватная база не подходит для обработчика `Mother`, даже если исключение было выброшено из контекста, имеющего доступ к преобразованию.

Неоднозначная повторяющаяся база также не подходит:

```cpp
struct Granny {};
struct Mother : Granny {};
struct Father : Granny {};
struct Son : Mother, Father {};

try {
    throw Son{};
} catch (const Granny&) {
    std::cout << "Granny\n";
} catch (const Son&) {
    std::cout << "Son\n";
}
```

> Вывод: `Son`.

У `Son` два подобъекта `Granny`, поэтому нельзя выбрать единственную базовую ссылку.

При виртуальном открытом наследовании общий подобъект один:

```cpp
struct Mother : virtual Granny {};
struct Father : virtual Granny {};
struct Son : Mother, Father {};
```

Теперь `catch (const Granny&)`, расположенный раньше `catch (const Son&)`, подходит однозначно.

`catch (...)` подходит к любому типу и поэтому должен стоять последним.

## §7.4. RAII

Исключение может покинуть функцию между получением ресурса и ручным освобождением:

```cpp
void check(int value) {
    if (value == 0) {
        throw std::runtime_error("zero value");
    }
}

void f(int value) {
    int* pointer = new int(value);
    check(*pointer);
    delete pointer;
}
```

При `f(0)` функция `check` выбросит исключение. Управление не вернётся к строке `delete pointer`, поэтому память утечёт.

RAII — Resource Acquisition Is Initialization — связывает владение ресурсом со временем жизни объекта. Ресурс получается в конструкторе, а освобождается в деструкторе:

```cpp
class IntOwner {
    int* pointer;

public:
    explicit IntOwner(int* pointer)
        : pointer(pointer) {}

    IntOwner(const IntOwner&) = delete;
    IntOwner& operator=(const IntOwner&) = delete;

    ~IntOwner() {
        delete pointer;
    }

    int& operator*() {
        return *pointer;
    }
};
```

```cpp
void f(int value) {
    IntOwner owner(new int(value));
    check(*owner);
}
```

Если `check` выбрасывает исключение, раскрутка стека уничтожает `owner`, а его деструктор выполняет `delete`. Ручная строка очистки после потенциально опасного вызова больше не нужна.

Копирование запрещено, потому что простая копия сырого указателя создала бы двух владельцев. Оба деструктора попытались бы удалить один объект, что привело бы к UB.

Стандартный класс для уникального владения динамическим объектом — `std::unique_ptr`:

```cpp
void f(int value) {
    auto pointer = std::make_unique<int>(value);
    check(*pointer);
}
```

`std::unique_ptr` нельзя копировать, но можно перемещать, то есть передавать владение. При уничтожении он автоматически освобождает объект.

RAII применяется не только к памяти: тем же способом время жизни объекта можно связать с файлом, блокировкой или другим ресурсом. Главное правило — полностью созданный владелец должен освободить ресурс в деструкторе.

## §7.5. Исключения в конструкторах и деструкторах

### Исключение из конструктора

```cpp
struct A {
    A() {
        std::cout << "A ";
    }

    ~A() {
        std::cout << "~A ";
    }
};

struct S {
    A member;

    explicit S(int value) {
        std::cout << "S ";

        if (value == 0) {
            throw std::runtime_error("construction failed");
        }
    }

    ~S() {
        std::cout << "~S ";
    }
};
```

```cpp
try {
    S object(0);
} catch (...) {
}
```

> Вывод: `A S ~A`.

Полный объект `S` не был создан, поэтому `S::~S` не вызывается. Но поле `member` успело полностью сконструироваться, поэтому оно автоматически уничтожается.

Если исключение возникает при создании нескольких полей, уничтожаются только уже завершившие конструирование поля — в обратном порядке. Тот же принцип действует для базовых подобъектов.

Поэтому ресурс нужно сразу помещать в RAII-поле. Если хранить сырой указатель и рассчитывать освободить его в `S::~S`, деструктор не поможет при незавершённом конструкторе `S`.

### Function-try-block конструктора

Обычный `try` в теле конструктора не охватывает список инициализации. Function-try-block начинает обработку до него:

```cpp
struct A {
    explicit A(int value) {
        std::cout << "A(" << value << ") ";

        if (value == 0) {
            throw std::runtime_error("A failed");
        }
    }

    ~A() {
        std::cout << "~A ";
    }
};

struct S {
    A first;
    A second;

    explicit S(int value)
    try
        : first(1), second(value) {
        std::cout << "S ";
    } catch (const std::exception& error) {
        std::cout << "caught: " << error.what() << ' ';
    }
};
```

```cpp
try {
    S object(0);
} catch (...) {
    std::cout << "outer catch";
}
```

Последовательность:

1. `first` успешно создаётся.
2. Конструктор `second` выбрасывает исключение.
3. Уже созданный `first` уничтожается.
4. Выполняется обработчик function-try-block.
5. После завершения обработчика конструктора исходное исключение автоматически выбрасывается снова.
6. Его ловит внешний `catch`.

Обработчик конструктора не может объявить объект успешно созданным. К моменту входа в него полностью созданные базы и поля уже уничтожены, поэтому обращаться к нестатическим членам такого объекта нельзя.

Function-try-block доступен и обычной функции:

```cpp
void f() try {
    operation();
} catch (const std::exception& error) {
    std::cerr << error.what() << '\n';
}
```

Для обычной функции завершение обработчика не обязано повторно выбрасывать исключение. Автоматический повторный выброс при достижении конца обработчика относится к function-try-block конструктора и деструктора.

### Исключения из деструктора

Начиная с C++11 неявная спецификация деструктора обычно является `noexcept(true)`, если деструкторы его баз и полей также не допускают исключений. Если исключение покидает такой деструктор, вызывается `std::terminate`.

```cpp
struct Dangerous {
    ~Dangerous() noexcept(false) {
        throw std::runtime_error("destructor failed");
    }
};
```

`noexcept(false)` позволяет исключению выйти из деструктора, если деструктор вызван в обычной ситуации. Но если уже выполняется раскрутка стека из-за другого исключения, второе исключение приводит к `std::terminate`:

```cpp
void f() {
    Dangerous object;
    throw std::runtime_error("first exception");
} // ~Dangerous выбрасывает второе исключение -> terminate
```

Именно поэтому деструкторы должны самостоятельно обрабатывать ошибки и не выпускать исключения наружу.

До C++17 для такой проверки использовали `std::uncaught_exception()`. В C++17 появилась замена `std::uncaught_exceptions()`, которая возвращает количество активных необработанных исключений. Старая функция была признана устаревшей в C++17 и удалена в C++20.

Счётчик можно сравнить со значением, сохранённым при создании объекта, чтобы понять, началась ли новая раскрутка. Однако строить корректность обычного деструктора на таком различии следует осторожно.

## §7.6. Exception safety

Исключение может прервать функцию в любой операции, которая способна его выбросить. Поэтому важно заранее определить, в каком состоянии останутся объекты и ресурсы.

Основные уровни гарантий:

1. **No-throw guarantee.** Операция гарантированно не выпускает исключений.
2. **Strong exception guarantee.** При исключении наблюдаемое состояние остаётся таким, каким было до вызова: операция либо полностью успешна, либо не оказывает эффекта.
3. **Basic exception guarantee.** После исключения объекты остаются валидными, инварианты соблюдены и ресурсы не потеряны, но значения могут измениться.
4. **No guarantee.** После исключения нельзя рассчитывать даже на сохранение инвариантов.

Basic guarantee иногда называют слабой гарантией. «Валидное состояние» не обязательно означает прежнее содержимое: объект можно уничтожить, присвоить ему новое значение или вызвать разрешённые операции, но конкретное значение может быть не определено интерфейсом.

RAII является основой basic guarantee: локальные владельцы автоматически освобождают ресурсы при раскрутке.

Strong guarantee часто строят по схеме «сначала подготовить всё отдельно, затем выполнить небросающий обмен или фиксацию»:

```cpp
String& String::operator=(const String& other) {
    String copy(other); // может выбросить, текущий объект ещё не изменён
    swap(copy);         // должен не выбрасывать
    return *this;
}
```

Если копирование не удалось, текущая строка не изменилась. После успешного `swap` операция завершена.

### Спецификатор `noexcept`

```cpp
void close() noexcept {
    // Функция обещает не выпускать исключений.
}
```

`noexcept` не запрещает выполнить `throw` синтаксически. Если исключение всё же попытается покинуть функцию, вызывается `std::terminate`:

```cpp
void f() noexcept {
    throw 1; // при выполнении -> terminate
}
```

Функция может бросить и перехватить исключение внутри себя, не нарушив обещание:

```cpp
void f() noexcept {
    try {
        operation();
    } catch (...) {
        // Исключение не выходит наружу.
    }
}
```

Спецификатор может зависеть от константного выражения:

```cpp
template <typename T>
void swap_values(T& first, T& second)
    noexcept(noexcept(first.swap(second))) {
    first.swap(second);
}
```

Здесь используются две разные конструкции:

- внешний `noexcept(...)` — спецификатор функции;
- внутренний `noexcept(expression)` — оператор, возвращающий `true`, если выражение объявлено небросающим.

Функция `swap_values` обещает не выпускать исключения ровно тогда, когда вызов `first.swap(second)` также является небросающим.

Нельзя объявлять `noexcept` только ради оптимизации, если вызываемые операции действительно способны выбросить исключение. Нарушение обещания не превращает ошибку в обычный `catch`, а завершает программу.

Деструкторы и многие операции освобождения ресурсов проектируют небросающими. Но нельзя утверждать, что любой `operator[]` или любая простая на вид функция автоматически `noexcept`: спецификация зависит от конкретной реализации и вызываемых операций.
