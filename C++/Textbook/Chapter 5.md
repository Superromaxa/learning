    # V. Полиморфизм

Полиморфизм позволяет работать с объектами разных производных типов через общий интерфейс базового класса. Один и тот же вызов может выполнять разный код в зависимости от фактического типа объекта.

В C++ это поведение обычно строится на виртуальных функциях, ссылках или указателях на базовый класс и динамической диспетчеризации.

## §5.1. Виртуальные функции

Рассмотрим обычную и виртуальную функции:

```cpp
struct Base {
    void f() const {
        std::cout << "Base::f\n";
    }

    virtual void g() const {
        std::cout << "Base::g\n";
    }
};

struct Derived : Base {
    void f() const {
        std::cout << "Derived::f\n";
    }

    void g() const override {
        std::cout << "Derived::g\n";
    }
};
```

```cpp
Derived derived;
Base& base = derived;

base.f();
base.g();
```

> Вывод:
>
> ```text
> Base::f
> Derived::g
> ```

Выражение `base` имеет статический тип `Base&`, но обозначает объект фактического типа `Derived`.

- Для невиртуальной `f` функция выбирается по статическому типу выражения, поэтому вызывается `Base::f`.
- Для виртуальной `g` во время выполнения определяется финальный переопределитель для фактического объекта, поэтому вызывается `Derived::g`.

### Статический и динамический тип

**Статический тип** известен компилятору из текста программы. В примере это `Base`.

**Динамический тип** описывает наиболее производный объект, который действительно находится по ссылке или указателю. В примере это `Derived`.

Динамический тип важен только там, где язык требует динамического поведения. Обычный доступ к невиртуальным членам, разрешение перегрузки и проверка доступа в основном опираются на статическую информацию.

Виртуальный вызов работает через ссылку или указатель:

```cpp
Base* pointer = &derived;
pointer->g(); // Derived::g
```

Если функция вызывается через объект с известным производным типом, смысл остаётся тем же, но компилятор часто заранее знает конечную функцию и устраняет косвенный вызов:

```cpp
derived.g(); // Derived::g
```

Такая оптимизация называется девиртуализацией. Она не меняет правил языка.

### Переопределение

Функция производного класса переопределяет виртуальную функцию базы, если совпадают необходимые части объявления: имя, список параметров, `const`/`volatile`-квалификация и ref-квалификаторы. Возвращаемый тип обычно должен совпадать, кроме разрешённых ковариантных возвращаемых типов для указателей и ссылок на классы.

```cpp
struct Base {
    virtual void process(int) const;
};

struct Derived : Base {
    void process(int) const override;
};
```

Ключевое слово `virtual` достаточно написать в базовом объявлении. Во всех производных классах соответствующая функция остаётся виртуальной автоматически:

```cpp
struct FurtherDerived : Derived {
    void process(int) const override;
};
```

Даже если в `Derived` и `FurtherDerived` убрать слово `virtual`, поведение не изменится. `override` рекомендуется оставлять как проверку намерения.

Класс, имеющий хотя бы одну виртуальную функцию — собственную или унаследованную, — называется полиморфным.

### Ковариантный возвращаемый тип

Переопределитель может возвращать указатель или ссылку на более конкретный класс:

```cpp
struct Base {
    virtual Base* clone() const;
};

struct Derived : Base {
    Derived* clone() const override;
};
```

`Derived*` является ковариантным по отношению к `Base*`. Для обычных значений правило не работает:

```cpp
Derived clone() const override; // не ковариантный возврат по значению
```

### Виртуальный деструктор

Если объект предполагается удалять через указатель на базовый класс, деструктор базы должен быть виртуальным:

```cpp
struct Base {
    virtual ~Base() = default;
};

struct Derived : Base {
    std::vector<int> data;

    ~Derived() {
        std::cout << "~Derived\n";
    }
};

Base* pointer = new Derived;
delete pointer;
```

Сначала вызывается `Derived::~Derived`, затем `Base::~Base`. Полный производный объект уничтожается корректно.

Если деструктор базы невиртуальный, `delete` через `Base*`, указывающий на производный объект, приводит к UB.

```cpp
struct Base {
    ~Base() = default; // невиртуальный
};

Base* pointer = new Derived;
delete pointer; // UB
```

У полиморфного интерфейса обычно объявляют `virtual ~Base() = default`. Альтернативный дизайн — сделать невиртуальный деструктор `protected`, если удаление через базовый указатель принципиально запрещено:

```cpp
class Base {
protected:
    ~Base() = default;
};
```

Тогда внешний код не сможет написать `delete base_pointer`, а конкретные производные объекты по-прежнему можно уничтожать через их собственный тип.

## §5.2. Переопределение, `override` и `final`

### Несовпадение квалификаторов

Незаметное отличие в сигнатуре создаёт новую функцию вместо переопределения:

```cpp
struct Base {
    virtual void f() const {
        std::cout << "Base::f\n";
    }
};

struct Derived : Base {
    void f() { // нет const, поэтому это другая функция
        std::cout << "Derived::f\n";
    }
};
```

```cpp
Derived derived;
Base& base = derived;

base.f(); // Base::f
```

Компилятор считает объявления разными: функция `Derived::f()` не переопределяет `Base::f() const`, а скрывает её имя в области `Derived`.

`override` превращает такую ошибку в явную диагностику:

```cpp
struct Derived : Base {
    void f() override {} // ошибка: ничего не переопределяет
};
```

Правильная версия:

```cpp
struct Derived : Base {
    void f() const override {
        std::cout << "Derived::f\n";
    }
};
```

`override` не включает виртуальность и не меняет диспетчеризацию. Он требует, чтобы функция действительно переопределяла виртуальную функцию базы. Такая проверка защищает от опечаток, изменения сигнатуры базы и забытых квалификаторов.

На практике переопределители обычно помечают `override`, а повторять `virtual` необязательно:

```cpp
void f() const override;
```

### `final` для функции и класса

`final` запрещает дальнейшее переопределение виртуальной функции:

```cpp
struct Derived : Base {
    void f() const final;
};

struct Last : Derived {
    void f() const override; // ошибка
};
```

Производный класс может объявить одноимённую функцию с другой сигнатурой, но это будет отдельная перегрузка или скрывающее объявление, а не переопределение `final`-функции.

Класс тоже можно закрыть для наследования:

```cpp
class Complete final : public Base {};

class More : public Complete {}; // ошибка
```

`override` и `final` являются контекстными ключевыми словами. В подходящих местах они имеют специальный смысл, но в других контекстах могут использоваться как идентификаторы:

```cpp
int override = 0;
```

Так писать разрешено, хотя подобные имена могут ухудшать читаемость.

### Доступ и виртуальный вызов

Проверка доступа выполняется для функции, найденной по статическому типу выражения. Доступ финального переопределителя отдельно в месте вызова не проверяется:

```cpp
struct Base {
    virtual void f() const {
        std::cout << "Base\n";
    }
};

struct Derived : Base {
private:
    void f() const override {
        std::cout << "Derived\n";
    }
};

Derived derived;
Base& base = derived;
base.f();
```

> Вывод: `Derived`.

Вызов разрешён, потому что `Base::f` открыт. После этого виртуальная диспетчеризация выбирает `Derived::f`, даже если она закрыта в `Derived`.

Но прямой вызов через статический тип `Derived` запрещён:

```cpp
derived.f(); // ошибка доступа
```

Компилятор проверяет доступ, но по правилам использует объявление, выбранное через статический тип.

Если `Base::f` была бы `private`, обычный внешний вызов `base.f()` не скомпилировался бы, даже если переопределитель `Derived::f` открыт.

### Один переопределитель для нескольких баз

Одна функция производного класса может переопределить виртуальные функции из нескольких ветвей:

```cpp
struct Mother {
    virtual void f() {
        std::cout << "Mother\n";
    }
};

struct Father {
    virtual void f() {
        std::cout << "Father\n";
    }
};

struct Child : Mother, Father {
    void f() override {
        std::cout << "Child\n";
    }
};
```

```cpp
Child child;

Mother& mother = child;
Father& father = child;

mother.f(); // Child::f
father.f(); // Child::f
```

`Child::f` является финальным переопределителем для обеих функций. Это возможно, потому что их объявления совместимы для переопределения.

## §5.3. Абстрактные классы и чисто виртуальные функции

Иногда базовый класс должен задать обязательную операцию, но не может предоставить осмысленную общую реализацию. Такую функцию объявляют чисто виртуальной:

```cpp
struct Shape {
    virtual double area() const = 0;
    virtual ~Shape() = default;
};
```

Запись `= 0` не присваивает функции число. Это специальный синтаксис pure-specifier.

Класс, у которого есть хотя бы одна чисто виртуальная функция без конкретного финального переопределителя, является абстрактным. Создать самостоятельный объект такого класса нельзя:

```cpp
Shape shape; // ошибка компиляции
```

Но можно использовать указатели и ссылки:

```cpp
void print_area(const Shape& shape) {
    std::cout << shape.area() << '\n';
}
```

Конкретные классы реализуют интерфейс:

```cpp
struct Square : Shape {
    double side;

    explicit Square(double side)
        : side(side) {}

    double area() const override {
        return side * side;
    }
};

struct Circle : Shape {
    double radius;

    explicit Circle(double radius)
        : radius(radius) {}

    double area() const override {
        constexpr double pi = 3.14159265358979323846;
        return pi * radius * radius;
    }
};
```

```cpp
Square square{2.0};
Shape& shape = square;

std::cout << shape.area() << '\n';
```

> Вывод: `4`.

Коллекцию разнородных объектов удобно хранить через владеющие указатели:

```cpp
std::vector<std::unique_ptr<Shape>> shapes;

shapes.push_back(std::make_unique<Square>(2.0));
shapes.push_back(std::make_unique<Circle>(1.0));

for (const auto& shape : shapes) {
    std::cout << shape->area() << '\n';
}
```

`std::unique_ptr` автоматически удалит объекты через виртуальный деструктор `Shape`. Вариант с `new` и необработанным `Shape*` потребовал бы вручную удалить каждый элемент и легко привёл бы к утечке при исключении или раннем выходе.

### Определение чисто виртуальной функции

Чисто виртуальная функция может иметь определение, но класс всё равно остаётся абстрактным:

```cpp
struct Shape {
    virtual double area() const = 0;
};

double Shape::area() const {
    return 0.0;
}
```

Обычный виртуальный вызов по-прежнему требует конкретного финального переопределителя. Реализацию базы можно вызвать квалифицированно из производного класса:

```cpp
struct UnitShape : Shape {
    double area() const override {
        return Shape::area() + 1.0;
    }
};
```

Квалифицированный вызов `Shape::area()` подавляет виртуальную диспетчеризацию и выбирает конкретное определение.

Чисто виртуальный деструктор тоже обязан иметь определение:

```cpp
struct Interface {
    virtual ~Interface() = 0;
};

Interface::~Interface() = default;
```

Сам `Interface` остаётся абстрактным, но при уничтожении производного объекта базовая часть всё равно должна быть уничтожена, поэтому линкеру требуется тело деструктора.

### Статический и динамический полиморфизм

**Статический полиморфизм** разрешается во время компиляции. К нему относят перегрузку функций и, например, шаблоны, о которых можно узнать далее.

**Динамический полиморфизм** выбирает поведение по динамическому типу во время выполнения. Виртуальные функции — основной встроенный механизм такого полиморфизма.

Оба подхода позволяют использовать общий интерфейс, но отличаются стоимостью, возможностью хранить разнородные объекты и моментом выбора реализации.

## §5.4. RTTI и `dynamic_cast`

RTTI — runtime type information — предоставляет информацию о динамическом типе полиморфного объекта. К основным языковым средствам RTTI относятся `dynamic_cast` и `typeid`.

### Проверяемое преобразование вниз

```cpp
struct Base {
    virtual ~Base() = default;
};

struct Derived : Base {
    int value = 42;
};

Derived object;
Base* base = &object;

Derived* derived = dynamic_cast<Derived*>(base);
```

Во время выполнения `dynamic_cast` проверяет, что объект действительно содержит подходящий подобъект `Derived`. Здесь проверка успешна, поэтому `derived` указывает на `object`.

Если преобразование указателя невозможно, возвращается `nullptr`:

```cpp
Base plain_base;
Base* base = &plain_base;

Derived* derived = dynamic_cast<Derived*>(base);

if (derived == nullptr) {
    std::cout << "not a Derived\n";
}
```

Для ссылочного преобразования нулевого результата быть не может, поэтому при неудаче бросается `std::bad_cast` из `<typeinfo>`:

```cpp
try {
    Derived& derived = dynamic_cast<Derived&>(base_reference);
} catch (const std::bad_cast& error) {
    std::cout << error.what() << '\n';
}
```

Проверяемое преобразование вниз или вбок требует, чтобы исходный статический тип был полиморфным. Наличие хотя бы одной виртуальной функции предоставляет реализации способ узнать динамический тип.

Восходящее преобразование к однозначной доступной базе не нуждается в RTTI и обычно выполняется обычным неявным преобразованием. `dynamic_cast` синтаксически может использоваться и для некоторых таких преобразований, но практической проверки там не требуется.

### Боковое преобразование

`dynamic_cast` умеет переходить между разными базовыми подобъектами одного наиболее производного объекта:

```cpp
struct Mother {
    virtual ~Mother() = default;
};

struct Father {
    virtual ~Father() = default;
};

struct Child : Mother, Father {};

Child child;
Mother* mother = &child;

Father* father = dynamic_cast<Father*>(mother);
```

`father` указывает на подобъект `Father` внутри того же `Child`. Реализация учитывает фактический тип и корректирует адрес. Если объект, доступный через `mother`, не содержит подходящего `Father`, результат будет `nullptr`.

Доступность и однозначность наследования по-прежнему имеют значение. RTTI не предназначено для обхода `private` или неоднозначных отношений.

### Преобразование к `void*`

От указателя на полиморфный подобъект можно получить адрес наиболее производного объекта:

```cpp
Mother* mother = &child;
void* complete_object = dynamic_cast<void*>(mother);
```

Результат указывает на начало полного объекта `Child`, не обязательно на начало подобъекта `Mother`. Это отличается от обычного `static_cast<void*>(mother)`, который сохраняет адрес именно текущего подобъекта.

### `typeid`

Оператор `typeid` возвращает ссылку на объект `std::type_info`:

```cpp
const std::type_info& info = typeid(object);
```

Для выражения полиморфного типа учитывается динамический тип:

```cpp
Derived object;
Base& base = object;

std::cout << (typeid(base) == typeid(Derived)) << '\n';
```

> Вывод: `1`.

Для неполиморфного выражения используется статический тип:

```cpp
struct PlainBase {};
struct PlainDerived : PlainBase {};

PlainDerived object;
PlainBase& base = object;

// typeid(base) описывает PlainBase, а не PlainDerived
```

`std::type_info::name()` возвращает строку, выбранную реализацией. Она может быть сокращённой или закодированной и не обязана совпадать с исходным написанием типа. Для логики программы лучше сравнивать `type_info`, использовать `std::type_index` или строить явный интерфейс, а не разбирать `name()`.

Если разыменовать нулевой указатель в операнде `typeid` полиморфного типа, бросается `std::bad_typeid`:

```cpp
Base* pointer = nullptr;

try {
    const std::type_info& info = typeid(*pointer);
} catch (const std::bad_typeid&) {
    // Нулевой полиморфный объект.
}
```

Для многих других операндов `typeid` не вычисляет выражение, но полиморфный glvalue является важным исключением: объект нужно исследовать во время выполнения.

Частые проверки точного типа могут означать, что виртуальный интерфейс спроектирован недостаточно хорошо. Если каждый новый наследник требует добавить ещё один `typeid` или `dynamic_cast`, иногда лучше выразить различающееся поведение виртуальной функцией.

## §5.5. Представление полиморфных объектов

Стандарт C++ описывает результат виртуального вызова, но не требует использовать виртуальные таблицы, хранить указатель в начале объекта или выбирать конкретный размер служебных данных.

Большинство распространённых ABI реализуют виртуальные функции через:

- **vtable** — таблицу адресов виртуальных функций и служебной информации для конкретного типа;
- **vptr** — скрытый указатель из объекта или подобъекта на подходящую таблицу.

Эта модель полезна для понимания стоимости и отладки, но является моделью реализации, а не переносимой гарантией языка.

### Типичная схема

```cpp
struct Base {
    virtual void f() {}
    void ordinary() {}
    int x = 0;
};

struct Derived : Base {
    void f() override {}
    virtual void g() {}
    int y = 1;
};
```

Упрощённая реализация может выглядеть так:

```text
объект Base:    [vptr Base][x][padding]
объект Derived: [vptr Derived][x][y]

vtable Base:    [служебные данные][&Base::f]
vtable Derived: [служебные данные][&Derived::f][&Derived::g]
```

При вызове `base_pointer->f()` программа в типичной реализации:

1. читает скрытый указатель из базового подобъекта;
2. выбирает ячейку, соответствующую `f`;
3. вызывает найденную функцию с корректным `this`.

Обычная функция `ordinary` не требует ячейки для динамического выбора. Её машинный код также не хранится внутри каждого объекта.

На распространённой 64-битной ABI один `vptr` занимает 8 байт, поэтому пустой полиморфный объект часто имеет размер не меньше 8. Но стандарт не обещает ни наличие ровно одного указателя, ни его размер, ни положение в начале объекта.

В таблице могут находиться RTTI, смещения, несколько вариантов деструктора и другие ABI-зависимые записи. Порядок ячеек тоже не является частью стандарта C++.

### Девиртуализация

Виртуальная семантика не означает, что каждый вызов обязательно выполняет чтение таблицы. Если компилятор доказывает динамический тип, он может вызвать функцию напрямую и даже встроить её тело:

```cpp
Derived object;
object.f();
```

`final`, локальная видимость класса, link-time optimization и анализ потока данных помогают такой оптимизации. Поэтому стоимость виртуального вызова нельзя оценивать только по исходному слову `virtual`: нужно учитывать конкретный код и оптимизацию.

## §5.6. Множественное и виртуальное наследование в памяти

При множественном наследовании один наиболее производный объект содержит несколько базовых подобъектов. Каждый полиморфный подобъект может требовать собственный способ виртуальной диспетчеризации.

```cpp
struct Mother {
    int mother_value = 0;
    virtual void f() {}
};

struct Father {
    int father_value = 0;
    virtual void g() {}
};

struct Child : Mother, Father {
    int child_value = 0;

    void f() override {}
    void g() override {}
};
```

В каждом базовом полиморфном подобъекте находится свой `vptr`. Объект `Child` занимает 32 байта и располагается в памяти так:

```text
          ┌──────┬─────┬─────┬──────┬─────┬─────┐
Child:    │ VM   │  M  │ pad │ VF   │  F  │  C  │
          └──────┴─────┴─────┴──────┴─────┴─────┘
размер:      8      4     4      8      4     4
смещение:    0      8    12     16     24    28
```

Здесь:

- `VM` — `vptr` подобъекта `Mother`;
- `M` — поле `mother_value`;
- `VF` — `vptr` подобъекта `Father`;
- `F` — поле `father_value`;
- `C` — поле `child_value`.

Подобъект `Mother` начинается вместе со всем объектом `Child`, а подобъект `Father` — со смещения 16 байт. Поэтому указатели `Mother*` и `Father*`, полученные из одного `Child*`, содержат разные адреса.

### Корректировка `this`

```cpp
Child child;
Father* father = &child;
father->g();
```

`father` указывает не на начало полного объекта, а на подобъект `Father`, находящийся со смещения 16 байт. Однако `Child::g` должна получить указатель на начало `Child`, иначе через `this` нельзя будет правильно обратиться к `child_value`.

Перед входом в `Child::g` значение `this` сдвигается на 16 байт назад:

```text
вызов через Father
        ↓
корректировка this от Father к Child
        ↓
Child::g
```

Для этого в виртуальной таблице подобъекта `Father` хранится информация, необходимая для выбора `Child::g` и корректировки `this`.

### Упрощённое строение виртуальных таблиц

У подобъектов `Mother` и `Father` разные `vptr`, поэтому каждый из них указывает на свою часть виртуальной таблицы `Child`:

```text
vtable Mother:
┌────────────────┬──────────────────┬─────────────────┐
│ top_offset = 0 │ typeinfo: Child  │ &Child::f       │
└────────────────┴──────────────────┴─────────────────┘

vtable Father:
┌───────────────────┬──────────────────┬───────────────────────┐
│ top_offset = -16  │ typeinfo: Child  │ thunk → Child::g      │
└───────────────────┴──────────────────┴───────────────────────┘
```

`top_offset` содержит смещение от текущего базового подобъекта до начала полного объекта. `Mother` уже находится в начале `Child`, поэтому её смещение равно нулю. `Father` начинается со смещения 16 байт, поэтому для возвращения к началу `Child` нужно прибавить `-16`. Это смещение позволяет, например, найти начало полного объекта при `dynamic_cast<void*>`.

`typeinfo` указывает на описание динамического типа полного объекта. Обе таблицы содержат информацию о `Child`, потому что и `Mother`, и `Father` в этом случае являются частями одного объекта `Child`. Эта информация используется операциями `typeid` и `dynamic_cast`.

В оставшихся ячейках находятся адреса виртуальных функций. Через `Mother` функцию `Child::f` можно вызвать сразу: полученный `this` уже указывает на начало `Child`. Через `Father` прямой вызов `Child::g` был бы неправильным, потому что `this` указывает на середину объекта.

Поэтому в ячейке `g` находится `thunk` — небольшой служебный фрагмент кода. Он получает `Father*`, выполняет известную для этого наследования корректировку на `-16` и затем передаёт исправленный `this` в `Child::g`:

```text
Father* this
     ↓
this -= 16
     ↓
Child* this
     ↓
Child::g(this)
```

### Виртуальная база

```cpp
struct Granny {
    int granny_value = 0;
    virtual void f() {}
};

struct Mother : virtual Granny {
    int mother_value = 0;
};

struct Father : virtual Granny {
    int father_value = 0;
};

struct Child : Mother, Father {
    int child_value = 0;
    void f() override {}
};
```

`Mother` и `Father` внутри `Child` используют один общий подобъект `Granny`. Он хранится после собственных подобъектов и полей `Child`:

```text
          ┌──────┬───┬─────┬──────┬───┬───┬──────┬───┬─────┐
Child:    │ VM   │ M │ pad │ VF   │ F │ C │ VG   │ G │ pad │
          └──────┴───┴─────┴──────┴───┴───┴──────┴───┴─────┘
размер:      8     4    4      8     4   4     8     4    4
смещение:    0     8   12     16    24  28    32    40   44
```

`VM`, `VF` и `VG` — указатели на виртуальные таблицы подобъектов `Mother`, `Father` и `Granny`. Поля `M`, `F`, `C` и `G` соответствуют `mother_value`, `father_value`, `child_value` и `granny_value`.

Весь объект занимает 48 байт. Общий подобъект `Granny` начинается со смещения 32 байта. Поэтому преобразования `Mother*` и `Father*` в `Granny*` дают один и тот же адрес:

```cpp
Child child;

Mother* mother = &child;
Father* father = &child;

Granny* from_mother = mother;
Granny* from_father = father;

std::cout << std::boolalpha
          << (from_mother == from_father); // true
```

Смещение виртуальной базы хранится в виртуальных таблицах `Mother` и `Father`. Благодаря этому один и тот же код преобразования `Mother*` в `Granny*` находит `Granny` и в самостоятельном объекте `Mother`, и внутри объекта `Child`, хотя положение виртуальной базы в этих объектах различается.

## §5.7. Ограничения и нетривиальные случаи виртуальных функций

### Какие функции не бывают виртуальными

Статическая функция не связана с конкретным объектом и не имеет `this`, поэтому она не может быть виртуальной:

```cpp
struct Example {
    virtual static void f(); // ошибка
};
```

Конструктор тоже не может быть виртуальным: до выбора и выполнения конструктора объект требуемого динамического типа ещё не создан. Полиморфное создание обычно выражают виртуальной функцией `clone`, фабрикой или отдельной функцией.

Шаблон (превью следующей главы) функции-члена нельзя объявить виртуальным:

```cpp
struct Example {
    template<class T>
    virtual void process(T value); // ошибка
};
```

У виртуальной таблицы должен существовать конечный набор вызываемых функций для класса, а шаблон порождает разные функции только по мере использования типов. Шаблонный класс при этом вполне может содержать обычные виртуальные функции.

### Определение виртуальной функции

Обычная виртуальная функция, которая ODR-используется программой, должна иметь определение. Одного объявления недостаточно:

```cpp
struct Base {
    virtual void f();
};
```

Если реализации `Base::f` нигде нет, сборка часто завершится ошибкой линковки. Даже если в конкретном исходном пути функция явно не вызывается, реализация может нуждаться в её адресе для виртуальной таблицы.

Чисто виртуальная функция может не иметь определения, пока нет квалифицированного вызова, требующего тела. Чисто виртуальный деструктор — исключение на практике использования: его тело всегда требуется при уничтожении производного объекта.

### Виртуальные вызовы в конструкторах

Во время выполнения конструктора `Base` производная часть объекта ещё не создана. Поэтому виртуальный вызов из конструктора `Base` не переходит в `Derived`:

```cpp
struct Base {
    Base() {
        f();
    }

    virtual void f() {
        std::cout << "Base::f\n";
    }
};

struct Derived : Base {
    int value = 42;

    void f() override {
        std::cout << value << '\n';
    }
};

Derived object;
```

> Во время конструктора `Base` вызывается `Base::f`.

Это защищает от обращения к `Derived::value` до его инициализации. Виртуальный вызов ограничен текущей ветвью конструирования: динамическим типом для такого вызова считается создаваемая сейчас часть.

Аналогичное правило действует при уничтожении. Когда выполняется `Base::~Base`, производная часть уже уничтожена, поэтому виртуальный вызов не переходит в неё.

### Чисто виртуальный вызов при создании и уничтожении

```cpp
struct Base {
    Base() {
        f();
    }

    virtual void f() = 0;
    virtual ~Base() = default;
};
```

Вызов чисто виртуальной функции для создаваемого базового подобъекта приводит к UB. Производный переопределитель ещё не участвует в диспетчеризации. В зависимости от формы вызова и реализации программа может получить предупреждение, ошибку линковки, аварийное завершение через обработчик pure virtual call или другое проявление UB.

Косвенный вызов не спасает ситуацию:

```cpp
struct Base {
    Base() {
        helper();
    }

    void helper() {
        f();
    }

    virtual void f() = 0;
};
```

`helper` вызывается невиртуально, но внутри него `f()` остаётся виртуальным вызовом для текущего базового подобъекта. На момент вызова функции `f()` ее определение состоит из вывода текста "pure virtual function call" и вызова `std::terminate`.

Практический вывод: конструкторы и деструкторы не должны полагаться на полиморфное поведение ещё не созданных или уже уничтоженных частей. Общую инициализацию лучше вынести в невиртуальную функцию базы или выполнять после полного создания объекта.

### Типичная смена таблиц во время жизни

В реализации с `vptr` процесс можно представить так:

1. Перед телом конструктора `Base` служебное состояние указывает на виртуальные функции `Base`.
2. После создания базовой части начинается создание `Derived`, и состояние переключается на таблицу `Derived`.
3. При уничтожении сначала действует таблица `Derived`.
4. После завершения производного деструктора при уничтожении `Base` состояние снова соответствует `Base`.

Это объясняет наблюдаемое поведение, но стандарт гарантирует именно правила вызова, а не физическое переприсваивание конкретного скрытого указателя.

### Аргументы по умолчанию

Виртуально выбирается тело функции, но аргументы по умолчанию подставляются по статическому типу в месте вызова:

```cpp
struct Base {
    virtual void f(int value = 1) {
        std::cout << "Base " << value << '\n';
    }
};

struct Derived : Base {
    void f(int value = 2) override {
        std::cout << "Derived " << value << '\n';
    }
};

Derived derived;
Base& base = derived;

base.f();
derived.f();
```

> Вывод:
>
> ```text
> Derived 1
> Derived 2
> ```

В первом вызове компилятор видит `Base&` и подставляет `1`, после чего виртуальная диспетчеризация выбирает тело `Derived::f`. Во втором вызове статический тип — `Derived`, поэтому подставляется `2`.

Разные значения по умолчанию у переопределителей почти всегда создают путаницу. Надёжнее оставить значение только у публичной точки интерфейса или использовать невиртуальную функцию-обёртку:

```cpp
struct Base {
    void f() {
        f_impl(1);
    }

private:
    virtual void f_impl(int value) = 0;
};
```

Теперь правило выбора значения находится в одном невиртуальном месте, а производные классы меняют только реализацию.

### Представление указателя на виртуальный метод

```cpp
struct LeftBase {
    virtual void f() {}
};

struct RightBase {
    virtual void g() {}
};

struct Child : LeftBase, RightBase {
    void f() override {}
    void g() override {}
};

void (Child::*method)() = &Child::g;
```

Указатель на функцию-член должен уметь представить невиртуальный адрес, виртуальную ячейку и возможную корректировку `this`. Чаще всего он состоит из двух машинных слов, где специальные биты различают адрес функции и индекс виртуальной таблицы.

В некоторой реализации последние два машинных слова могут кодировать сдвиг относительно виртуальной таблицы и сдвиг относительно начала объекта. Так как указатели всегда располагаются по четным адресам, последний бит всегда 0, поэтому некоторые реализации используют его (заменяют на 1), чтобы сообщить о том, что указатель указывает не на обычный метод, а на виртуальный: что машинное слово нужно считать не адресом, а сдвигом в виртуальной таблице.
