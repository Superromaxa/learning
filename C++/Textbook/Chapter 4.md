# IV. Наследование

Наследование позволяет построить новый класс на основе уже существующего. Объект производного класса содержит подобъект базового класса и может дополнять его новыми данными и операциями.

```cpp
class Animal {
public:
    void eat() {}
};

class Cat : public Animal {
public:
    void meow() {}
};
```

У объекта `Cat` есть базовый подобъект `Animal`, поэтому для него можно вызвать и `eat`, и `meow`:

```cpp
Cat cat;
cat.eat();
cat.meow();
```

Наследование не следует использовать только ради повторного использования нескольких строк кода. Публичное наследование выражает отношение «производный тип является разновидностью базового и может использоваться вместо него». Если такого отношения нет, композиция типов часто описывает модель точнее.

Класс можно наследовать от структуры, а структуру — от класса. Ключевые слова `class` и `struct` не создают разные категории типов.

## §4.1. Публичное, защищённое и приватное наследование

В объявлении производного класса указывается базовый класс и вид наследования:

```cpp
class PublicDerived : public Base {};
class ProtectedDerived : protected Base {};
class PrivateDerived : private Base {};
```

Если вид наследования не указан, у `struct` используется `public`, а у `class` — `private`:

```cpp
struct S : Base {}; // public Base
class C : Base {};  // private Base
```

Нужно различать два набора правил:

1. Модификатор члена (`public`, `protected`, `private`) определяет, кто может обратиться к самому члену.
2. Вид наследования определяет, насколько отношение между базовым и производным классами доступно внешнему коду и каким станет доступ унаследованных членов.
3. Модификаторы доступа не влияют на область видимости переменных, функций и классов, они лишь задают права на доступ.

### Доступ к членам

- `public` доступен из любого контекста, где видно имя;
- `private` доступен членам и друзьям того класса, где он объявлен;
- `protected` доступен также производным классам, но по специальным правилам.

```cpp
class Base {
public:
    int public_value = 1;

protected:
    int protected_value = 2;

private:
    int private_value = 3;
};
```

Производный объект физически содержит и закрытый член базового подобъекта, но производный класс не получает к нему прямой доступ:

```cpp
class Derived : public Base {
    void f() {
        public_value = 10;     // допустимо
        protected_value = 20;  // допустимо
        private_value = 30; // ошибка компиляции
    }
};
```

`private_value` не исчезает из объекта. Решение о его закрытости принадлежит `Base`, и класс `Derived` не может его отменить. Работать с таким полем нужно через доступный интерфейс `Base`.

### Как вид наследования меняет доступ

При публичном наследовании:

- `public`-члены базы остаются `public` в производном классе;
- `protected` остаются `protected`;
- `private` по-прежнему доступны только самой базе и её друзьям.

При защищённом наследовании открытые и защищённые члены базы становятся `protected` в производном классе.

При приватном наследовании открытые и защищённые члены базы становятся `private` в производном классе.

| Член в базе | `public`-наследование | `protected`-наследование | `private`-наследование |
|---|---|---|---|
| `public` | `public` | `protected` | `private` |
| `protected` | `protected` | `protected` | `private` |
| `private` | недоступен производному классу | недоступен производному классу | недоступен производному классу |

Таблица описывает доступ через производный класс. Она не переписывает объявление внутри самой базы.

### Особое правило `protected`

Производный класс получает доступ к защищённому члену не через любой объект базового типа, а через объект подходящего производного типа:

```cpp
class Base {
protected:
    int value = 0;
};

class Derived : public Base {
public:
    void copy_from(const Derived& other) {
        value = other.value; // допустимо
    }

    void copy_from_base(const Base& other) {
        value = other.value; // ошибка компиляции
    }
};
```

`Derived` может работать с унаследованным `protected`-состоянием объектов `Derived` и его наследников. Но он не получает право открывать закрытый для внешнего мира член произвольного объекта `Base`.

В выражении `other.value` объект `other` имеет тип `Base`. Производный класс не получает доступ к `protected`-полю через произвольный объект базового типа, поэтому такое обращение запрещено.

Это правило важно в длинных цепочках:

```cpp
struct Granny {
protected:
    int value = 0;
};

struct Mother : protected Granny {};

struct Son : Mother {
    void f(Son& other, Granny& granny) {
        value = 1;       // доступ через текущий Son
        other.value = 2; // доступ через другой Son
        granny.value = 3; // ошибка
    }
};
```

Имя `value` находится при поиске и существует в объекте, но затем правила доступа могут запретить конкретное обращение. Видимость имени и доступность — не одно и то же.

## §4.2. Поиск имён, сокрытие и доступность

Если производный класс объявляет член с тем же именем, он скрывает одноимённые члены базового класса:

```cpp
struct Base {
    int value = 1;

    void f() {
        std::cout << "Base::f\n";
    }

    void g(int) {
        std::cout << "Base::g(int)\n";
    }
};

struct Derived : Base {
    int value = 2;

    void f() {
        std::cout << "Derived::f\n";
    }

    void g(double) {
        std::cout << "Derived::g(double)\n";
    }
};
```

```cpp
Derived object;
object.f();
object.g(1);
```

> Вывод:
>
> ```cpp
> Derived::f
> Derived::g(double)
> ```

`Base::g(int)` подошла бы аргументу `1` точнее, но до разрешения перегрузки поиск имени уже остановился на `Derived`, где нашёл `g`. Объявление функции с тем же именем скрывает весь набор перегрузок базы, а не только функцию с совпадающей сигнатурой.

Сначала определяется набор объявлений по правилам поиска имён, затем среди найденных функций разрешается перегрузка.

### `using` для перегрузок базового класса

Набор базы можно вернуть в область производного класса:

```cpp
struct Derived : Base {
    using Base::g;

    void g(double) {
        std::cout << "Derived::g(double)\n";
    }
};
```

Теперь:

```cpp
Derived object;
object.g(1);   // Base::g(int)
object.g(1.5); // Derived::g(double)
```

`using Base::g` вводит объявления базы в набор производного класса. Если `using` расположен в другой секции доступа, он может изменить доступ к допустимому унаследованному имени через производный тип:

```cpp
class Base {
protected:
    void reset() {}
};

class Derived : public Base {
public:
    using Base::reset;
};
```

Теперь внешний код может вызвать `reset` у `Derived`. Но производный класс не может таким способом получить доступ к `private`-члену базы: он не имеет права назвать его в `using`.

Попытка ввести поле с именем, которое уже непосредственно объявлено в производном классе, создаёт конфликт:

```cpp
struct Derived : Base {
    int value = 2;
    using Base::value; // конфликт имён
};
```

### Квалифицированное имя

К скрытому члену базы можно обратиться явно:

```cpp
Derived object;

std::cout << object.value << '\n';       // Derived::value
std::cout << object.Base::value << '\n'; // Base::value

object.f();       // Derived::f
object.Base::f(); // Base::f
```

Квалификация выбирает область, но не обходит контроль доступа. Если `Base::value` недоступен в текущем контексте, запись имени полностью ничего не изменит.

Начальный `::` означает глобальную область видимости:

```cpp
::Base
```

Он нужен только при реальном конфликте с локальным или вложенным именем `Base`. Приватное наследование само по себе не обязывает использовать `::Base`: проблема доступа к базовому подобъекту и поиск имени типа — разные механизмы.

### Доступность injected class name

Имя класса автоматически вводится в область самого класса. Такое имя называется injected class name:

```cpp
struct Base {
    int x;
};
```

В область класса автоматически добавляется имя `Base`, обозначающее сам тип. В диагностике компилятор может показать это введённое имя как `Base::Base`. Такое сообщение относится к имени типа, найденному в области класса, а не к вызову конструктора.

Injected class name участвует в наследовании и поиске имён. Поэтому приватное наследование может повлиять не только на преобразование производного объекта к базовому типу, но и на доступность имени базового класса в следующем производном классе:

```cpp
struct Base {
    int x;
};

struct Derived : private Base {};

struct FurtherDerived : Derived {
    void f(Base& base) { // ошибка компиляции: Base::Base недоступно
        base.x = 1;
    }
};
```

При разборе параметра `Base&` компилятор ищет имя `Base` из области `FurtherDerived`. Оно находится через цепочку наследования:

```text
FurtherDerived -> Derived -> Base
```

Но `Derived` наследуется от `Base` приватно. Для `FurtherDerived` найденное таким способом имя `Base::Base` недоступно, поэтому ошибка возникает уже в объявлении параметра. До проверки выражения `base.x` компилятор не доходит.

Глобальный тип можно указать квалифицированным именем:

```cpp
struct FurtherDerived : Derived {
    void f(::Base& base) {
        base.x = 1;
    }
};
```

Начальный `::` заставляет искать `Base` в глобальной области, а не среди имён, найденных через наследование. Поле `Base::x` открыто, поэтому обращаться к нему через самостоятельный объект `Base` разрешено.

Квалификация `::Base` позволяет назвать глобальный тип, но не меняет доступность преобразования по иерархии:

```cpp
struct FurtherDerived : Derived {
    void f() {
        ::Base& base = *this; // ошибка компиляции: Base — недоступная база
    }
};
```

Приватное наследование между `Derived` и `Base` по-прежнему запрещает `FurtherDerived` преобразовывать себя в `Base`.

### Когда проверяется доступ

Упрощённо компилятор:

1. выполняет поиск имени;
2. формирует кандидатов и выбирает лучшую перегрузку;
3. проверяет доступ выбранной функции.

Поэтому недоступная функция может победить при разрешении перегрузки, после чего вызов станет ошибкой. Компилятор не обязан откатываться и искать менее подходящую, но открытую перегрузку:

```cpp
class Example {
public:
    void f(double) {}

private:
    void f(int) {}
};

Example object;
// object.f(1); // выбрана точная, но private-перегрузка f(int)
```

Такое поведение не даёт обходить интерфейс класса с помощью менее точных преобразований аргументов.

## §4.3. Устройство объекта и преобразования типов

Объект производного класса содержит базовый подобъект:

```cpp
struct Base {
    int x = 1;
};

struct Derived : Base {
    double y = 2.0;
};
```

У `Derived` есть подобъект `Base` с полем `x` и собственное поле `y`. В используемой в примерах 64-битной системе `int` занимает 4 байта и выравнивается по 4, а `double` занимает 8 байт и выравнивается по 8. Объект размещается так:

```text
смещение  размер  содержимое
0         4       Base::x
4         4       выравнивающее заполнение
8         8       Derived::y
```

Поэтому `sizeof(Derived) == 16`, а `alignof(Derived) == 8`.

### Empty Base Optimization

Самостоятельный объект пустого класса имеет ненулевой размер:

```cpp
struct Empty {};
static_assert(sizeof(Empty) >= 1);
```

Пустой базовый подобъект не занимает дополнительного места в следующем классе:

```cpp
struct Value : Empty {
    double number;
};
```

`Empty` размещается по тому же начальному адресу, что и объект `Value`, а поле `number` также начинается со смещения `0`. Поэтому `sizeof(Value) == sizeof(double) == 8`. Такое размещение называется Empty Base Optimization (EBO).

### Восходящее преобразование

При доступном и однозначном наследовании указатель или ссылка на производный объект неявно преобразуются в указатель или ссылку на базовый подобъект:

```cpp
void change(Base& base) {
    base.x = 10;
}

Derived object;
change(object);
```

Новая копия не создаётся. Параметр `base` обозначает подобъект `Base` внутри `object`, поэтому после вызова `object.x == 10`. Через ссылку типа `Base&` функция может обращаться только к членам `Base`.

То же относится к указателям:

```cpp
Derived* derived_pointer = &object;
Base* base_pointer = derived_pointer;
```

В показанном размещении подобъект `Base` начинается со смещения `0`, поэтому `derived_pointer` и `base_pointer` содержат одинаковый адрес.

Преобразование должно быть доступным и вести к единственному базовому подобъекту. Приватная база недоступна обычному внешнему коду, а повторяющаяся невиртуальная база может сделать преобразование неоднозначным.

### Срезка объекта

При передаче по значению создаётся отдельный объект базового типа:

```cpp
void consume(Base base);

Derived object;
consume(object);
```

Для параметра вызывается подходящий конструктор копирования или перемещения `Base`, которому передаётся базовый подобъект `object`. Поле `Derived::y` в новом объекте отсутствует. Это называется object slicing — срезка.

Сначала выполняется стандартное преобразование к ссылке на базовый подобъект, после чего обычный конструктор `Base` создаёт новый `Base`. После срезки новый объект действительно имеет тип `Base`, и поля производного класса в нём отсутствуют. Ссылка или указатель позволяют обратиться к базовому подобъекту без создания отдельного `Base` и без потери производной части исходного объекта.

### Обратное преобразование

Не каждый объект `Base` является частью `Derived`, поэтому неявного преобразования вниз нет:

```cpp
Base base;
Derived& derived = base; // ошибка компиляции
```

`static_cast` может выполнить обратное преобразование ссылки или указателя при подходящей базе:

```cpp
Derived object;
Base& base_reference = object;

Derived& derived_reference = static_cast<Derived&>(base_reference);
```

Здесь преобразование корректно, потому что `base_reference` действительно обозначает подобъект внутри `Derived`.

Если ссылка на самом деле обозначает самостоятельный `Base`, `static_cast<Derived&>` не выполняет динамическую проверку. Использование результата нарушит правила программы и приводит к UB:

```cpp
Base base;
Derived& wrong = static_cast<Derived&>(base); // опасно
```

`static_cast` вниз запрещён, если базовый класс недоступен или преобразование по иерархии неоднозначно.

### Почему `reinterpret_cast` не заменяет приведение по иерархии

Для доступной однозначной базы используется обычное неявное преобразование:

```cpp
Derived object;
Base* base = &object;
```

`reinterpret_cast` меняет тип указателя, но не делает недоступную базу доступной и не выбирает один из нескольких неоднозначных базовых подобъектов. Если обычное преобразование `Derived*` в `Base*` запрещено, обращение через результат `reinterpret_cast` не становится корректным.

Преобразования значений устроены иначе: объект `Derived` можно скопировать в `Base` со срезкой, но обычного преобразования значения `Base` в полноценный `Derived` нет. Недостающие поля и инварианты производного класса невозможно восстановить автоматически.

### Преобразование `Derived → Base`

Объект `Derived` содержит подобъект `Base`, поэтому его можно неявно преобразовать к копии, указателю или ссылке на `Base`. При создании копии происходит срезка: в новый объект копируется только базовая часть.

`static_cast` выполняет те же допустимые преобразования явно.

`reinterpret_cast<Base>(derived)` не компилируется, потому что `reinterpret_cast` не выполняет преобразование одного объекта класса в отдельный объект другого класса. Для указателей и ссылок такая запись синтаксически разрешена.

### Преобразование `Base → Derived`

Неявное преобразование запрещено для всех трёх форм. Не каждый объект `Base` является базовой частью объекта `Derived`, поэтому компилятор не может автоматически считать его полноценным `Derived`.

Создать отдельный `Derived` из `Base` через `static_cast` или `reinterpret_cast` также нельзя.

В `Base` нет поля `Derived::y`, а у `Derived` нет конструктора, создающего недостающую производную часть из объекта `Base`.

`static_cast` разрешает обратное преобразование указателя или ссылки:

```cpp
Derived derived;
Base* base_pointer = &derived;

Derived* derived_pointer = static_cast<Derived*>(base_pointer);
```

Здесь преобразование корректно, потому что `base_pointer` указывает на базовый подобъект настоящего `Derived`.

Если исходный указатель или ссылка обозначает самостоятельный `Base`, обратный `static_cast` приводит к UB.

`reinterpret_cast` для указателей и ссылок также компилируется, но не проверяет, находится ли по адресу объект `Derived`, и не выполняет необходимую корректировку адреса по иерархии. Поэтому обращение через результат может привести к UB.

### Приватное наследование

Теперь `Derived` наследуется от `Base` приватно:

```cpp
struct Base {
    int x = 1;
};

struct Derived : private Base {
    double y;
    Derived()
        : y(2.0) {}

};
```

Внутри самого `Derived` и в его друзьях приватная база доступна. В таком контексте восходящие преобразования `Derived → Base` снова разрешены, поскольку код имеет право использовать информацию о наследовании.

`reinterpret_cast` не проверяет доступность базы и не выполняет преобразование по иерархии. Поэтому преобразования указателей и ссылок синтаксически разрешены даже во внешнем коде:

```cpp
Derived derived;

Base* base_pointer = reinterpret_cast<Base*>(&derived);
Base& base_reference = reinterpret_cast<Base&>(derived);
```

Преобразование отдельного объекта через `reinterpret_cast` по-прежнему невозможно, поэтому в столбцах `copy` остаётся CE.

Обратные преобразования указателей и ссылок из `Base` в `Derived` также компилируются через `reinterpret_cast`, но корректный объект `Derived` по адресу не проверяется. Обращение через результат может привести к UB.

## §4.4. Конструкторы и деструкторы при наследовании

До выполнения тела конструктора производного класса его базовые подобъекты и поля уже должны быть созданы.

Порядок инициализации:

1. виртуальные базовые классы — наиболее производным классом;
2. прямые невиртуальные базы в порядке объявления в списке баз;
3. поля в порядке объявления в классе;
4. тело конструктора.

Порядок списка инициализации этот порядок не меняет.

```cpp
struct Base {
    int x;

    explicit Base(int value)
        : x(value) {
        std::cout << "Base ";
    }
};

struct Member {
    Member() {
        std::cout << "Member ";
    }
};

struct Derived : Base {
    Member member;
    int y;

    Derived(int x, int y)
        : Base(x), member(), y(y) {
        std::cout << "Derived ";
    }
};
```

Создание `Derived object{1, 2};` выведет:

```text
Base Member Derived
```

У `Base` нет конструктора без аргументов, поэтому `Derived` обязан явно выбрать `Base(x)`. Если базу не указать, компилятор попытается вызвать её конструктор по умолчанию и сообщит об ошибке.

Конструктор производного класса не «независим» от конструкторов базы: он не наследует их автоматически, но всегда обязан обеспечить создание базового подобъекта.

### Порядок уничтожения

Уничтожение идёт в обратном порядке:

1. выполняется тело деструктора производного класса;
2. уничтожаются его поля в обратном порядке объявления;
3. уничтожаются прямые невиртуальные базы в обратном порядке;
4. наиболее производный объект уничтожает виртуальные базы.

```cpp
struct A {
    A()  { std::cout << "A "; }
    ~A() { std::cout << "~A "; }
};

struct B : A {
    A member;

    B()  { std::cout << "B "; }
    ~B() { std::cout << "~B "; }
};
```

Для локального `B object;` полный вывод будет:

```text
A A B ~B ~A ~A
```

Сначала создаётся базовый `A`, затем поле `member`, затем выполняется тело `B`. При уничтожении сначала выполняется `~B`, затем уничтожается `member`, затем базовый `A`.

В теле деструктора производного класса его поля и базы ещё существуют. Когда управление дошло до деструктора базы, производная часть уже завершила своё уничтожение. Поэтому базовый деструктор не должен пытаться обращаться к полям наследника.

Обычные методы можно вызывать, пока используемые ими части объекта ещё существуют.

### Наследование конструкторов

Начиная с C++11 конструкторы базы можно ввести в производный класс:

```cpp
struct Base {
    explicit Base(int value) {}
    Base(int first, int second) {}
};

struct Derived : Base {
    using Base::Base;

    int extra = 0;
};

Derived first{1};
Derived second{1, 2};
```

Выбранный конструктор создаёт базовый подобъект, а остальные части `Derived` инициализируются обычным для них способом. В примере `extra` получает `0` из инициализатора поля.

Наследование конструкторов не превращает конструктор копирования `Base` в конструктор `Derived` из `Base`:

```cpp
Base base{1};
Derived derived = base; // ошибка компиляции
```

Иначе из одного базового подобъекта пришлось бы непонятным образом строить недостающую производную часть. Для `Derived` отдельно рассматриваются его собственные неявные или объявленные конструкторы копирования и перемещения.

Если поле производного класса нельзя инициализировать при вызове унаследованного конструктора, соответствующий конструктор `Derived` окажется непригодным или удалённым.

## §4.5. Множественное наследование

C++ позволяет наследоваться от нескольких классов:

```cpp
struct Mother {
    int mother_value = 1;
};

struct Father {
    int father_value = 2;
};

struct Child : public Mother, private Father {
    int child_value = 3;
};
```

Объект `Child` содержит подобъекты `Mother` и `Father`, а также поле `child_value`. В используемой в примерах системе каждый из трёх `int` занимает 4 байта:

```text
смещение  размер  содержимое
0         4       Mother::mother_value
4         4       Father::father_value
8         4       Child::child_value
```

Поэтому `sizeof(Child) == 12`, а `alignof(Child) == 4`.

### Корректировка указателя

Разные базовые подобъекты часто начинаются по разным адресам внутри объекта:

```cpp
Child child;
Mother* mother = &child;
```

`Mother` начинается со смещения `0`, поэтому `mother` содержит тот же адрес, что и `&child`. Подобъект `Father` начинается со смещения `4`, поэтому при доступном преобразовании к `Father*` компилятор увеличивает адрес на 4 байта.

Внешний код не сможет неявно получить `Father*`, потому что наследование `Father` приватное. Внутри `Child` такое преобразование доступно.

### Одинаковые имена в разных базах

Если обе базы объявляют одно имя, автоматически объединённого набора перегрузок не возникает:

```cpp
struct Left {
    void f(int) {}
};

struct Right {
    void f(double) {}
};

struct Combined : Left, Right {};

Combined object;
object.f(1); // ошибка: имя f неоднозначно
```

Неоднозначность появляется уже при поиске имени, до сравнения сигнатур. Нужную функцию можно квалифицировать:

```cpp
object.Left::f(1);
object.Right::f(1.5);
```

Или явно собрать набор перегрузок:

```cpp
struct Combined : Left, Right {
    using Left::f;
    using Right::f;
};
```

Теперь обычное разрешение перегрузки выберет подходящую функцию.

### Ромбовидное наследование

Пусть две базы независимо наследуются от одного типа:

```cpp
struct Granny {
    int value = 0;
};

struct Mother : Granny {};
struct Father : Granny {};

struct Child : Mother, Father {};
```

Объект `Child` содержит два разных подобъекта `Granny`: один внутри `Mother`, второй внутри `Father`.

```text
        Granny   Granny
           ↑       ↑
         Mother  Father
            ↖     ↗
             Child
```

В памяти объект `Child` будет лежать следующим образом:

```text
          ┌─────┬─────┬─────┬─────┬─────┐
Child:    │ GM  │  M  │ GD  │  D  │  S  │
          └─────┴─────┴─────┴─────┴─────┘
```

Поэтому обращение неоднозначно:

```cpp
Child child;
child.value = 1;       // какой Granny?
Granny& base = child;  // какой подобъект выбрать?
```

Запись `Mother::Granny` не создаёт нового типа: оба пути ведут к одному типу `Granny`. Для выбора конкретного подобъекта сначала выбирают ветвь:

```cpp
Mother& mother = child;
Granny& maternal_granny = mother;

Father& father = child;
Granny& paternal_granny = father;
```

То же можно записать вложенными приведениями:

```cpp
Granny& maternal_granny = static_cast<Mother&>(child);
```

После выбора `Mother&` дальнейшее преобразование к её `Granny` однозначно.

Комбинация прямой и косвенной базы одного типа тоже создаёт несколько подобъектов и неоднозначные преобразования:

```cpp
struct Mother : Granny {};
struct Child : Mother, Granny {};
```

В такой ситуации обратиться к полям `Granny`, от которой унаследован `Child` невозможно: этот класс будет недосягаем без сдвига указателя.

Такую иерархию компилятор может принять с предупреждением. `reinterpret_cast` или ручной сдвиг адреса не гарантируют корректное обращение к нужному подобъекту.

### Указатели на члены при множественном наследовании

```cpp
struct Mother {
    void f() {}
};

struct Father {
    void f() {}
};

struct Child : Mother, Father {};

void (Father::*father_method)() = &Father::f;

Child child;
(child.*father_method)();
```

При вызове реализация должна найти подобъект `Father` внутри `child` и передать функции правильный `this`. Указатель на член должен содержать информацию, необходимую для такой корректировки.

Указатель на член базы можно неявно преобразовать в указатель на член производного класса при доступном однозначном невиртуальном наследовании:

```cpp
void (Child::*child_method)() = father_method;
(child.*child_method)();
```

Указатель на метод хранит сведения, необходимые для выбора функции и корректировки `this`. На самом деле размер указателя на метод в два раза больше указателя на функцию (чтобы была возможность сохранить информацию о сдвиге). Поэтому он не является обычным указателем на функцию. Вызывать такой метод нужно через операции `.*` или `->*`.

## §4.6. Виртуальное наследование

Виртуальное наследование позволяет нескольким ветвям разделять один базовый подобъект:

```cpp
struct Granny {
    int value = 0;
};

struct Mother : virtual Granny {};
struct Father : virtual Granny {};

struct Child : Mother, Father {};
```

Теперь в `Child` находится один общий виртуальный подобъект `Granny`:

```text
             Granny
             ↗    ↖
         Mother  Father
            ↖     ↗
             Child
```

```cpp
Child child;
child.value = 10;

Granny& granny = child;
```

Оба пути через `Mother` и `Father` приводят к одному `Granny`, поэтому обращение и преобразование однозначны.

Виртуальным является наследование конкретной базы, а не сам класс навсегда. Запись `virtual Granny` сообщает, что для наиболее производного объекта все виртуальные пути к `Granny` должны использовать общий подобъект.

### Кто конструирует виртуальную базу

Виртуальную базу инициализирует наиболее производный класс:

```cpp
struct Granny {
    int g;
    explicit Granny(int value) {}
};

struct Mother : virtual Granny {
    int m;
    Mother()
        : Granny(1) {}
};

struct Father : virtual Granny {
    int f;
    Father()
        : Granny(2) {}
};

struct Child : Mother, Father {
    int c;
    Child()
        : Granny(3), Mother(), Father() {}
};
```

При создании самостоятельного `Child` именно `Child` создаёт общий `Granny` со значением `3`. Инициализаторы `Granny(1)` и `Granny(2)` в конструкторах промежуточных классов для этого объекта игнорируются. Они понадобятся, если создать самостоятельный объект `Mother` или `Father`, где соответствующий класс сам является наиболее производным.

Порядок создания начинается с виртуальных баз, затем создаются обычные прямые базы, поля и выполняется тело наиболее производного конструктора. Уничтожение идёт в обратном порядке.

### Представление в памяти

Чтобы из `Mother*` или `Father*` найти общий `Granny`, компилятор добавляет служебные данные со смещением виртуальной базы. Каждый промежуточный базовый подобъект хранит восьмибайтовый служебный указатель:

В памяти объект выглядит следующим образом:

```text
          ┌──────┬───┬─────┬──────┬───┬───┬───┬─────┐
Child:    │  VM  │ M │ pad │  VD  │ D │ S │ G │ pad │
          └──────┴───┴─────┴──────┴───┴───┴───┴─────┘
```

Тут для `Mother` и `Father` необходимы указатели на "место", где лежит `Granny`.

```text
смещение  размер  содержимое
0         8       служебный указатель Mother
16        8       служебный указатель Father
32        4       общий Granny::value
36        4       завершающее заполнение
```

Поэтому для приведённых классов `sizeof(Child) == 40`. Служебные данные позволяют найти общий `Granny`, даже когда обращение начинается с указателя на `Mother` или `Father`.

### Преобразования из виртуальной базы

Восходящее преобразование к общей виртуальной базе выполняется нормально:

```cpp
Child child;
Granny& granny = child;
```

Но статическое преобразование обратно из виртуальной базы к производному типу запрещено:

```cpp
Child& child_again = static_cast<Child&>(granny); // ошибка
```

Один `Granny` может быть виртуальной базой разных производных классов, поэтому нужное смещение нельзя определить только по типу `Granny`.

Преобразования от обычных невиртуальных прямых баз к производному классу могут оставаться допустимыми для `static_cast`, если выполнены остальные требования:

```cpp
Mother& mother = child;
Child& child_again = static_cast<Child&>(mother);
```

Здесь `Mother` — непосредственная невиртуальная база `Child`, хотя сама `Mother` виртуально наследует `Granny`.

### Когда неоднозначность сохраняется

Чтобы объединить общий базовый подобъект, все участвующие пути должны наследовать именно его виртуально:

```cpp
struct Mother : virtual Granny {};
struct Father : Granny {};
struct Child : Mother, Father {};
```

В `Child` снова два `Granny`: один общий виртуальный для виртуальных путей и один обычный внутри `Father`. Преобразование `Child -> Granny` неоднозначно.

Виртуальное наследование самих `Mother` и `Father` тоже не объединит их обычные базовые подобъекты `Granny`:

```cpp
struct Mother : Granny {};
struct Father : Granny {};

struct Child : virtual Mother, virtual Father {};
```

У `Mother` и `Father` по-прежнему свои невиртуальные `Granny`. Виртуальность применена не к той связи, где произошло дублирование.

### Поиск имён и правило доминирования

В сложной решётке виртуального наследования одно и то же объявление может быть достижимо несколькими путями. Повторное достижение одного объявления через общий виртуальный подобъект само по себе не обязательно создаёт неоднозначность.

Если на одном пути производный класс скрывает имя из виртуальной базы, а другой путь приходит к тому же общему подобъекту, при поиске действует правило доминирования: более производное объявление может доминировать над объявлением виртуальной базы.

```cpp
struct VirtualBase {
    void f() {}
};

struct Left : virtual VirtualBase {
    void f() {}
};

struct Right : virtual VirtualBase {};

struct Result : Left, Right {};
```

Для объекта `Result` вызов `f()` выбирает `Left::f`: он скрывает `VirtualBase::f` на одном пути и доминирует над общим объявлением базы.

Если независимые ветви объявят собственные функции с одинаковым именем, ни одна не будет более производной относительно другой:

```cpp
struct Left : virtual VirtualBase {
    void f() {}
};

struct Right : virtual VirtualBase {
    void f() {}
};

struct Result : Left, Right {};
```

Тогда `Result::f()` неоднозначен. Нужно явно выбрать ветвь, ввести нужное имя через `using` с дополнительным разрешением конфликта или определить собственный `Result::f`.

Виртуальное наследование создаёт один общий базовый подобъект, но усложняет конструирование, преобразования и расположение объекта в памяти. Его применяют, когда несколько ветвей иерархии должны работать с одним общим состоянием базового класса.
