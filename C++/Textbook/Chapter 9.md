# IX. Аллокаторы и взаимодействие с памятью

Контейнер отвечает за расположение и время жизни элементов, но ему не обязательно самостоятельно решать, откуда брать память. Эти обязанности разделяются: контейнер определяет, сколько памяти требуется и какие объекты в ней должны существовать, а аллокатор предоставляет и освобождает подходящее хранилище.

Это разделение особенно важно для узловых контейнеров. Обычный `std::list`, `std::map` или `std::set` при вставках часто получает память для отдельных узлов. Универсальная операция выделения памяти сравнительно дорога, поэтому в конкретной программе может быть выгодно получать память крупными блоками, переиспользовать освобождённые узлы или работать с заранее подготовленным буфером.

Аллокатор не меняет логическую модель контейнера. `vector` с пользовательским аллокатором всё равно хранит элементы непрерывно, а `map` сохраняет упорядоченность и логарифмическую сложность. Меняется источник памяти и связанное с ним состояние.

## §9.1. Введение

Большинство стандартных контейнеров имеет параметр аллокатора. Например, упрощённые объявления выглядят так:

```cpp
template <typename T, typename Allocator = std::allocator<T>>
class vector;

template <
    typename Key,
    typename Value,
    typename Compare = std::less<Key>,
    typename Allocator = std::allocator<std::pair<const Key, Value>>
>
class map;
```

По умолчанию используется `std::allocator`, поэтому в обычном коде параметр не виден:

```cpp
std::vector<int> values;
```

Концептуальную цепочку можно представить так:

```text
контейнер
    -> allocator_traits
        -> аллокатор
            -> функция выделения памяти
                -> низкоуровневый механизм среды выполнения
```

Последние звенья не закреплены стандартом. Глобальный `operator new` часто использует системный распределитель памяти, но не обязан буквально вызывать `malloc`, а `malloc` не обязан обращаться к операционной системе при каждом вызове.

### Память и объекты — разные уровни

Аллокатор прежде всего предоставляет сырую память. Получение памяти не означает, что в ней уже существуют объекты:

```cpp
std::allocator<std::string> allocator;

std::string* memory = allocator.allocate(3);
// Места для трёх string есть, но самих объектов string ещё нет.
```

Затем контейнер создаёт объекты в выбранных позициях:

```cpp
using Traits = std::allocator_traits<decltype(allocator)>;

Traits::construct(allocator, memory, "first");
Traits::construct(allocator, memory + 1, "second");
```

Перед освобождением памяти время жизни созданных объектов завершают:

```cpp
Traits::destroy(allocator, memory + 1);
Traits::destroy(allocator, memory);
allocator.deallocate(memory, 3);
```

Параметр `3` у `deallocate` должен соответствовать блоку, полученному от `allocate(3)`. Аллокатор может использовать размер при освобождении, даже если конкретная реализация глобального `operator delete` способна работать без него.

В реальном коде между успешными `construct` и `destroy` должна быть защита от исключений. Если конструирование второго элемента завершится неудачей, первый уже является живым объектом и его необходимо уничтожить перед освобождением блока.

### Упрощённый аллокатор

Минимальную идею можно показать так:

```cpp
template <typename T>
class SimpleAllocator {
public:
    using value_type = T;

    SimpleAllocator() = default;

    template <typename U>
    SimpleAllocator(const SimpleAllocator<U>&) noexcept {}

    [[nodiscard]] T* allocate(std::size_t count) {
        if (count > static_cast<std::size_t>(-1) / sizeof(T)) {
            throw std::bad_array_new_length();
        }

        return static_cast<T*>(
            ::operator new(count * sizeof(T))
        );
    }

    void deallocate(T* pointer, std::size_t) noexcept {
        ::operator delete(pointer);
    }
};
```

Здесь `allocate` не вызывает конструкторы `T`, а `deallocate` не вызывает деструкторы. Именно поэтому контейнер способен иметь `capacity() > size()`: память для будущих элементов существует, а сами элементы ещё нет.

Эта учебная реализация показывает интерфейс, но не рассматривает отдельно типы с расширенным требованием к выравниванию. Полноценный распределитель обязан вернуть адрес, подходяще выровненный для `T`.

Начиная с C++11 пользователю обычно не требуется добавлять в аллокатор собственные `construct` и `destroy`: `std::allocator_traits` предоставляет стандартное поведение. Если они всё же определены в подходящем интерфейсе, версия языка и реализация traits могут учитывать их.

### Состояние и равенство аллокаторов

`std::allocator<T>` не хранит пользовательского ресурса, и его экземпляры взаимозаменяемы. Но произвольные пользовательские аллокаторы не обязаны быть равны.

Смысл равенства практический: память, выделенную одним экземпляром, допустимо освободить другим равным ему экземпляром.

```cpp
if (left_allocator == right_allocator) {
    // Блок, полученный через left_allocator,
    // можно вернуть через right_allocator.
}
```

Например, два аллокатора могут ссылаться на один пул и быть равными, а аллокаторы, связанные с разными пулами, — неравными. Контейнер обязан учитывать это при копировании, перемещении, присваивании и обмене содержимым.

### Нестандартные стратегии

#### Pool allocator

Пул получает крупный блок и выдаёт небольшие части из него. Это снижает число обращений к общему распределителю и может улучшить локальность данных.

Пулу нужно решать, как отслеживать свободные участки и когда освобождать общий блок. Если несколько копий аллокатора используют один пул, состояние ресурса должно жить, пока оно нужно хотя бы одной копии или контейнеру с выделенными из него блоками.

#### Stack allocator

Такой аллокатор выдаёт память из заранее переданного буфера, часто линейно сдвигая текущую позицию. Название описывает стратегию, а не гарантирует, что сам буфер всегда находится в автоматической памяти: он может быть частью другого объекта или динамического блока.

Линейный распределитель очень быстро выделяет память. Поэлементное освобождение может ничего не делать, а весь буфер сбрасывается целиком. Из-за этого особенно важно, чтобы буфер жил дольше всех использующих его контейнеров и элементов.

#### Free-list allocator

Освобождённые блоки не возвращаются немедленно общему распределителю, а связываются в список свободных участков. Следующий запрос подходящего размера использует один из них повторно.

Это особенно естественно для узлов одинакового размера. Однако список свободных блоков содержит сырую память, а не продолжающие жить старые объекты: перед добавлением блока в free list объект должен быть уничтожен.

### Перепривязка к внутреннему типу

Пользователь видит `list<T, Alloc>`, но список выделяет не голые `T`, а внутренние узлы примерно такого вида:

```cpp
struct Node {
    Node* previous;
    Node* next;
    T value;
};
```

Следовательно, контейнеру нужен аллокатор для `Node`, сохраняющий тот же ресурс, что и переданный аллокатор для `T`. Для этого используется перепривязка:

```cpp
using AllocTraits = std::allocator_traits<Alloc>;
using NodeAlloc = typename AllocTraits::template rebind_alloc<Node>;
using NodeTraits = std::allocator_traits<NodeAlloc>;
```

`template` после `::` необходим, потому что `rebind_alloc` — зависимое шаблонное имя. `typename` сообщает, что результат является типом.

Исторический интерфейс пользовательского аллокатора мог содержать:

```cpp
template <typename U>
struct rebind {
    using other = SimpleAllocator<U>;
};
```

Современный код контейнера обращается через `allocator_traits`, который во многих обычных случаях способен получить перепривязанный тип и без явно написанного `rebind`.

Аллокатор передаётся как тип, а не как шаблонный шаблонный параметр. Это позволяет использовать аллокаторы с разным набором шаблонных параметров и хранить уже конкретизированное состояние ресурса.

Если аллокатор пустой, хранение его обычным полем могло бы увеличить размер контейнера. Реализации исторически применяли наследование и Empty Base Optimization. В современном коде похожую задачу может решать `[[no_unique_address]]`; сам атрибут подробнее рассматривается в §9.6.

## §9.2. `allocator_traits`

`std::allocator_traits<Alloc>` нормализует интерфейс разных аллокаторов. Контейнер обращается к traits, а traits либо вызывает соответствующую возможность `Alloc`, либо предоставляет стандартное поведение там, где это предусмотрено.

```cpp
using Traits = std::allocator_traits<Alloc>;

auto pointer = Traits::allocate(allocator, count);
Traits::construct(allocator, address, arguments...);
Traits::destroy(allocator, address);
Traits::deallocate(allocator, pointer, count);
```

Упрощённо идея `construct` выглядит так:

```cpp
template <typename Alloc>
struct SimplifiedTraits {
    template <typename T, typename... Args>
    static void construct(Alloc& allocator,
                          T* pointer,
                          Args&&... arguments) {
        // Концептуально: использовать поддерживаемый интерфейс
        // аллокатора либо стандартное placement-конструирование.
        std::construct_at(
            pointer,
            std::forward<Args>(arguments)...
        );
    }
};
```

Аргументы принимаются как forwarding references и передаются через `std::forward`. Запись `const Args&...` изменила бы категории значений и мешала бы перемещению.

Traits также предоставляет связанные типы и свойства:

- `value_type` — тип объекта, для которого задан аллокатор;
- `pointer` и `const_pointer` — типы указателей аллокатора;
- `size_type` и `difference_type`;
- `rebind_alloc<T>` — аллокатор того же семейства для другого типа;
- признаки распространения аллокатора при операциях контейнера;
- `is_always_equal` — можно ли считать все экземпляры взаимозаменяемыми.

### Копирование состояния ресурса

Копирование объекта аллокатора обычно должно быть недорогим. Если он управляет большим пулом, копия не обязана дублировать весь пул. Экземпляры могут хранить указатель на общее состояние с управляемым временем жизни.

Но конкретный механизм — часть реализации аллокатора. Это может быть счётчик ссылок, внешний ресурс с заведомо большим временем жизни или иной владелец. Само наличие пользовательского аллокатора не требует обязательно использовать reference counting.

Копия аллокатора, созданная обычным копирующим конструктором, должна быть совместима с исходным экземпляром. При копирующем конструировании контейнера, однако, используется отдельная настройка:

```cpp
Alloc selected =
    std::allocator_traits<Alloc>::
        select_on_container_copy_construction(source_allocator);
```

По умолчанию traits возвращает обычную копию. Пользовательский аллокатор может определить одноимённый метод и выбрать другое состояние для нового контейнера. Например, копия контейнера может получить отдельный ресурс вместо совместного использования исходного пула.

### Распространение при присваивании

Копирующее конструирование создаёт новый контейнер, а присваивание работает с уже существующим контейнером и его памятью. Поэтому для присваивания используются признаки типов:

```cpp
using Traits = std::allocator_traits<Alloc>;

Traits::propagate_on_container_copy_assignment::value;
Traits::propagate_on_container_move_assignment::value;
Traits::propagate_on_container_swap::value;
```

Если `propagate_on_container_copy_assignment` равен `true`, при копирующем присваивании аллокатор назначения заменяется аллокатором источника. Если `false`, назначение сохраняет свой аллокатор и копирует элементы в память своего ресурса.

Это различие нельзя игнорировать:

```text
контейнер A -> ресурс A -> блок A
контейнер B -> ресурс B -> блок B
```

Если после присваивания контейнер `A` начнёт хранить аллокатор ресурса `B`, но оставит блок, выделенный ресурсом `A`, будущая деаллокация может пойти не в тот ресурс.

При замене неравных аллокаторов старые элементы уничтожают и старую память возвращают старым аллокатором. Новую память выделяют уже тем аллокатором, который должен принадлежать итоговому контейнеру.

Аналогичная проблема возникает при перемещающем присваивании. Если аллокатор распространяется либо два экземпляра равны, обычно можно забрать готовый блок. Если неравные аллокаторы не распространяются, элементы приходится переносить в память ресурса назначения.

Для `swap` особенно важно свойство `propagate_on_container_swap`. Обмен одними указателями при сохранении неравных непропагируемых аллокаторов привёл бы к освобождению памяти чужим ресурсом.

### `is_always_equal`

`allocator_traits<Alloc>::is_always_equal` сообщает на уровне типа, что любые экземпляры `Alloc` взаимозаменяемы. Для пустого аллокатора без состояния это часто `true`.

Если свойство истинно, контейнеру не нужно выполнять проверку `left_allocator == right_allocator` во время выполнения. Это позволяет безопасно и быстро передавать блоки между экземплярами.

Если свойство ложно, конкретные экземпляры всё равно могут оказаться равными. Тогда контейнер может проверить их через `operator==` и воспользоваться быстрым путём.

## §9.2.1. Аллокатор в упрощённом `vector`

Вектор хранит экземпляр аллокатора и обращается к нему через traits:

```cpp
template <typename T, typename Alloc = std::allocator<T>>
class MyVector {
private:
    using Traits = std::allocator_traits<Alloc>;

    T* data_ = nullptr;
    std::size_t size_ = 0;
    std::size_t capacity_ = 0;
    [[no_unique_address]] Alloc allocator_;

public:
    // Остальной интерфейс.
};
```

Для краткости пример предполагает, что `Alloc::pointer` является обычным `T*`, как у `std::allocator`. Полностью обобщённый контейнер должен учитывать связанные типы из `allocator_traits`.

### `reserve`

```cpp
void reserve(std::size_t new_capacity) {
    if (new_capacity <= capacity_) {
        return;
    }

    T* new_data = Traits::allocate(allocator_, new_capacity);
    std::size_t constructed = 0;

    try {
        for (; constructed < size_; ++constructed) {
            Traits::construct(
                allocator_,
                new_data + constructed,
                std::move_if_noexcept(data_[constructed])
            );
        }
    } catch (...) {
        while (constructed != 0) {
            --constructed;
            Traits::destroy(allocator_, new_data + constructed);
        }

        Traits::deallocate(allocator_, new_data, new_capacity);
        throw;
    }

    for (std::size_t index = 0; index < size_; ++index) {
        Traits::destroy(allocator_, data_ + index);
    }

    if (data_ != nullptr) {
        Traits::deallocate(allocator_, data_, capacity_);
    }

    data_ = new_data;
    capacity_ = new_capacity;
}
```

Один и тот же экземпляр `allocator_` выделяет и освобождает блок. Объекты конструируются и уничтожаются отдельно от операций над памятью.

Старый блок освобождается только после успешного создания всех элементов в новом. Если копирование выбросит исключение, частично созданный новый диапазон уничтожается, но старый вектор остаётся прежним.

### Копирующий конструктор

Новый контейнер выбирает аллокатор через `select_on_container_copy_construction`:

```cpp
MyVector(const MyVector& other)
    : allocator_(Traits::select_on_container_copy_construction(
          other.allocator_)) {
    // Выделение памяти через allocator_ и копирование элементов other.
}
```

Нельзя просто скопировать внутренний указатель `other.data_`: два вектора стали бы считать себя владельцами одного диапазона, изменяли бы общие элементы и дважды освободили бы память.

### Копирующее присваивание

У копирующего присваивания есть два принципиальных случая.

Если аллокатор не распространяется, объект сохраняет `allocator_`. Он может переиспользовать свой блок, если вместимости хватает и корректно обработаны возможные исключения, либо выделить новый блок своим аллокатором.

Если аллокатор распространяется и новый экземпляр не равен старому, безопасная общая схема такова:

1. подготовить элементы в памяти нового аллокатора;
2. при неудаче очистить только новый блок и оставить назначение прежним;
3. уничтожить старые элементы;
4. освободить старый блок старым аллокатором;
5. заменить аллокатор и установить новые указатели.

Порядок важен. Нельзя сначала присвоить `allocator_ = other.allocator_`, а затем через уже заменённый объект освобождать старую память.

Оператор присваивания самого аллокатора не следует безусловно считать `noexcept`, если это не следует из его требований и свойств. Реализация контейнера должна выстроить операцию с учётом реальных гарантий используемых типов.

## §9.3. Перегрузка `new` и `delete`

Нужно различать `new`-выражение и функцию `operator new`.

```cpp
Widget* pointer = new Widget(argument);
```

`new`-выражение выполняет две логические стадии:

1. вызывает подходящую функцию выделения `operator new`, получая сырую память;
2. конструирует в этой памяти объект `Widget`.

Функция `operator new` отвечает только за память. Её прямой вызов не создаёт объект:

```cpp
void* memory = ::operator new(sizeof(Widget));
Widget* pointer = ::new (memory) Widget(argument);
```

Обратное `delete`-выражение сначала вызывает деструктор объекта, а затем подходящую функцию `operator delete`:

```cpp
delete pointer;
```

Прямой вызов `::operator delete(memory)` деструктор не вызывает.

### Замена глобальных функций выделения

Программа может предоставить разрешённые стандартом заменяющие определения глобальных функций выделения и освобождения:

```cpp
void* operator new(std::size_t size) {
    if (void* memory = std::malloc(size)) {
        return memory;
    }

    throw std::bad_alloc();
}

void operator delete(void* memory) noexcept {
    std::free(memory);
}

void* operator new[](std::size_t size) {
    if (void* memory = std::malloc(size)) {
        return memory;
    }

    throw std::bad_alloc();
}

void operator delete[](void* memory) noexcept {
    std::free(memory);
}
```

Выбрасывающая версия обязана при неудаче следовать контракту выделяющей функции, а не просто вернуть `nullptr`. Реальная заменяющая реализация также должна учитывать предусмотренное стандартом поведение `new_handler`.

Логирование внутри глобального `operator new` требует осторожности. `std::cout`, форматирование строки или контейнер, используемый журналом, сами могут выделять память и рекурсивно вызвать тот же `operator new`.

Следует предоставить согласованные формы освобождения, которые может выбрать реализация, включая необходимые array-, sized- и aligned-варианты. Ограничиться одной функцией в демонстрационном фрагменте можно, но это ещё не полноценная промышленная замена всего семейства.

Конкретный способ, которым стандартная библиотека позволяет пользовательскому определению заменить своё, является деталью реализации и линкера. На переносимом уровне нужно полагаться на разрешённый стандартом интерфейс, а не на атрибут вроде `_LIBCPP_WEAK` конкретной библиотеки.

### `new[]`, `delete[]` и число элементов

Выражение:

```cpp
Widget* array = new Widget[10];
delete[] array;
```

должно уничтожить десять созданных объектов. Реализация может сохранить число элементов в служебной области рядом с массивом — такую область часто называют array cookie. Но её наличие, размер и формат стандартом не закреплены.

Важно разделять уровни: деструкторы вызывает семантика `delete[]`-выражения, а не пользовательское тело функции `operator delete[]`. К моменту входа в функцию освобождения объекты уже должны быть уничтожены.

Если конструктор элемента массива с индексом `k` выбросит исключение, уже созданные элементы с меньшими индексами уничтожаются в обратном порядке, после чего выделенная для массива память освобождается. Полностью созданного массива при этом не возникает, и указатель вызывающему коду не возвращается.

Формы должны совпадать:

```cpp
Widget* one = new Widget;
delete one;

Widget* many = new Widget[10];
delete[] many;
```

Смешивание `new` с `delete[]` или `new[]` с `delete` приводит к UB.

### `std::nothrow`

Невыбрасывающая форма возвращает нулевой указатель при неудаче вместо распространения `std::bad_alloc`:

```cpp
Widget* pointer = new (std::nothrow) Widget;

if (pointer == nullptr) {
    // Память получить не удалось.
}
```

Это не означает, что конструктор `Widget` становится невыбрасывающим. Если его собственный код выбросит исключение, такое исключение распространяется обычным образом; `nothrow` относится к неудаче выделения памяти.

### Placement-формы с дополнительными аргументами

Класс или глобальная область могут предоставлять выделяющую функцию с дополнительными параметрами:

```cpp
void* operator new(std::size_t size, int tag, double factor) {
    std::cout << "allocation: " << tag << ' ' << factor << '\n';

    if (void* memory = std::malloc(size)) {
        return memory;
    }

    throw std::bad_alloc();
}

void operator delete(void* memory, int, double) noexcept {
    std::free(memory);
}
```

Тогда выражение выбирает эту форму:

```cpp
Widget* pointer = new (57, 1.79) Widget;
```

Соответствующая placement-форма `operator delete(void*, int, double)` автоматически вызывается, если выделение прошло успешно, но конструктор `Widget` выбросил исключение. Дополнительные аргументы позволяют найти подходящую парную функцию освобождения.

После успешного конструирования обычное выражение `delete pointer` не передаёт `57` и `1.79`. Оно ищет обычную форму освобождения. Поэтому пользовательская схема должна заранее определить, как корректно уничтожается успешно созданный объект; нельзя написать особое `delete (57, 1.79) pointer`.

Placement `new` из стандартной библиотеки:

```cpp
::new (memory) Widget(arguments...);
```

принимает уже готовый адрес и не выделяет память. После ручного placement-конструирования вызывающий код обычно вручную завершает время жизни объекта и возвращает память исходному владельцу.

### Классовые `operator new` и `operator delete`

Функции выделения можно определить для конкретного класса:

```cpp
class Node {
public:
    static void* operator new(std::size_t size) {
        return node_pool.allocate(size);
    }

    static void operator delete(void* memory) noexcept {
        node_pool.deallocate(memory);
    }
};
```

Обычное `new Node` сначала ищет классовую функцию. Запись `::new Node` принудительно использует глобальную форму.

Если запретить классовый `operator new`, обычное создание через `new Type` станет недоступным:

```cpp
class StackOnly {
public:
    static void* operator new(std::size_t) = delete;
};
```

Это не запрещает существование объекта во всякой динамической памяти: объект всё ещё можно разместить placement-конструированием в чужом буфере. Запрещается конкретный обычный путь через классовый `new`-интерфейс.

Запретить автоматическое создание сложнее, потому что синтаксис обычного локального объекта не обращается к отдельному настраиваемому «оператору стека». Обычно ограничивают доступ к конструкторам или деструктору и предоставляют фабрику с контролируемым способом владения.

### Удаление через базовый тип

```cpp
struct Base {
    ~Base() = default;
};

struct Derived : Base {
    ~Derived();
};

Base* pointer = new Derived;
delete pointer; // UB: деструктор Base невиртуальный.
```

Если объект предполагается удалять через указатель на базовый класс, деструктор базы должен быть виртуальным:

```cpp
virtual ~Base() = default;
```

Проблема относится к деструктору, а не к «виртуальному конструктору»: виртуальных конструкторов в C++ нет.

С массивами ситуация строже:

```cpp
Base* array = new Derived[10];
delete[] array; // UB даже при виртуальном деструкторе Base.
```

`delete[]` должен работать с тем типом массива, который был создан. Полиморфное удаление массива производных объектов через указатель на базовый тип не поддерживается.

### Destroying delete

Начиная с C++20 класс может определить destroying delete:

```cpp
class Object {
public:
    static void operator delete(
        Object* pointer,
        std::destroying_delete_t
    ) noexcept {
        pointer->~Object();
        ::operator delete(pointer);
    }
};
```

При обычном `delete` деструктор вызывается до входа в функцию освобождения. Destroying delete объединяет выбор способа разрушения и освобождения: функция получает ещё живой объект и сама обязана вызвать правильный деструктор.

Это низкоуровневый механизм, а не автоматический способ сделать тип «только динамическим». При ошибочной реализации, забывшей деструктор, ресурсы объекта не будут освобождены корректно.

## §9.4. Выравнивание

Каждый объект имеет требование к выравниванию. Если `alignof(T) == 4`, подходящий адрес обычно должен быть кратен четырём. Значение можно узнать через `alignof`:

```cpp
std::cout << alignof(int) << '\n';
std::cout << alignof(double) << '\n';
```

Даже если процессор умеет выполнить невыровненный доступ, создание или использование объекта по неподходящему адресу нарушает требования языка.

```cpp
int* array = new int[10];
char* bytes = reinterpret_cast<char*>(array);
int* shifted = reinterpret_cast<int*>(bytes + 1);

*shifted = 1; // UB: адрес, вероятно, не выровнен для int.
```

Одного `reinterpret_cast` недостаточно для появления корректного объекта по произвольному адресу. Помимо выравнивания необходимо учитывать наличие хранилища, время жизни объекта и допустимость доступа к соответствующим байтам.

### `alignas`

`alignas` усиливает требование к выравниванию объекта или типа:

```cpp
struct alignas(64) CacheLineData {
    int value;
};

alignas(32) std::byte buffer[128];
```

```cpp
static_assert(alignof(CacheLineData) == 64);
```

Реализация может не поддерживать произвольное число: корректное выравнивание должно быть допустимым для платформы. Более слабое ненулевое `alignas`, которое попыталось бы уменьшить естественное выравнивание типа, некорректно.

Тип, чьё требование больше стандартного гарантированного выравнивания обычной выделяющей функции, называют over-aligned. Начиная с C++17 `new`-выражение может выбирать формы `operator new` с параметром `std::align_val_t`, а парное удаление должно использовать согласованную aligned-форму.

### `std::align`

`std::align` ищет внутри существующего буфера подходяще выровненный участок:

```cpp
alignas(std::max_align_t) std::byte buffer[128];

void* pointer = buffer;
std::size_t space = sizeof(buffer);

void* result = std::align(
    alignof(double),
    sizeof(double),
    pointer,
    space
);
```

Если места достаточно, функция возвращает выровненный адрес и одновременно изменяет `pointer` и `space`: указатель сдвигается к найденной позиции, а `space` уменьшается на размер пропущенного префикса. Размер размещаемого объекта автоматически из `space` не вычитается — владелец буфера должен сам учесть занятые байты перед следующим размещением.

Если подходящего участка нет, возвращается `nullptr`, а входные `pointer` и `space` не изменяются.

`malloc` возвращает память, выровненную достаточно для типов с обычным фундаментальным требованием выравнивания. Для расширенно выровненных типов нужны соответствующие aligned-механизмы; нельзя безусловно считать обычный `malloc` достаточным для любого `alignas`.

### Битовые поля

Битовое поле позволяет задать ширину поля в битах:

```cpp
struct Flags {
    unsigned ready : 1;
    unsigned mode : 3;
    unsigned error : 1;
};
```

Это не переносимый способ точно задать двоичный формат структуры. Порядок размещения битовых полей, направление упаковки и переход через границы единиц хранения во многом зависят от реализации.

У битового поля нет отдельного адреса, поэтому получить обычный указатель на него нельзя. По той же причине к нему нельзя привязать обычную неконстантную ссылку так, как к самостоятельному объекту.

Присваивание значения, не помещающегося в битовое поле, не является автоматически UB. Однако итоговое значение в таком случае определяется реализацией:

```cpp
Flags flags{};
flags.mode = 10; // 10 не представимо тремя битами.
```

Распространённая реализация оставит младшие три бита и получит `2`, но переносимый код не должен на это рассчитывать. Для знаковых полей дополнительно зависит от реализации их допустимый диапазон и представление.

## §9.5. Scoped-аллокаторы

Вложенный контейнер содержит два уровня объектов:

```text
vector
  -> string
  -> string
  -> string
```

Аллокатор внешнего `vector` используется для памяти под объекты строк. Однако каждая строка сама выделяет память под символы через собственный аллокатор. Обычная передача аллокатора во внешний контейнер не означает, что он автоматически попадёт во внутренние элементы.

```cpp
template <typename T>
using MyAlloc = CustomAllocator<T>;

using MyString = std::basic_string<
    char,
    std::char_traits<char>,
    MyAlloc<char>
>;

using OuterAlloc = MyAlloc<MyString>;
std::vector<MyString, OuterAlloc> strings(OuterAlloc{resource});
```

`OuterAlloc` выделяет место под `MyString`, но конструктор каждой строки ещё должен получить `MyAlloc<char>` с нужным ресурсом. Если этого не сделать, внутренний объект может использовать аллокатор по умолчанию или иное состояние.

### `std::scoped_allocator_adaptor`

`std::scoped_allocator_adaptor` передаёт внутренний аллокатор allocator-aware элементам при их конструировании:

```cpp
using InnerAlloc = MyAlloc<char>;
using OuterAlloc = MyAlloc<MyString>;
using ScopedAlloc = std::scoped_allocator_adaptor<
    OuterAlloc,
    InnerAlloc
>;

ScopedAlloc allocator(
    OuterAlloc{resource},
    InnerAlloc{resource}
);

std::vector<MyString, ScopedAlloc> strings(allocator);
strings.emplace_back("abc");
strings.emplace_back("cde");
```

Внешняя часть используется самим `vector`, внутренняя — при создании его элементов. Для более глубокой вложенности адаптер может содержать несколько уровней внутренних аллокаторов.

Пример со `std::allocator` формально возможен, но плохо демонстрирует смысл: его экземпляры не несут различимого пользовательского ресурса. Польза становится заметна у stateful-аллокатора, связанного с конкретным пулом или буфером.

### `uses_allocator`

Traits проверяет, объявляет ли тип поддержку соответствующего аллокатора:

```cpp
std::uses_allocator_v<Element, InnerAlloc>
```

Если тип поддерживает аллокатор, стандартная модель допускает две формы конструктора:

```cpp
Element(std::allocator_arg_t, const Alloc&, arguments...);
```

или:

```cpp
Element(arguments..., const Alloc&);
```

Адаптер выбирает допустимую форму и добавляет внутренний аллокатор. Если тип не является allocator-aware, он конструируется только из исходных аргументов.

Упрощённая идея выглядит так:

```cpp
template <typename OuterAlloc, typename InnerAlloc>
class SimplifiedScopedAllocator {
private:
    OuterAlloc outer_;
    InnerAlloc inner_;

public:
    template <typename T, typename... Args>
    void construct(T* pointer, Args&&... arguments) {
        if constexpr (std::uses_allocator_v<T, InnerAlloc>) {
            if constexpr (std::is_constructible_v<
                              T,
                              std::allocator_arg_t,
                              const InnerAlloc&,
                              Args...>) {
                std::allocator_traits<OuterAlloc>::construct(
                    outer_,
                    pointer,
                    std::allocator_arg,
                    inner_,
                    std::forward<Args>(arguments)...
                );
            } else {
                static_assert(std::is_constructible_v<
                    T,
                    Args...,
                    const InnerAlloc&
                >);

                std::allocator_traits<OuterAlloc>::construct(
                    outer_,
                    pointer,
                    std::forward<Args>(arguments)...,
                    inner_
                );
            }
        } else {
            std::allocator_traits<OuterAlloc>::construct(
                outer_,
                pointer,
                std::forward<Args>(arguments)...
            );
        }
    }
};
```

Настоящий `scoped_allocator_adaptor` дополнительно выбирает между префиксной и суффиксной формами конструктора, перепривязывает типы и рекурсивно передаёт аллокаторы на следующие уровни.

Он не создаётся ради того, чтобы «не создавать новый объект аллокатора» вообще: небольшие объекты аллокаторов всё равно могут копироваться. Его задача — правильно распространить связанное с ресурсом состояние во вложенные allocator-aware объекты.

## §9.6. Атрибуты

Атрибуты записываются в двойных квадратных скобках и передают реализации дополнительную информацию:

```cpp
[[attribute]] declaration;
```

Они могут влиять на диагностику, оптимизацию или размещение объектов. Атрибут не является произвольным комментарием: у каждого стандартного атрибута есть допустимые позиции и формальная семантика.

### `[[no_unique_address]]`

Атрибут C++20 разрешает полю потенциально не занимать отдельный адрес, если его тип это допускает:

```cpp
template <typename T, typename Alloc>
class Container {
private:
    T* data_ = nullptr;
    std::size_t size_ = 0;
    [[no_unique_address]] Alloc allocator_;
};
```

Пустой аллокатор логически является полем, но реализация может разместить его без увеличения размера контейнера, подобно Empty Base Optimization. Атрибут не гарантирует конкретный размер: он разрешает оптимизацию, учитывая остальные ограничения объектной модели.

Для непустого аллокатора его состояние всё равно нужно где-то хранить.

### `[[nodiscard]]`

`[[nodiscard]]` появился в C++17. Если результат помеченной функции или объект помеченного типа игнорируется, компилятору рекомендуется выдать предупреждение:

```cpp
[[nodiscard]] bool save();

save(); // Обычно предупреждение: результат проверки потерян.
```

Атрибут уместен, когда игнорирование результата часто означает ошибку. Поэтому им помечают функции вроде `empty()`: вызов `container.empty();` легко перепутать с очищающим действием, хотя он лишь возвращает `bool`.

Функции выделения памяти также возвращают критически важный адрес. Однако `nodiscard` остаётся диагностикой, а не запретом языка: корректная программа может явно отбросить результат, например приведением к `void`, если это действительно намеренно.

Начиная с C++20 атрибут может содержать пояснение:

```cpp
[[nodiscard("check whether the operation succeeded")]]
Result perform();
```

### `[[deprecated]]`

Атрибут отмечает устаревший интерфейс:

```cpp
[[deprecated("use parse_v2 instead")]]
Result parse_v1(std::string_view text);
```

Использование остаётся допустимым, но реализация обычно предупреждает о необходимости миграции. Это позволяет постепенно заменить публичный интерфейс, не ломая сборку всех клиентов немедленно.

### `[[maybe_unused]]`

`[[maybe_unused]]` подавляет предупреждение о сущности, которая намеренно может не использоваться:

```cpp
void process([[maybe_unused]] int debug_id) {
#ifdef ENABLE_DEBUG_LOG
    log(debug_id);
#endif
}
```

Атрибут полезен в шаблонах и условно компилируемом коде, где использование зависит от конкретной инстанциации или конфигурации. Он не заставляет компилятор удалить переменную и не меняет её время жизни.

### `[[likely]]` и `[[unlikely]]`

Начиная с C++20 атрибутами можно указать ожидаемую вероятность пути выполнения:

```cpp
if (value >= 0) [[likely]] {
    process(value);
} else [[unlikely]] {
    report_error(value);
}
```

Это подсказка оптимизатору, а не условие корректности. «Маловероятная» ветка продолжает работать и обязана быть корректной. Неправильная подсказка может ухудшить производительность, поэтому её стоит применять при наличии измерений или надёжного знания распределения данных.

Атрибут относится к метке ветви или инструкции, а не является заменой обычного условия.

### `[[assume]]`

`[[assume(expression)]]` появился в C++23 и сообщает, что выражение истинно в данной точке:

```cpp
void process(int* pointer) {
    [[assume(pointer != nullptr)]];
    use(*pointer);
}
```

Если предположение нарушено, поведение не определено. Это не проверка наподобие `assert`: атрибут не обязан вычислять условие и сообщать об ошибке. В выражение предположения нельзя закладывать необходимые побочные эффекты.

`assume` следует использовать только для факта, который уже гарантирован логикой программы или внешним контрактом. Иначе оптимизатор получает право удалить проверки и преобразовать код на основании ложного утверждения.

### `[[noreturn]]`

`[[noreturn]]` с C++11 отмечает функцию, которая не возвращает управление вызывающему коду обычным способом:

```cpp
[[noreturn]] void fail(const char* message) {
    throw std::runtime_error(message);
}
```

Функция может завершить процесс или всегда выбрасывать исключение. Если выполнение помеченной функции всё же достигнет возврата вызывающему коду, поведение не определено.

Атрибут помогает диагностике и анализу потока управления. Например, после вызова `fail` компилятор знает, что продолжения по этой ветке не существует.
